# Put a repo in conditions for repo-panel (padrón 1.1)

You are in the pi session of ONE repo, and the user typed an order that points you here. The order names the requirement ids to apply and the padrón version. Follow this file; do nothing outside it. Worked examples are in `requirements/EXAMPLES.md`: read them before steps 5, 7 and 8.

1. Read `requirements.json` in the panel folder (the folder that contains this `requirements/` folder). Each requirement has an `id`, a `title`, a `level` and a `remedy`.
2. Apply ONLY the ids named in the order. Skip every other requirement, even if it looks incomplete.
3. For each id, follow its `remedy`. The versioned blocks you add to `AGENTS.md` are the files in `requirements/blocks/`: copy the whole file, opening and closing markers included, unchanged.
   - `registro.md` and `ciclo.md` use the markers `<!-- orquestacion:registro v1.0 -->` and `<!-- /orquestacion:registro -->` (the same for `ciclo`); the panel's own `tareas.md`, `entrega.md` and `estado.md` use `<!-- panel:tareas v1.0 -->` and `<!-- /panel:tareas -->` (the same for `entrega` and `estado`).
   - Put the blocks right after the title and the one-line description at the top of `AGENTS.md`, in this order: `registro`, `tareas`, `entrega`, `ciclo`, `estado`. Leave the rest of the file where it is: do not reorder, reword or summarize the repo's technical rules. A block that is already there with an older version is replaced where it stands, whole.
   - The `ciclo` block has regions between `<!-- SALA -->` and `<!-- /SALA -->`: keep the region (both marker lines and everything between them) when the repo is a member of a room or when the order names `sala-region`; remove it only when neither applies. If a kept region is missing from the `ciclo` block already in `AGENTS.md`, restore it exactly as in `requirements/blocks/ciclo.md`.
4. For `panel-ignored`, append the line `.panel/` to `.git/info/exclude` of the repo (create the file if it does not exist, and do not duplicate the line). Never add it to `.gitignore` and never commit it: it is local to this clone, so there is nothing to deliver.
5. `AGENTS.md` is the ONLY instruction file of the repo.
   - Other files that give instructions to agents (`.cursorrules`, `ai-instructions.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, pull request templates, ...) are obsolete for this repo: do not follow them, do not edit them and do not delete them.
   - If `AGENTS.md` names another file as the authority (a "Document Authority" section, "see X for the rules"), replace that statement with one line saying that `AGENTS.md` is the only source of instructions of the repo, and keep the links to technical documents (architecture, API, data model).
   - In your last answer, for each such file give its path, the date of its last commit (`git log -1 --format=%cs -- <path>`) and the headings it has that `AGENTS.md` does not, so the person decides what to move into `AGENTS.md` before removing it (example E).
   - Never delete existing rules from `AGENTS.md`, with ONE exception: the instructions that steps 7 and 8 tell you to remove. Add the blocks to the existing `AGENTS.md`, or create the file if it does not exist.
6. If `AGENTS.md` already has a rule that conflicts with a block, STOP. Quote both rules, ask the user which one wins, and wait. Do not decide alone. The exceptions are what the user already decided: how tasks are created or managed (step 7), branches, commits and pull requests (step 8), and which file is the authority (step 5). Those are never asked: the panel's mechanism wins.
7. Tasks have ONE mechanism, the one the `tareas` block states: every task is a row of `docs/ROADMAP.md`.
   - Format: the three header lines (`**Dónde está:**`, `**Qué sigue:**`, `**Qué lo bloquea:**`) and the units table. The header of the table has exactly these column names, spelled like this and in any order: `ID`, `Entrega` (what the unit delivers), `Depende de` (its dependencies), `Estado` (one word) and, optionally, `Resultado visible`, `Notas` and `Ficha`.
   - A table that already exists in `docs/ROADMAP.md` with other names (for example `Unidad` or `Dependencias`): rename those headers to the names above and keep every row (example A).
   - Any other way the repo tracks tasks (`planning/`, a `ROADMAP.md` at the root, task lists or boards kept in files): migrate it, and do not ask which system to keep: the user already decided to abandon every other one. Write one row per task, keeping its existing ID (propose a short one only when it has none), its state translated with the table of example C, `Depende de` only from the dependencies the source declares (otherwise write `—`: never infer or invent dependencies) and `Ficha` pointing to its existing file or folder (example B).
   - A work breakdown kept inside each change (OpenSpec `openspec/changes/<name>/tasks.md`, fichas with a checklist) is not a task list: leave it where it is, as history, and never write a row per checkbox. Import only what is still pending: for each change with unchecked items write ONE row (ID = the name of the change, `Estado` `Pendiente`, `Ficha` = its folder, `Notas` = `Migrada; sin verificar si ya se implementó (N de M pasos sin marcar)`) and list those changes in your report (example F). Changes with every item checked, and archived ones, get no row.
   - Do not check whether the pending work is already implemented: you cannot tell from the code (a step can be reopened on purpose by an audit, a gate is a decision), and a wrong `Completada` hides work. The `tareas` block says to verify it, with evidence and the person's OK, when the row is taken.
   - A state with a pause (for example `Paused - ...`) is `Bloqueada` if the source names what blocks it, otherwise `Pendiente`; keep the pause in `Notas` (example C).
   - Never delete the old task files: they become the fichas. Replace an old index or summary that repeats statuses with one line pointing to `docs/ROADMAP.md`, and update the links that pointed to a roadmap you moved.
   - Remove from `AGENTS.md` every instruction about how to create, name, prioritize, track, assign or close tasks (templates, planning workflows, state vocabularies, backlog rules): the `tareas` block replaces them. Keep every other rule.
   - STOP and ask the user only when a task's ID or state cannot be derived from its source (a state word that is not in example C, a task without a name).
   - Do not invent units: if the project has no tasks, ask the user for the plan; until they answer, the table may hold only row `U0` (`Entrega`: `Adoptar la Orquestación`, `Depende de`: `—`, `Estado`: `Completada`), which records the adoption itself.
8. Delivery belongs to the person, with `/flow-base`, `/flow-commit` and `/flow-pr`; the `entrega` block states it.
   - Never create or switch branches, even during this installation: leave the changes in the working tree, on the branch you are on. `/flow-commit` creates the branch itself when the current one is protected.
   - Never commit by any means other than `/flow-commit`, and never push or open a pull request. Do not use `git add` or `git mv` (step 9).
   - Before the first file, check what the gate of the `ciclo` block asks: you are on the base branch, the tree is clean and without stash, and the local base branch equals the remote one (`git fetch`). If not, write nothing and tell the person what is missing (normally: run `/flow-base`).
   - Remove from `AGENTS.md` every instruction about branch names or branching strategy for day-to-day work, commit message format, and pull request format or process (Git Flow sections, commit conventions, PR templates): the `entrega` block replaces them. Keep the lines that say what a long-lived branch is for (production, release, hotfix or deployment branches), because pipelines may depend on them, and report them (example D). If you are unsure whether a rule is about branches, commits or pull requests, keep it.
9. Never use `git mv` or `git add`: leave the git index empty (use plain file operations to move or rename files), because `/flow-commit` refuses to start when files are staged.
10. Record the padrón: write in `docs/ORQUESTACION.md` the line `- **Padrón del panel:** ` followed by the padrón version of the order (the one in the title of this file). If the file does not exist, create it with the date of adoption, the profile, the version of each block installed (say when `ciclo` was installed without its `SALA` regions), the rules not adopted or changed (write none when there is none) and that line. Do it last, after every other id of the order.
11. Your last answer has two parts, in the user's language: first the report (example E): what you migrated, each task with its ID and state; what you removed from `AGENTS.md`, each with its heading and line count; the instruction files that are now obsolete (step 5); and anything you could not do. Then ONE last line, `Siguiente: ...`, with the next step for the user (normally: run `/flow-commit`).
