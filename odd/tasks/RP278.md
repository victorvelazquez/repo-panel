# RP278: el merge no cuelga ni devuelve errores crudos

Pedido de Dirección (sala UPEN), 2026-11-25. Fila RP278 de `docs/ROADMAP.md`. Plan aprobado (L2, L3).
Zona crítica (ejecutar la fusión): pruebas primero y vistas fallar, prueba del abuso, suite completa, CRLF, mutación corta, verificación independiente, PR propio.
Estado: en implementación.

## Specs

- S1. Mensaje claro: cuando una llamada a `gh` del merge devuelve una salida vacía o cortada (el `JSON.parse` falla), el texto del error de Go «unexpected end of JSON input», un cuerpo de 5xx de GitHub («Server Error», `HTTP 5xx`) o la mató el tope de tiempo, `POST /api/merge` responde un mensaje fijo: «GitHub did not answer in time: check the PR on GitHub before retrying». Nunca un `SyntaxError` crudo ni un 500. Un rechazo claro de GitHub (por ejemplo 405 «Head branch was modified», 409) sigue mostrando su primera línea real, como hoy.
- S2. Tope corto: cada llamada a `gh` del camino del merge (`repoMeta`, `viewPr`, el `PUT` de la fusión, la relectura y el `DELETE` de la rama) lleva su propio tope, más corto que los 60 s por defecto (20 s para las lecturas, 30 s para el `PUT`).
- S3. Resultado incierto: si el `PUT` falla sin un rechazo claro, el panel relee el PR unas 3 veces, separadas un par de segundos, con el tope corto. `MERGED` es éxito (`{merged:true}`, como hoy). `OPEN` responde 502 con el motivo. Si no se pudo leer, 502 «GitHub did not confirm the merge: check the PR on GitHub before retrying».
- S4. Tope de la espera de un lugar: «si no hay lugar en 20 s, el panel responde 503 con un mensaje claro en vez de colgarse». Es una opción de `server/exec.js` que usa solo el camino del merge; las demás llamadas a `gh` y `git` siguen esperando lugar como hoy (prueba de que no cambian). Un pedido que se rinde sale de la cola y no corre después.
- S5. Nada de esto cambia el éxito normal: un merge que GitHub acepta responde igual que hoy, con la misma cantidad de llamadas a `gh` (la relectura solo corre cuando el `PUT` falla).
