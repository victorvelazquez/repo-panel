# Serie de sesiones: abrir, cerrar y cambiar la sesión de cada repo (RP98 a RP100)
Ficha de las filas RP98, RP99 y RP100 de `docs/ROADMAP.md`. Hoy el modelo es una sesión adoptada por repo para siempre: el chat (`chatBody` en `public/resumen.js`) lista sesiones solo cuando no hay ninguna adoptada, y la ✕ solo oculta la tarjeta.
El host de sesiones vivas es `server/rpchost.js` (`createRpcHost`, un proceso de pi por repo, hasta 6) y la adopción vive en `server/sessions.js` (`config.json` `sessions`).

## Specs
- **S1. Origen.** «tambien veo que debemos tener una ux mejorada para abrir y cerrar sesiones de cada repo. ejempo, si el panel no tiene ni una sesion abierta, me debe mostrar una lista de sesion disponibles para abrir, o si no tiene ninguna sesion anterior iniciada debe permitir abrir o iniciar una sesion nueva. una vez estando en una sesion, debe permitir cerrar el chat de esa sesion y volver al listado de sesiones disponible para abrir y poder seleccionar cualquier otra sesion para abrir. y asi.»
- **S2. Decisiones.** Se le preguntó si cerrar una sesión también la «suelta» (vuelve a la lista) o solo detiene el proceso, y si debe haber una sesión viva por repo o varias a la vez, con una recomendación para cada una (cerrar detiene el proceso y vuelve a la lista; una sola viva por repo). La persona respondió: «voy por tu recomendacion a las preguntas que haces.»
- **S3. Qué es cerrar.** Tres cosas distintas: *ocultar el chat* (la ✕, la sesión sigue viva), *cerrar la sesión* (se detiene el proceso de pi del repo y se suelta la adopción, así el chat vuelve a la lista) y *cambiar de sesión* (abrir otra de la lista). Una sola sesión viva por repo.
- **S4. Nueva sesión.** El id de RP97 es por repo (`panel-<carpeta>-<id corto del repo>`): usarlo para «nueva» retomaría la anterior. Cada sesión nueva necesita su propio id.
- **S5. Terminal.** El panel no ve los procesos de pi abiertos en una terminal; abrir en el panel una sesión que también está abierta en Gentle Shell pondría dos procesos sobre el mismo archivo. Antes de avisar hay que averiguar si pi bloquea sus archivos de sesión.
- **S6. Decisiones de RP99.** Se le hicieron tres preguntas, cada una con una recomendación: qué hace Abrir, qué pasa con el cuadro para escribir cuando está la lista a la vista y cuántas sesiones se listan. La persona eligió las tres recomendaciones: «Mostrarla ya y arrancar al escribir (recomendado)» (Abrir adopta la sesión y muestra su historial al instante; el proceso de pi arranca al enviar el primer mensaje), «Deshabilitado con una razón (recomendado)» (con la lista a la vista el cuadro queda gris con la razón y nada se arranca sin que se pida) y «Hasta 20 con desplazamiento (recomendado)» (todas las que trae el servidor, en una lista que se desplaza). «Nueva sesión» crea una sesión con id propio (el de RP97 más una parte única) y solo se acepta cuando el repo no tiene sesión viva ni adoptada.
- **S7. Decisiones de RP100.** Se averiguó primero que pi no bloquea sus archivos de sesión (L7), así que el panel solo puede dar una pista, y se le hicieron dos preguntas con una recomendación cada una. La persona eligió las dos recomendaciones: «Etiqueta en la fila y confirmar al abrir (recomendado)» (la fila de una sesión tocada hace poco lleva una etiqueta y pulsar Open pregunta si se sigue; solo la página, el servidor no cambia) y «2 minutos (recomendado)» (una sesión cuyo archivo se escribió hace menos de 2 minutos cuenta como tocada hace poco). Límite que se le dijo a la persona: una terminal abierta pero quieta no escribe y no se detecta; es una pista, no una garantía.
- **S8. Decisiones de RP101.** Pedida por la persona al ver el 504 de «New session» dos veces seguidas: esperar más y decir la verdad. Tope del arranque de 2 a 5 minutos, una espera de la página un poco mayor que la del servidor, y el mismo mensaje claro para los dos cortes. No se muestra `stderr` de pi (el cliente solo deja pasar mensajes fijos); no se hace un indicador de tiempo transcurrido.
