# RP226: el método de fusión lo permite cada repo

La persona fusiona PRs de repos que permiten métodos distintos: `repo-panel` e `implementation-guides` no permiten merge commit; los otros 13 permiten los tres (medido el 2026-11-17 con `gh repo view`). Hoy el panel manda UN método global del navegador a todos, y GitHub rechaza el que el repo no admite. Se hace la forma 1 (automática); la forma 2 (método fijo por repo) NO se hace.

## Specs

- **S1.** El panel le pregunta a GitHub qué métodos permite cada repo (`mergeCommitAllowed`, `squashMergeAllowed`, `rebaseMergeAllowed`, vía `gh repo view --json`), con la caché que ya tiene `repoMeta` (10 minutos). Origen: L3, «Dejamos el repo como está y hacemos la forma 1, la automática».
- **S2.** Si el método pedido está permitido (o GitHub no dice nada de él), se usa ese, y la respuesta de `POST /api/merge` es la de siempre: `{ merged: true, branch }`, sin campos nuevos. Lo que ya andaba no cambia.
- **S3.** Si el método pedido NO está permitido, se usa uno permitido, en este orden: squash, rebase, merge (lectura del agente: es el orden del historial lineal de `repo-panel`, que la persona quiere conservar), y la respuesta agrega `method` (el usado) y `requested` (el pedido). El aviso de la página lo dice en el mismo `toast` de siempre, por ejemplo «merged with squash (merge is not allowed here)».
- **S4.** Si el repo no permite ningún método, `POST /api/merge` contesta 409 con un texto claro y NO manda ninguna orden de fusión a GitHub. Si `gh` no devuelve los campos (una versión vieja), se usa el método pedido como antes.
- **S5.** El panel nunca usa un método que el repo prohíbe. Fusionar es una acción que no se deshace.
- **S6.** La configuración de GitHub de ningún repo se toca: el panel solo lee. `API_VERSION` sigue en 15 (solo se agregan campos a una respuesta).
