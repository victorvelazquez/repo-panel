# Kletus.dev

A local, single-window dashboard for the repos you work on. It answers one question: **what is left for me to do?**

- A kanban board with one card per pending thing, in columns: **Clean · Changes · Committed · Pull requests · Merged**. A repo with local changes and a ready PR shows up in both columns.
- **Pull requests.** Every open PR lives in one **Pull requests** column (green top border): the ones **ready to merge** come first (with a green accent on the left of the card), then the ones that need a fix (red), then the ones whose checks are still running or that wait for review. Inside each group the order is the one GitHub gives.
- **Clean, Merged, Idle and Needs attention.** **Clean** is a column by default, first on the board: the compact rows of repos with nothing to do, plus the cards that need a person (a manual action, a failed `/flow-ship` with a clean tree). Repos whose branch already merged (`Merged: run /flow-base`, clean tree, nothing ahead) have their own purple **Merged** column. If you prefer a quieter board, untick **Clean column** in the header: the rows move to a collapsible **Idle · N repos** bar under the board (closed by default, its state is remembered; not drawn when no repo is idle) and the cards that need a person go to a red **Needs attention** column, leftmost, that exists only while it has cards. Tick it again (or press **Show as column** in the Idle bar) to go back; Merged stays in both layouts.
- **Merge feedback.** After you press **Merge** the button is disabled and reads `Merging…`, then `Merged ✓`, and stays that way until the repo has been refreshed and the card moves away; a failed merge enables it again at once.
- **Merge, then `/flow-base`.** After a merge made from the panel succeeds, it sends `/flow-base` to the repo's session by itself when that session is open and free (not working, not asking, no background jobs); otherwise it sends nothing, never starts a closed session, and the card keeps its `/flow-base` button. The toast says which one happened.
- Per repo: uncommitted files, `+/−` lines, unpushed commits, and a full diff viewer.
- Per open PR: CI status and a **Merge** button that only enables when every check is green and GitHub reports the PR as mergeable. PRs with failed checks, conflicts or an outdated branch stay in **Pull requests**, marked red as needing attention (the separate **Needs attention** column is for repos, not PRs).
- Repos organised in groups (personal, work, commercial…), shown as a colored tag on each card, with a group filter and a name search.
- A roadmap block on each repo card (in progress or next unit, progress bar, a problems badge and, on click, the roadmap header). It reads `docs/ROADMAP.md` from the remote base branch, not the working tree; repos without that file look unchanged.
- The states `Lista`, `En revisión` and `En curso` (derived) are computed from Git and GitHub, never written in the file. A unit is linked to a branch or an open PR by its ID inside the branch name or the PR title; those units are skipped when picking the next one (`siguiente`).
- A **Go work on** strip above the board lists the next actions in order: a PR ready to merge, a repo whose branch already merged (`/flow-base`; with uncommitted changes it is only that, never also "Deliver changes"), changes not delivered yet, and a clean repo with a next roadmap unit. Clicking a chip filters the board to that repo. A manual order in `priority` (see Configuration) wins over the automatic one.
- The strip also has two chips for repos that must not be delivered yet: **Manual action** (red) for a repo that needs a person's hands (detached HEAD, commits on the base branch, a merge or rebase in progress, a diverged branch, or a `/flow-ship` that needs attention) and **Waiting for you** (blue) for a repo whose declared state is `needs-input` or `blocked`, with its next step. Such repos are no longer told to deliver changes; the full text is in the chip's tooltip.
- The **Conformity** tab (with a count badge) is a full-width view, not a drawer: it hides the shared filters (they never applied to it), is never saved as the tab to reopen, and a repo name in it filters the board and takes you back to the tab you came from. It lists every repo, whatever the filters, that has no usable `docs/ROADMAP.md` or whose file has problems, with the line of each problem. Info-level problems (such as a dependency outside the table) are not listed. It is built from the roadmap read from the remote base branch, so unpushed edits do not show. Opening the panel at `http://127.0.0.1:<port>/#conformity` opens that drawer on load.
- The Conformity tab also shows the **requirements** a repo must meet to show well in the panel, listed in `requirements.json` at the panel root, and the **prerequisites** of this machine (`git`, `gh` logged in, `pi`). Failing, outdated and unavailable requirements come first, with their level (`required` or `recommended`), their category and a remedy (the instruction an AI agent applies in that repo, shown as a second line); passing ones are collapsed. The panel only **detects**: it reads the remote base branch and never edits a file of another repo; applying a remedy is the agent's job, through `/flow-ship` and `/flow-pr`. Whether `flow-skills` is registered in pi is not checked. The required `manual-leftovers` requirement detects what the order cannot name by itself: a manual section of `AGENTS.md` outside the blocks (for example a `## Orquestación` with Puerta, Avisos a Dirección, Tamaño, Verificación según el riesgo or Contratos entre proyectos) that restates what an installed block already says, or the old `/flow-branch`; it removes every block region and looks at what is left (headings of level 2 to 4 with those exact titles, and the text `/flow-branch`), and the detail lists at most 5 findings. It exists because the order only names the ids that fail, so a repo whose `registro` and `ciclo` pass would otherwise never be asked to apply the "replace the WHOLE section" rule of `requirements/INSTALL.md` step 3.
- A card of a repo that lacks a **required** requirement shows one small warning with the number, "⚠ N" (RP94b: the tooltip and the aria-label say "N requirements missing" and list the ids); to hide it, use "Hide warning" in the card menu. A gap that is only recommended shows nothing on the card (the drawer still lists it), and nothing is shown while the requirements load or if they failed to load. Hiding the warning keeps the repo on the panel with the basic features; the choice is saved as `dismissed` in `config.json`.
- A **⋯** menu on each card holds "Put in conditions", present only while some requirement is not passing, and "Hide warning" / "Show warning"; its last item is "Remove from panel…" (RP94: it replaced the loose ✕ button, asks before it removes and deletes nothing from disk or GitHub). "Put in conditions" asks `POST /api/pi` with the key `put-in-conditions`; the server builds ONE line from the repo's requirements (the ids that are not passing, required first) that tells the agent in the open session to read `requirements/INSTALL.md` (absolute path, in double quotes, with the user's authorization to read that one file outside the repo) and apply those ids. It needs a started, idle session of the repo, like the other buttons, and it refuses with 409 when everything already passes or the requirements could not be read. `confirmed` only means pi took the prompt to start a run (RP233); it does not prove the agent read or applied anything.
- **Answering a question from the panel (RPC2-3).** When pi asks something (a permission such as *Allow guarded git push?*, a `select`, an `input` or an `editor`) the chat shows a card under the history with the title and the FULL message (the command) as escaped text, and the answer is a click: `POST /api/rpc/dialog` `{ id, requestId, ... }`, once (the buttons lock at the click). The server checks the SHAPE against the method of the pending dialog before it writes anything to the agent: `confirm` takes `{ confirmed: boolean }`, `select` takes `{ value }` only when it is one of the options it showed, `input` and `editor` take `{ value }` (LF and TAB only, up to 4000 characters), any of them takes `{ cancelled: true }`; anything else (an extra key, another shape, two shapes) is a fixed 400 and the dialog stays pending. A title is cut at 300 characters, a message at 4000 and options at 20 of 200; when anything is cut the dialog carries `truncated: true`. **RP245 (parity with the terminal, decided by the person):** a dialog whose text is cut (by the server, or with an ellipsis at its end or at its start), empty or with hidden characters is still answered with all its options, as in the terminal, which shows the same preview; the card adds the note «The text is cut or has hidden characters: it is the same preview the terminal shows» and keeps showing hidden characters as markers (⟦U+200B⟧). An option the server cut cannot be chosen (the session expects the whole text): it is drawn disabled with «This option is cut: answer it in the terminal», and the server never takes a value that a cut option also shows. **Deny** comes first in a confirm, which has no «Allow always», and no key answers. **RP237:** with the interactive variable the session asks a guarded command as an «Allow…» select whose title carries the command on its second line (`Allow guarded git push?` then `git push origin HEAD`); the card reads the first line as the question and the rest as the command, shown as the session sends it (the same preview the terminal shows: whitespace collapsed, at most 180 characters), and offers every option the session sends, in its order (`Allow once`, `Allow for this session`, `Always allow …`, `Deny`, the last one drawn as a refusing button), as the terminal does (the person chose parity with the terminal). A command cut at its end or at its START (a leading «…», which the session adds when the guarded action is far into the command) or with a hidden character gets the note above, and since RP245 its options are offered too; a command that merely starts with dots (`../scripts/x.sh`, `./run.sh`) is not a cut and has no note. The commands pi names `/gentle:yolo:1`, `/gentle:mode:2` and so on (when two extensions register the same name) are refused too.
- **The right column is tabs; its Changes tab (RP92, RP128).** With the right column in (from 1100 px of layout, see RP89) the column is a row of TABS (RP128): Tasks, Changes, Status and Files, in the order of the cycle (a tab with nothing to show is not drawn). Only the open tab shows its name, the others are icons (and in a column narrower than 300 px none does); the arrows, Home and End move between them, and the open tab and the folded folders belong to the opening of the repo. It starts on the tab that fits the situation (RP148), decided once, as soon as the repo's facts are known: **Changes** with uncommitted changes, **Status** when the branch has an open pull request, **Tasks** when the tree is clean with nothing ahead to deliver, and Changes in any other case; a tab you choose with a click is never replaced, and the choice does not move by itself when the situation changes. The Changes tab lists the files with uncommitted changes of the open repo as a TREE of folders: the total on top (files, added and deleted lines), one row per folder with its count (a chain of single folders is one row, folders come first, each one can be folded), and for each file its name (the whole path is its tooltip; a long name is clipped), the added and deleted lines (`bin` for a binary file) and its status letter, at most 200 files with the rest counted. It is drawn from the facts the board already keeps fresh, so it reads nothing new and is never stale. Touching a file opens it in the diff tab of the centre block (RP90) and marks it in the tree. With the column in, the Changes tab of the chat is gone (the card replaces it) and the chip **● N files** of a card opens the repo on the chat, where the card is; under 1100 px, where there is no column, the Changes tab stays as before. The Files tab (RP65) is not touched. In the Changes tree a folder has a filled blue icon and a file an outline grey one; each level is indented 16 px (8 px in a narrow column) and a file sits one level to the right of its folder.
- **Projects tab (RP220).** The right column of a room (its folder open in the chat, RP218) hides the Tasks tab, because a room carries no roadmap, and gets a first tab, **Projects** (the repos assigned to the room, its members; the card of the room calls them projects too), which is the one it opens on: one block per member, with a line between one block and the next, showing the state of its session (the live one, as in the card of the list), how long ago it moved with the subject of its last commit, and its PR with its CI, or "no open PR". A member that is not a repo of the panel is listed as "not in the panel". It is read-only and reads what the page already has (no new route and no new field in RP220); Changes, Status, Files and, on a phone, Notes stay, and the arrows of the keyboard walk Projects, Changes, Status and Files in a room. A repo that is not a room keeps its tabs as they were. The card of the room, its chat and this tab are built from the configuration of the page (`GET /api/config`: name, folder and members, instant) and do NOT wait for `GET /api/rooms`, which runs git and can take tens of seconds (the page gives up after 25 s); that read only completes the card (its last commit) and the Conformity requirements, and if it fails the page keeps its last good data. A free member also says how its last task ended (RP228): **Finished**, **Failed** or **Stopped** (a task the person stopped by hand), with an icon, for 15 minutes or until another task starts; the row of the Summary gained `session.last` for it, so `API_VERSION` is 16. The report on demand (RP229) is a separate row.
- **Diff tab (RP90).** The tab bar of the centre block gets ONE more tab, the last one, once a file is open in it: it is named after the file (the whole path is its tooltip), it has its own ✕ to close it, it is reused for every file you open (it never multiplies) and it stays in the bar when you go back to the chat, where touching it shows the diff again (the diff is read again each time you switch to it, because the files change). Changing repo drops it. It draws the diff viewer of the Changes tab for that one file, from the same `GET /api/diff` (the server did not change); a file that is not changed any more says so. A file is opened by touching it in the files card of the right column (RP92) or, where there is no column, in the list of the Changes tab, which always lists every file.
- **Open and New session (RP99).** With no session adopted for the repo the chat shows the list of the folder's sessions (up to 20, newest first, in a box that scrolls) with an **Open** button per session and a **New session** button. **Open** adopts that session and shows its history at once; the pi process starts when the first message is sent. **New session** calls `POST /api/rpc/start { id, new: true }` (`new` is `true` or absent, anything else is `400`): it starts a session with its OWN id (`panel-<folder>-<repo id>-<6 hex>`, so a new session never resumes an old one) and adopts it; it is `409` when the repo already has a live or an adopted session (close it first). While the list is in view the Send button is disabled and the box says why, so nothing starts or is adopted without being asked. A start takes up to five minutes, so while one is on its way (and while a session is live) `POST /api/sessions/adopt` is `409` (close it first) and the Open buttons are disabled: the chat never shows the history of one session while another one runs.
- **A session open in a terminal (RP100).** pi does not lock its session files (it creates the file with an exclusive flag the first time it writes and then appends lines), so two programs on the same session mix up its history and the panel cannot see your terminals. The hint it has is the last write of the session file, which the list already shows: a session written to less than 2 minutes ago gets the tag "Active a moment ago, it may be open in a terminal" and **Open** asks before adopting it. Only the page does this (the server does not change). A terminal that is open but quiet writes nothing and is not detected: it is a hint, not a guarantee.
- **Open the session in a normal terminal (RP118).** In the ⋮ menu of the head of the chat (RP195), before *Close session*, a *Terminal* item shows the line to run in PowerShell (or a POSIX shell) to open the session of the repo with the whole interface of pi: the folder of the repo and the launcher of the active runtime (Gentle Shell, not the original `pi`, which keeps its sessions elsewhere) with `--session-id` and the real id of the session, and a *Copy* button. The server writes the line (`GET /api/terminal?id=<repo id>`, token required, read only): the folder and the launcher go in single quotes, the id is only letters, digits, dot, dash and underscore, and it refuses what it cannot carry safely, such as a control character, a character that shows one thing and runs another (direction marks, zero-width characters, odd spaces) or, on Windows, a typographic quote or one of `& | < > ^ %` in the folder name (cmd.exe reads those as operators, so the block is labelled *PowerShell*: paste it there). It only shows the line: it does not open a terminal and does not close the session, so close it in the panel first (pi does not lock its session files, RP100).
- **New session (RP264).** A **New session** item of the ⋮ menu of the head of the chat, right before *Close session*, and typing `/new` in the chat box, start a new conversation with a clean context on the SAME pi process (pi's own `new_session`, the `/new` of the terminal; over RPC pi does not run a typed `/new`, so before this it reached pi as a message and stayed working). It calls `POST /api/rpc/renew { id }` (token required; only the repo id is read). Only a free session may: a session that is answering, asking, compacting, running a shell command, starting or already switching answers 409 with a fixed message, and while it switches every other message, steer, shell command and compaction is refused too (Stop still goes). The id pi names for the new conversation (read with `get_state` and checked like any session id) becomes the adopted session of the repo, so a restart comes back to it; the old conversation stays in its file and in the list of sessions. Every open tab hears the `renewed` event and reads the history and the context again. If an extension cancels the switch, nothing changes and the chat says so; if pi switched but its new id cannot be read, the session is closed rather than left showing the old conversation.
- **Close session (RP98).** A **Close session** item of the ⋮ menu of the head of the chat (RP195; it was a button at the right of the session state in the composer frame), shows while the repo has a session (adopted or live). It calls `POST /api/rpc/close { id }` (token required; the repo comes from the config by id; any other field is ignored): the pi process of that repo is stopped, also one that is still starting (its start, and any start that joined it, then fails with `409 The session was closed` and adopts nothing), the adoption of that repo is released (a session the browser names is never touched) and the answer is the closed status. **Orderly close (RP238).** The answer comes at once, but pi is not cut: the panel ends its stdin, which makes pi save its session file and exit by itself (about 13 s measured through the launcher), and only a pi still alive after a 20 s grace is killed with its tree (`taskkill /T /F` on Windows, `SIGKILL` to its process group elsewhere); a pi that already exited is never killed (on POSIX this means a process group it left behind is not killed either, since its id may already belong to another process). After a kill the close counts as done once pi reports its exit, or at most 2 s later. Once the panel is shutting down, a new start is refused with `503 The panel is shutting down`. Until that pi is gone, a new start of the same repo waits (it shows `starting`), so two pi never write the same session file; other repos are not held. The chat goes back to the list of the folder's sessions, where one can be adopted or a new one started. A session that is working or asking is confirmed first. The ✕ of the chat only hides it: the session keeps running. Closing frees one of the 6 live slots; one live session per repo.
- **Side by side (RP66c).** A **Side by side** button above the diff (in the Changes tab and in the diff tab) shows the changes in two columns, old on the left and new on the right: context on both sides, and a group of deleted lines next to a group of added ones, one by one. The choice is kept in the browser with the other preferences (`prefs.split`). When the code box is narrower than 700 px the two halves stack (deleted first, the context once), with CSS only, so nothing is redrawn. The colors and the escaping are the ones of the unified view.
- **Changes tab (RP64).** The same right panel has a third tab, Changes: the single code viewer. Click the **● N files** chip of a card (on the Summary or on the Work board; from Work the page goes to the Summary first) to open that repo on Changes. It shows the list of changed files (status, path, added and deleted lines; click one to open it in the diff tab of the centre block, RP90) and the code of the uncommitted diff with two line-number gutters (old and new), hunk headers and the added and deleted lines coloured. It reads the existing `GET /api/diff` each time you switch to the tab, keeps the last good answer if a later read fails, and draws at most 2000 code rows (then a "+N more lines" note). It replaced the old diff drawer; the Conformity drawer is unchanged. The composer is hidden on this tab and nothing is ever sent from it.
- **Files tab (RP65).** The right panel has a fourth tab, Files: a tree of the repo's files (folders folded, except the ones that hold a changed file) and, below it, the file you pick, in the same numbered-lines look as Changes, with its **changed lines highlighted** (an untracked file is changed on every line). It reads only: `GET /api/files?id=<repo>` lists what git knows (tracked plus untracked and not ignored) and `GET /api/file?id=<repo>&path=<path>` reads one of those files. Files that look like secrets are shown (your decision), but a path is served only when it is a plain repo-relative path, is exactly an entry of git's listing, is a regular file (a symlink is never followed) whose real path stays inside the repo, and is not under `.git`; ignored files (such as `.env`) are never listed or served, and a refused request always gives the same `File not found`. Files over 1 MiB and binary files show a note instead of text. An image of the repo (RP268: png, jpg, gif or webp, told by its first bytes and not by its name, up to 5 MiB) shows as an image, with an **Open in new tab** link that opens it alone in the browser; its bytes come from `GET /api/file/image?id=<repo>&path=<path>`, with the same guards as `GET /api/file`, only when the bytes are one of those types (any other file is a 415, SVG included, which stays text), sent with `nosniff` and a sandbox. Known limits: the file is re-opened after the checks (a local process that can write inside the repo could race it), and each read runs two `git ls-files`. The tree uses the same look as the Changes tree (RP146): a folder is a chevron, a filled blue folder icon and its name, a file is an outline grey icon one level to the right of its folder, with the same indent step (16 px, 8 px in a narrow column) and no guide lines; Modified stays yellow with its letter.
- **Notes server (RP93, the tab is RP93b).** `GET /api/notes?id=<repo id>` reads and `POST /api/notes` (`{ id, text, base }`) saves the notes of a repo: ONE fixed file, `.panel/notas.md` inside it; the page never sends a path and the repo comes from `config.json` by id. The answer carries the text and a `rev` (a hash of the content, empty when there is no file yet); a save sends the `rev` it last saw as `base`, and if the file changed outside since (Notepad, another tool) nothing is written and the answer is `{ conflict: true, text, rev }` with what is on disk. Before the first write, when Git does not ignore the file, the panel adds `.panel/` to that repo's `.git/info/exclude` (never twice, and put back exactly as it was if that does not hide the file), so the notes never show in `git status`; a notes file that Git already TRACKS is never written (409). The write is whole or nothing (a temp file, then a rename), saves of one repo run one at a time, the text is stored exactly as sent (at most 256 KB, counted in bytes), and `.panel` or the file being a link or not a regular file is refused (400), so nothing is read from or written outside the repo.
- **Merge in the composer and Status tab of the right column (RP129, RP175).** The **Merge** button sits in the composer next to the commands of the flow (it left the footer of the column, which is gone: the branch and the commits ahead are on the card, the CI is in the Status tab). It is drawn only when the repo has an open pull request of the current branch, and it does not depend on the state of the session. When it is off, the button keeps its reason in its title and nothing is written next to it; if the pull request itself is the reason (not ready, checks), the message box shows it muted as its placeholder (RP191), and it goes when you type. A hold (the session or a command is busy) is shown nowhere: the state on the left says it. The pull request is the open one whose head is the current branch and never another one: on the base branch, on a detached HEAD, while pull requests load or fail to load, or in a repo with no GitHub remote there is none, and no button is drawn. The button is the same Merge action of the cards (`data-act="merge"`, `POST /api/merge` with the method chosen in Settings, Delivery) and it follows the same rule, kept in ONE place (`mergeButton` in `public/view.js`, which the card of the board asks too): it is enabled only for a ready PR with no merge in flight or just done and no command running in the session. The server is still the real guard: it reads the PR again and refuses one that is not open or not ready. The Status tab shows that pull request (number as a link, state, title, branches and size), a summary of its checks, one row per check with its state (the state word goes away in a column narrower than 300 px) and, when some run failed, the same **Re-run failed** button of the cards; a yellow badge on the tab counts the pending checks. It reads what the board already has (`GET /api/prs`), adds no route and writes nothing.
- **Files in the right column, one viewer in the centre (RP130).** The explorer of the repo (and the list of changed files) is ALWAYS in the right column and never in the centre: its **Files** tab sits next to Changes and shows the tree of the repo (folders folded except the ones that hold a changed file, changed files marked, the open one highlighted). The centre is the place of action (the chat, Notes and ONE viewer tab): touching a file of Changes or of Files opens it in that tab, next to the chat, with its name and its own close button; a changed file picked in Changes shows its diff and a file picked in Files shows its content, and opening one replaces the other. Notes stay in the centre as a tab, as before. With the column in, the chat has no Files (or Tasks, or Changes) tab; under 1100 px there is no column, so the chat keeps its Files tab as before. It reads what already exists (`GET /api/files`, `GET /api/file`) and writes nothing. The column scrolls as a whole (RP132): the tree of Files takes its natural height with no scrollbar of its own, and the tab bar on top and the footer at the bottom stay in place with any long list (a window under about 570 px of height still scrolls the whole page).
- **Notes tab (RP93b).** The chat has a Notes tab (with or without the right column): a free-text notepad stored in the repo's `.panel/notas.md`, out of Git (RP93). It saves by itself about 800 ms after you stop typing and at once when you leave the tab, close the chat, open another repo or hide the page, one write at a time, and shows `Saving…`, `Saved` or `Not saved` (with a Retry button). If the file changed outside the panel nothing is written: you choose `Load the version on disk` or `Keep mine`. Unsaved text is never replaced by a read.
- **Choosing the pi (RPC1a).** The panel detects two installs of pi, Gentle Shell (launcher plus its `current` file, nothing is run) and the original `pi` on the PATH (its `--version` is read), and uses Gentle Shell first (`auto`) or the only one it finds. `GET /api/pi-runtime` lists them (`?check=1` also starts the active one in RPC mode once and ends it); `POST /api/pi-runtime` takes ONLY `{ runtime }`, `auto` or the id of a detected runtime, never a path. A custom `command` or `agentDir` can only be written by hand in the `pi` key of `config.json` and is validated (an absolute path or a bare name, no shell characters). The child gets a clean environment (no `PI_*`, `GENTLE_*` or `ENGRAM_*` from the panel); the first of the two runtimes above (never the original pi) then gets ONE fixed variable, `GENTLE_SHELL_INTERACTIVE_HOST=1` (RP237), so its question tools ask with a dialog the chat answers with buttons instead of writing the options as text (the value is always `1`, never copied from the panel's environment; the original pi does not get it). The same variable also turns on its `/gentle:desktop`, `/gentle:mode` and `/gentle:yolo`, which can change its permission mode (even to super-yolo, saved for new sessions) and its configuration, and the panel would not show it: the panel refuses a text that starts with one of them (409 `Permission and configuration commands (/gentle:desktop, /gentle:mode, /gentle:yolo) are not available from the panel: use the terminal`, on `/api/rpc/prompt` and `/api/rpc/steer`; the page keeps it in the box with that reason). They are used from the terminal, and the sessions folder follows the active runtime unless `REPO_PANEL_SESSIONS_DIR` is set. Conformity shows the pi in use and a selector.
- **Sessions over RPC (RPC1b).** The panel starts ONE `pi --mode rpc` per repo (the runtime chosen by RPC1a, in the repo folder from `config.json`, with the adopted `--session-id` or `panel-<folder>-<repo id>`: the first 8 letters and digits of the repo id are part of it (RP97), so two repos whose last folder has the same name never share one), at most 6 at once. Routes (token required): `POST /api/rpc/start`, `/api/rpc/prompt`, `/api/rpc/steer`, `/api/rpc/abort`, `/api/rpc/dialog` (answers only a dialog that is pending) `GET /api/rpc/status?id=` and `GET /api/rpc/states` (RPC2b-1: `{ states: { <repoId>: closed | starting | idle | busy | asking } }` for EVERY configured repo, `closed` by default, read from the host's memory: nothing is started; the page reads it on startup and on every reconnect of the stream); the page can send only a repo id and text, never a program, folder or argument. Events reach the page on the SSE stream as `event: rpc`; the stream carries nothing else (heartbeat comments aside). The sessions live inside the panel process: a restart ends them and they come back with the same `--session-id`. On Ctrl+C or a stop signal the panel closes every session the orderly way (RP238: all in parallel, each with its 20 s grace) and exits once they are all gone, instead of after a fixed 300 ms; `server.close` calls back only then. **Restart panel** in the tray ends the panel process at once (`Stop-Process -Force`), so it skips this wait: its pi processes are not killed (their stdin ends with the panel, so they exit by themselves) and the new panel does not know about them, so a session started again right away may overlap one that is still saving. **The queue survives a restart (F3).** Every time pi reports the queue of a session (`queue_update`) the panel writes it at once to `queues.json`, next to `config.json` like `push.json` (texts only, at most 20 per list and 4000 characters each, with the time each message entered; a `.tmp` file renamed, mode 0600). A queue that pi had when the panel died shows in `GET /api/attention` as `queue-lost`; the panel never starts a session to deliver it: when someone starts the session, the saved messages go first, in order (the first as a prompt, the rest as follow-ups) and a new message goes behind them. A queue with a message older than 12 hours, or one that starts with `/` or `!`, waits for `POST /api/rpc/queue-confirm { id }`, which delivers it at once to a live, free session or when the session is started; every saved text goes through the same checks as a new message, and what they would refuse (for example `/gentle:mode`, a `!` shell command, or a `/` command that would go as a follow-up) is dropped and listed in the answer as `refused` (`{ confirmed, count, refused }`). In `queue-lost` such a line carries `command: true`. `POST /api/rpc/clear-queue { id }` also empties the saved queue, and with the session closed it only empties that copy and answers what it removed (409 as before when there is none); closing the session or starting a new conversation empties it too. A broken `queues.json` reads as empty, and a write that fails is tried again on the next change. A start can take up to five minutes (4 s to over 60 s measured, with no pattern; 24 to 29 s when pi has to look for the session id among a repo's sessions; RP101 raised the cap from two minutes after a New session ran past it twice); one that runs out of time answers 504, so commands wait in a queue until the agent answers.
- **Why a session did not start (RP238b).** The error output of pi was dropped; now the server always reads it (so a pi that writes a lot never blocks on a full pipe), keeps only its last 16 KB in memory, never logs or sends it, and reduces it to one category of a closed list, read from the messages pi writes right before it exits (only its last 8 lines with text count and the one closest to the end wins, so an older tool line is not taken for the cause; colour codes are ignored): `no-model` (`No models available`, `No API key found`), `extension` (`Failed to load extension`), `session` (a rejected `--session-id`, `Session already exists`, `No session found matching`) and `folder` (`current working directory no longer exists`). A start that fails then answers 502 `The session could not be started: <fixed text>` (for example `No model or login is set up: run pi in a terminal to sign in`), and anything else keeps `The session could not be started`. A session that was up and dies by itself publishes `exit` at once and then an `rpc` event `{ kind: 'ended', cause }`, which the chat shows as a note (`The session ended: <fixed text>`); a session the panel closes says no cause. The cause waits at most 1 s for pi's error output to end, because Node may report the exit before that output is read.

Click the progress bar of a card (it is a button; Enter works too) to open that repo (on its Tasks tab, in the column or in the chat). The summary row, which stays under the tabs when the list scrolls, says when the list was read («Read 2 min ago», yellow from 15 minutes) and has a button that runs `git fetch` on that repo and reads the list again. - A **/flow-ship** button on cards with changes sends that command to the session of the repo over RPC (RPC2-2): the server calls `prompt` on the session the panel keeps for that repo. The session must be started and idle; otherwise it refuses with a fixed message (409 `The session is not started`, `The session is busy` or `The session is waiting for an answer`). The page starts a closed session first (it can take up to five minutes) and then sends, so a closed session never disables the button. `/flow-ship` commits the changes, checks Git and publishes the pull request in one run (it never merges); it needs the flow-skills package loaded in Pi, so reload Pi after updating it. **Checked commands (RP233).** When the panel starts a session it asks pi once for its commands (`get_commands`) and keeps the names in memory; the status of the session (`/api/rpc/start`, `/api/rpc/status`) then carries `missing`, the command keys whose command is not loaded, and their button is off with the reason «/flow-ship is not loaded in this session». `POST /api/pi` refuses such a key with 409 `/flow-ship is not loaded in this session: is flow-skills installed for pi?` and sends nothing, instead of letting the model read `/flow-ship` as plain chat. The server still accepts the keys `flow-commit` and `flow-commit-unstage` (an old page may send them), but the panel no longer offers `/flow-commit`. The browser sends a command key, never text, and only `/flow-ship`, `/flow-ship --unstage` (key `flow-ship-unstage`), the old `/flow-commit` and `/flow-commit --unstage`, `/flow-pr`, `/flow-base`, `/flow-base --stash` (key `flow-base-stash`), `/flow-next` (key `flow-next`), `put-in-conditions` and `fix-pr` exist on the server. The panel never adds `--unstage` on its own: only the button sends it. **One order at a time, and none while background jobs run (RP234).** There is no time window any more (the 45 s guard of the screen-reading days is gone): a repo takes one order while it is on its way to pi, so a second click before pi answered is 409 `Another order is on its way to this session: wait for its answer` (in memory, per repo, any key); the lock is freed as soon as pi answers or fails, and from then on the state of the session says busy, so a Retry of an order that failed goes at once. A delivery order (`/flow-ship`, `/flow-pr`, `/flow-base`, `/flow-next` and their variants) is refused while the session still has background jobs, counted with the same number the page shows (RP161): 409 `The session still has N background jobs running: wait for them to finish` (a background subagent leaves the session free while it works). A count that cannot be read is none and blocks nothing; `put-in-conditions` and `fix-pr` take only the lock. The order of the refusals is: unknown command (400), command not loaded (409), session not free (409), background jobs (409), an order on its way (409). `fix-pr` also takes `pr`, the integer number of an open pull request of that repo (`POST /api/pi` `{ id, command: "fix-pr", pr }`; `API_VERSION` 12): the server looks the PR up itself, refuses with 400 when `pr` is missing or not a positive integer and with 409 when the PR does not exist, is not open or has no failing checks, then builds ONE line from the PR number, title, head branch and up to 5 failing check names (control characters replaced by a space, double quotes dropped, title capped at 120 and each name at 60 characters). The order tells the agent to find out why with `gh`, switch to the PR branch only if the tree is clean (otherwise stop and ask), fix whatever is needed (production code, test code or configuration) as long as it serves the original objective of that PR (its title, description and commits), run the tests, and not commit, push or open pull requests. It is also told not to use `git mv` or `git add` and to leave the git index empty (`put-in-conditions` carries the same sentence, and so does `requirements/INSTALL.md`), because `/flow-ship` refuses to start when files are staged. When the failure is unrelated to that objective or looks transient (infrastructure, a flaky run, a runner problem) it must not edit code: it says so and recommends **Re-run failed**; when the right fix would change the PR's scope or needs a product decision it stops and asks. It goes through the same safeguards as the other buttons (a started, idle session and the send lock).
- Quick actions: open on GitHub, `git fetch --prune`, re-run failed checks, refresh.
- **Automatic fetch (RP150).** While a page is open the server runs `git fetch --quiet --no-prune` on each repo in the background (every 1 minute for a repo whose branch has an open pull request, every 5 minutes for the others; the interval doubles after a failure, up to 15 minutes), so the roadmap read from `origin/<base>` stays current. One fetch process per repo at a time (a repo and its linked worktrees count as one), at most 2 automatic fetches in flight, a 30 s limit, no credential prompts, no git maintenance; a repo with no remote or with a git lock taken is skipped. It never prunes, even with `fetch.prune` set, and never touches your branch, index or working tree. A forced refresh does not start one, and `POST /api/fetch` still runs `git fetch --prune --quiet`. Restart the server to pick it up.

## Requirements

The panel shells out to `git` and the GitHub CLI, so both must be installed and working before you start. There are no npm dependencies and nothing else to install.

1. **Node.js 20+** (`node --version`).
2. **Git** on your `PATH`, with access to your repos' remotes (`git fetch` must work from the terminal).
3. **GitHub CLI** ([install](https://cli.github.com)) logged in to the account that can see your repos:
   ```bash
   gh auth login
   gh auth status     # must show "Logged in"
   ```
   The token needs the `repo` scope (PRs, CI status, merging) and `workflow` to re-run failed checks. `gh auth login` grants `repo` by default; add `workflow` with `gh auth refresh -s workflow`.


Quick check that everything is ready: `node --version && git --version && gh auth status`. PRs, CI status and Merge depend on `gh`; the local git view only needs `git`.

## Start automatically at logon (Windows)

```powershell
powershell -ExecutionPolicy Bypass -File scripts/install-autostart.ps1    # install
powershell -ExecutionPolicy Bypass -File scripts/uninstall-autostart.ps1  # remove
```

This registers a per-user scheduled task (no admin needed) that runs the panel hidden at every logon and retries every minute if it fails. The port never changes, so the URL stays stable and you can pin it as a browser app. Launching the panel while it is already running just exits quietly. If another program owns the port, the launch fails with a clear message instead of picking a different port.

`install-autostart.ps1 -DryRun` shows what it would register without registering it, and `uninstall-autostart.ps1 -DryRun` says what it would remove without removing it. The installer needs a real `node.exe` on PATH (not an npm, volta or fnm `.cmd`/`.ps1` shim).

All four scripts that register or remove a task (`install-autostart`, `uninstall-autostart`, `install-tray`, `uninstall-tray`) refuse to run, even with `-DryRun`, from a copy that lives inside the OS temp folder: they print `... refused: this copy lives inside the OS temp folder (<folder>); install from the real repository folder.` to stderr and exit with code 2. The tasks are per-user and global to the machine, so a throwaway copy (a test, a worker) that registered one would silently overwrite the real task with paths into a folder that is about to disappear.

### Restart after an update

The page files are read from disk on every request, but the server code is loaded only when the process starts. After `git pull` (or any update of the panel) the server must be restarted, or the page will talk to old code and show the red out-of-date banner.

The autostart task is called `repo-panel` (it runs `conhost.exe --headless node server.js`). `Stop-ScheduledTask` alone does **not** stop the Node process: it stays alive holding the port, and a new start exits silently with "repo-panel is already running". Restart by ending the process that listens on the port and then starting the task:

```powershell
Get-NetTCPConnection -LocalPort 4310 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }; Start-ScheduledTask -TaskName repo-panel
```

Use the `port` from `config.json` if you changed it. To check: open `/health`, it must show the current `api`, and the red banner must disappear after reloading the page.

## Configuration

On first run there is nothing to configure: click **+ Repo** to add a single folder, or to scan a parent folder for every repo inside it. The panel saves your choices to `config.json`, which is git-ignored so your local paths are never committed.

You can also create `config.json` by hand; copy `config.example.json` as a starting point:

| Key | Meaning | Default |
| --- | --- | --- |
| `port` | Port to listen on | `4310` |
| `priority` | Optional list of repo names (e.g. `["repo-panel", "api"]`) that go first in the "Go work on" strip, in that order; case-insensitive, unknown names ignored | none |
| `chat.showResults` | `true` lets the chat ask, with a click on a tool chip, for the START of the text of that tool's result (`GET /api/chat/result`). Off by default, and anything other than the value `true` is off. It is a switch of privacy: a result is free text and can hold secrets (the output of `cat .env` or `env`), and no list of patterns catches every form of one. Never shown: the result of `read`. Change it in the Settings tab, or by hand in this file | `false` |
| `dismissed` | Optional list of repo ids whose "requirements missing" warning is hidden; written by the panel (`POST /api/dismiss` `{ id, on }`), invalid entries and duplicates ignored | none |
| `sessions` | Optional map of the session the panel adopted, `{ "<repoId>" or "room:<name>": { "id", "name", "adoptedAt" } }`; written by `POST /api/sessions/adopt` and `/start`, cleared by `/release`; entries with an invalid id (only `A-Za-z0-9._-`, 1 to 80 characters) are ignored | none |
| `rooms` | Optional list of rooms, `[{ "name", "path", "repos": [repoId] }]`; written by the panel's **+ Room** screen and the card menu, or by hand (see Rooms) | none |
| `groups` | Named groups of repos (`{ "name", "repos": [{ "path", "base", "roadmap" }] }`); `base` and `roadmap` are optional | `[]` |

`POST /api/queue` takes the per-repo facts from the browser (it does not rerun any git or gh command) and orders them: repos in `priority` first, then merge, branch, deliver and start, keeping board order within each kind. `POST /api/conformity` takes each repo's roadmap availability and problems and returns the repos that do not conform.

### Requirements

`requirements.json` is `{ "version", "blocks", "requirements": [{ "id", "title", "category", "level", "check", "remedy" }] }`. `blocks` holds the version each Orquestación block must have (`<!-- orquestacion:NAME vX.Y -->` ... `<!-- /orquestacion:NAME -->`). The checks are pure functions in `checks.js`; the server reads the files from `origin/<base>` (`AGENTS.md`, the roadmap, `docs/ORQUESTACION.md`) and `checks.js` decides.

**Changing the text of a block means bumping its version.** The panel marks a repo `outdated` only when the version in its `AGENTS.md` differs from the one in `blocks`, so an edit to `requirements/blocks/*.md` without a bump leaves every repo on the old rule with no warning. To change a block: edit its text, raise the version in its opening marker and in `blocks` of `requirements.json`, then refresh `requirements/blocks.lock.json` with `UPDATE_BLOCK_LOCK=1 node --test test/rp36-block-versions.test.js`. That file records the version and a hash of each block's text; `test/rp36-block-versions.test.js` fails when the text changed and the version did not, and when the lock is stale. The refresh itself REFUSES a text change under the same version (otherwise refreshing would defeat the guard); `UPDATE_BLOCK_LOCK=force` accepts it and is only for a block nobody has installed yet. Repos with the old version then show the requirement as `outdated` and "Put in conditions" reapplies only that block.

**The padrón is the version of the whole set of rules.** `padron` in `requirements.json` (and in the title of `requirements/INSTALL.md`, which the test keeps equal) covers the procedure the agent follows, not only the blocks. The order sent to the agent cites it (`for repo-panel (padrón X.Y)`), each repo records it in `docs/ORQUESTACION.md` with the line `- **Padrón del panel:** X.Y`, and the required requirement `padron-record` compares the two. So when the procedure changes without any block changing, raise `padron` (the same lock hashes `INSTALL.md` and `requirements/EXAMPLES.md`) and every repo shows `padron-record` as `outdated`. The worked examples in `requirements/EXAMPLES.md` are run by `test/rp41-standard.test.js` against the panel's own validator, so they cannot drift from what it accepts.

- Categories: `verificable` (the panel decides and can show it as passing), `parcial` (shows evidence, a person confirms) and `criterio` (never passing, only a reminder). Only `verificable` requirements can pass; a repo is `ready` only when every `required` one passes. `recommended` ones never affect `ready`.
- Result status: `pass`, `fail`, `outdated` (the block has another version, or is the old unversioned section), `unavailable` (could not be read: no repo, no base branch, missing file, or an unknown check type). Unavailable is never shown as passing or as failing.
- The old unversioned `## Orquestación` section (or the `orquestacion:bloque` marker) counts as an outdated `registro` block that asks to be updated, not as a missing one.
- The agent's instructions live in the panel folder, not in another project: `requirements/INSTALL.md` (the procedure: apply only the ids named in the order, never delete rules, stop and ask the user on a conflict with the repo's `AGENTS.md`, work on a task branch, never commit, push or open PRs) and `requirements/blocks/registro.md`, `requirements/blocks/ciclo.md` and `requirements/blocks/estado.md` (the exact text of the versioned blocks). Each `remedy` points at them. The roadmap table is the exception: the block does not define it, so `INSTALL.md` step 7 and the `roadmap-file` and `roadmap-table` remedies spell out its exact column names (`ID`, `Entrega`, `Depende de`, `Estado`; optional `Resultado visible`, `Notas`, `Ficha`), the same list the validator requires (`lib.RM_REQUIRED`). **One mechanism to create and manage tasks.** The `tareas` block (`requirements/blocks/tareas.md`, in Spanish, a required requirement installed into each repo's `AGENTS.md`) states it: every task is a row of `docs/ROADMAP.md`, created `Pendiente`, taken with `siguiente`, closed in the same diff, and nothing parallel is allowed. Step 7 of `INSTALL.md` tells the agent to migrate whatever other task system a repo has (`planning/`, a roadmap elsewhere, task lists kept in files) into that table, keeping the old files as fichas; to remove from `AGENTS.md` the instructions about how to create or manage tasks and the repo's own rules about branches, commits and pull requests (the panel's `/flow-base`, `/flow-ship` and `/flow-pr` decide those; the lines saying what a production, release or hotfix branch is for stay) and to list what it removed; never to invent dependencies (a task without one gets `—`); and to stop and ask only when a task's ID or state cannot be derived. With no tasks it writes only the row `U0`. A checklist kept inside each change (OpenSpec `tasks.md`, fichas) is not a task list: it stays where it is as history, and only what is still pending is imported, as ONE row per change that says `sin verificar` (the agent cannot tell from the code whether pending work is done: an audit can reopen a step on purpose and a gate is a decision). When a row marked `sin verificar` is taken, the `tareas` block tells the agent to verify it first, with evidence (merged PRs, commits, passing tests, receipts) and the person's OK; it never marks `Completada` by itself, because a wrong `Completada` hides work and unblocks other rows by mistake. The panel never edits another repo: the agent does, and the user delivers it with `/flow-ship` and `/flow-pr`.
- Two more requirements belong to the agent state (see Agent state); `estado-block` is `recommended` (it never changes `ready`) and `panel-ignored` is `required` since padrón 1.3, because every repo ignores `.panel/`: `estado-block` (AGENTS.md on the base branch has a closed `<!-- panel:estado v1.0 -->` ... `<!-- /panel:estado -->` block; the check declares its marker namespace, `"namespace": "panel"`, and the Orquestación blocks keep the default) and `panel-ignored` (Git ignores `.panel/state.json` in the repo's **working tree**: it runs `git check-ignore -q .panel/state.json` there, so it is a local fact, not read from the base branch; exit 0 is `pass`, 1 is `fail`, anything else, such as a missing folder, is `unavailable`). `panel-ignored` does not apply to rooms. Its remedy appends `.panel/` to `.git/info/exclude` (never `.gitignore`, never committed), so there is nothing to deliver with `/flow-ship`.
- A file that cannot be read from the base branch for any reason other than "not on that ref" is reported as `unavailable` (reason `error`), is not cached, and is never counted as failing or passing.
- `GET /api/requirements?id=<repoId>` returns `{ available, base, results, summary }`; `GET /api/prerequisites` returns `{ items: [{ id, ok, detail }] }` for `git`, `gh` and `pi` (a missing tool is `ok: false`, not an error).
- The Conformity tab says "All repositories conform." only when the roadmap report is empty **and** the requirements of every repo and the prerequisites were loaded and every repo is `ready`. While they load it says it is computing; if they fail to load it says so.

### Agent state

Work is often unfinished while the repo already shows changes (the agent is waiting for a decision), and after switching sessions it is easy to forget what to do next. So each agent session declares its state in a small file that the panel reads, and ends its replies with one clear line.

- **File**: `.panel/state.json` in the repo's working tree, ignored with `.git/info/exclude` (see `panel-ignored`), never committed. `{ "state", "next", "detail", "at" }`: `state` is `working` (still in progress), `needs-input` (waits for a decision of yours), `ready-to-commit` (done and verified), `ready-to-pr` (committed, ready for a pull request) or `blocked` (cannot continue; `detail` says why); `next` is one line saying what you should do now; `detail` is optional longer text; `at` is an ISO 8601 date-time.
- **The `estado` block** (`requirements/blocks/estado.md`, in Spanish like the other blocks, installed into the repo's `AGENTS.md` by "Put in conditions") tells the agent to rewrite the file after every action that writes files or needs a decision, and to end its reply with one line `Siguiente: <next>`.
- **Reader**: `GET /api/state?id=<repoId>` (token required, 404 for an unknown id) returns `{ available, state, next, detail, at, stale, reason }`. `available: false` has a `reason`: `missing` (no file), `invalid` (unparsable JSON, not an object, unknown `state`, `next` not a string or over 300 characters, `detail` over 4000, `at` not an ISO date-time or more than 5 minutes in the future), `unsafe` (`.panel` or the file is a symlink or link, not a regular file, or over 64 KB; checked with `lstat` before reading and never followed) or `error` (any other read failure). It never throws. An empty or whitespace-only `next` is `invalid`, and `next` is trimmed. `GET /api/local` only gains the additive fields listed under Delivering.
- **Stale**: `stale` is true when `at` is older (whole seconds) than the repo's last activity: the newest of the local `HEAD` commit date and the modification time of each changed or untracked file (the state file itself excluded, at most 200 files). A stale state is returned but flagged. If Git cannot say, it is not flagged.
- **Card**: with a valid, fresh state the card shows its `next` line (one line, full text, `detail` and `at` in the tooltip) with a dot: working yellow, needs-input blue, ready-to-commit and ready-to-pr green, blocked red. A stale state shows only a small gray "outdated" marker, never the old text. The `/flow-ship` button of a card with changes is hidden unless there is no usable state or the usable state is `ready-to-commit`, or you chose **Show /flow-ship anyway** (below); the server-side checks of the button (one idle session, lock) are unchanged. The line is only shown on cards with changes or unpushed commits.
- **Expiry of `working`**: a declared `working` older than 30 minutes (by its own `at`) counts as expired: the card shows only the gray "outdated" marker and the commit button is usable again, because an agent that crashed would otherwise hide it forever. `needs-input`, `blocked` and `ready-to-pr` never expire by time.
- **Show /flow-ship anyway**: when a declared state hides the commit button, the card's **⋯** menu offers this item. It brings the button back for that repo until the page is reloaded (kept in the page, never persisted). A merged branch with changes never shows it: that card offers `/flow-base --stash` instead of `/flow-ship`. The red stale mark names the real button in its tooltip (`/flow-base`, or `/flow-base --stash` with the uncommitted changes it carries).
- **A missing, invalid, unsafe, failed or stale state never blocks anything**: the panel behaves as before. The state can only hide the commit button.
- **Not verified**: the panel cannot tell whether an agent follows the block and writes the file (a model may skip it or write a wrong time, which makes its state look stale); and the line and dots were only checked with unit tests of the helpers, not in a browser.

### Delivering: /flow-pr, manual action and the verdict

The Committed column means "clean tree with commits not delivered yet". That alone is not enough to hand the branch to `/flow-pr`, so the card checks more and says when a person has to step in.

- **`GET /api/local`** gains three additive fields and changes nothing else: `head` (full SHA of `HEAD`, `null` for an unborn branch or on any Git error), `inProgress` (`null`, or `merge`, `rebase`, `cherry-pick` or `revert`, detected from the git dir with `git rev-parse --git-path`, so worktrees and submodules work; it never throws) and `base` (the base branch: the configured one, else `origin/HEAD`, else `main`). `API_VERSION` is now 8.
- **/flow-pr button.** A Committed card shows `/flow-pr` only when ALL hold: no changed or untracked file, commits ahead (also on a branch with no upstream), the branch is not the base and not detached, nothing needs manual action, the repo is not flagged stale (`Merged: run /flow-base`) and no `/flow-ship` verdict is running or needs attention. When an open PR from the current branch already exists, the label is **`/flow-pr (update PR)`**, because `/flow-pr` creates the PR or updates the open one. Otherwise there is no button. Committed cards no longer carry `/flow-ship`: with a clean tree there is nothing to commit; the button stays on Changes cards.
- **Needs manual action.** Commits are made only through `/flow-ship`, and PRs through `/flow-pr`. A card shows a red bar "Needs manual action: …", hides both buttons, goes to the top of its column and counts in the ⚠ problems filter (like a stale card) when: there are commits ahead while the current branch IS the base ("Commits on main: move them to a task branch"); HEAD is detached; a merge, rebase, cherry-pick or revert is in progress; or the branch diverged from its upstream (commits both ahead and behind). It does not fire for a clean branch that is only behind, a base branch with nothing ahead, or a task branch with commits ahead. A repo whose local state cannot be read keeps its existing error card.
- **Verdict after /flow-ship.** When a `/flow-ship` is sent from the page, the page remembers `{ at, head, files }` for that repo (in the page only: no history, nothing persisted, lost on reload) and follows the session state: the `rpc` state events of the stream feed the verdict at once (busy is running, idle after busy is judged) and the read-only `GET /api/pi-status?id=<repoId>` on the normal refresh cycle stays as the fallback. It answers `{ state }`: `closed`, `starting` as `busy`, `idle`, `busy` or `asking`, from the session host (token required; 404 for an unknown repo).
  - **running** ("shipping…"): the session is busy; or the session state is unknown or ambiguous and less than 30 minutes passed (15 for the old `/flow-commit`: a commit plus a pull request takes longer than a commit); or less than 30 seconds passed since sending (an idle prompt right after sending may not have started yet).
  - **ok**: the tree is clean (untracked files included), `HEAD` differs from the one recorded and nothing is left to deliver (no commit ahead of the upstream: the pull request is published); the old `/flow-commit` is ok with commits ahead instead. The record is cleared and the card shows the open PR. The session being busy still wins, so the verdict waits for it.
  - **attention** (red bar with the reason and a ✕ to dismiss; after `/flow-commit` `/flow-pr` is NOT offered while it shows, after `/flow-ship` it is, so a failed PR stage can be redone): the session is idle or closed but N files are still uncommitted, or `HEAD` did not change, or the session closed before a commit, or `HEAD` changed but commits are still ahead (the PR was not published; for `/flow-commit`: nothing left to deliver); or 30 minutes (15 for `/flow-commit`) passed with an unknown session and nothing changed.
  - It is judged from Git and the session state, never from terminal text, and the panel does not judge the quality of the commits.
- **In progress for every command (`API_VERSION` 13).** The same record, `{ cmd, at, head, branch, files, ahead }` (a fresh `GET /api/local` is read right before sending), is kept for `/flow-ship`, `/flow-ship --unstage`, `/flow-pr`, `/flow-base` and `/flow-base --stash`; `fix-pr`, `put-in-conditions` and `flow-next` keep only `{ cmd, at }`. The result of every command is judged from Git and the session state, never from terminal text (`flowVerdict` in `public/view.js`; `/flow-ship` keeps its `commitVerdict` above, and `--unstage` also needs an empty index):
  - **`/flow-pr`**: ok when the tree is clean, the branch has an upstream with nothing ahead and an open PR whose head is the current branch exists; attention "No open pull request for <branch> after /flow-pr" when the session is idle or closed after 30 seconds and that is not true.
  - **`/flow-base` and `/flow-base --stash`**: ok when the repo is on the base branch with nothing ahead or behind (the plain variant also clean); attention "Still on <branch> after /flow-base" when the session is idle after 30 seconds and the branch did not change.
  - **`fix-pr` and `put-in-conditions`**: only running while the session is busy; once it is idle the record is dropped with no verdict (a failure answer from the session is a legitimate outcome) and the card refreshes.
  - A closed session while running is attention ("The session closed while the command was running"); an unknown session for more than 15 minutes with nothing changed is attention.
  - While a verdict is **running** the status line says "committing…", "creating pull request…", "updating base branch…", "fixing pull request…" or "putting repo in conditions…" and EVERY flow button of that repo's cards, plus `Merge`, `Re-run failed` and `Fix CI`, is disabled with a tooltip naming the running command. When the session goes from busy to not busy the page refreshes that repo at once (the same refresh as the timer, so the card changes column without waiting) before it judges the result, and an ok record is cleared. An attention bar stays until dismissed (✕).
- **Staged files.** `GET /api/local` gains two additive fields, `stagedCount` (paths with a change in the index, renames included, untracked files never) and `stagedPaths` (those paths, sorted, at most 20), from the same `git status --porcelain=v2` read. `/flow-ship` refuses to start when the index is not empty, so a dirty card with staged files shows a bar ("N files are staged: /flow-ship needs an empty index. The button clears the index (git reset, your changes stay in the working tree) and then continues with the normal commit in the same run.") and offers `/flow-ship --unstage` instead of `/flow-ship`. That option is the flow-skills runtime's explicit one: a mixed reset, only when you press the button.
- **Why it failed.** The red bar of a failed command shows only its reason. A failed `/flow-ship` or `/flow-ship --unstage` labels its button `Retry /flow-ship` (or `Retry /flow-ship --unstage` while files are staged).
- **Animated progress (`API_VERSION` 14).** The in-progress line of a card ("committing…", "creating pull request…", "updating base branch…", "fixing pull request…", "putting repo in conditions…") has a pulsing dot and an animated ellipsis, and the line is a polite live region (`role="status"`, `aria-live="polite"`). A pull request whose checks are still running shows the chip `verifying checks · 2 running · 2/4` with the same pulsing dot (the tooltip still lists every check); the chips for passed, failed and no checks are unchanged. It is CSS only, with no timers. Because the page re-renders the board on every draw, each animated element gets an inline negative `animation-delay` from the clock (`animDelay` in `public/view.js`) so the animation does not jump. With `prefers-reduced-motion: reduce` every animation is off and the text stays.
- **A session waiting for your answer (`asking`).** After a command a session can stop at a selection dialog (for example "Review consent"). The RPC host reports `asking` while a dialog of the agent is pending, and `GET /api/pi-status` then answers `{ state: "asking" }`. The card keeps the buttons disabled and shows a static highlighted line "waiting for your answer in the session"; it never turns into "Needs attention" because of time, and the repo appears in the "Go work on" strip as "Waiting for you: Answer the question in the session". The panel only shows this notice: it NEVER answers or presses a key in the dialog, and `POST /api/pi` refuses with 409 "The session is waiting for your answer to a question" and sends nothing.
- **Clicks are never lost.** The page writes a region (the board, the "Go work on" strip, the Conformity tab) only when its HTML changed, and a redraw waits for the release of a held mouse button (at most 1.5 s), so nothing under the pointer is replaced between the press and the release. Before, every read of every repo redrew the whole board about 150 times a minute at rest and a press that spanned a redraw never produced its `click`.
- **Subagent presence on the server** (RP164): for the session the panel started, the server reads the presence files Gentle Pi publishes (`<agent folder>/gentle-agents/presence/`, read only, never `discovery`) and `GET /api/summary` carries, inside `session`, `subagents: { signal, list }` with at most 5 live subagents (`name`, `state` working, slow after 2 minutes without activity or stuck after 5, and whole `minutes` and `idle` minutes); with a heartbeat older than 15 seconds it says `signal: false` and lists nobody. Only the validated agent name travels, never the label, ids, paths or what the agent did. Without presence the row is the one of always. It is only shown: it never holds or releases a delivery button. The page shows it in a later task.
- **The buttons follow the session.** A repo with uncommitted changes shows `/flow-ship` (and `--unstage`) disabled with «the session is still working» or «waiting for your answer in the session» while the RPC session of the repo is busy or asking; a closed or idle session holds nothing, and neither does a repo whose session state is not known yet. «Show /flow-ship anyway» lifts the hold. The other delivery buttons follow the session too (RP159): `/flow-pr`, `/flow-base`, `/flow-base --stash`, `/flow-next` and Fix CI are disabled with the same reasons while the session is busy or asking, from the LIVE state of the session, whether or not a command of the page is being judged (Merge is not held: it does not talk to the session). RP163: the same buttons are held while the session waits for BACKGROUND JOBS even when it is free (the number the server counts, `session.jobs` of its row, RP161), with the reason «N background jobs are running»; it is released by itself when the next row comes without the number (the page asks for the summary about every 20 s, so it can take that long), at once if the page knows the session closed, and «Show /flow-ship anyway» lifts it for /flow-ship only. On the cards of the Summary the buttons `/flow-base` and `/flow-next` used to be held only while the order was on its way and came back as soon as the answer arrived; they now stay held while the session works, with the reason as the tooltip. When you press any `/flow-*` button the repo behaves as if that command were already running (the button disabled, the progress line shown, with the reason «Sending the order to the session») from the click until the answer, however often the card is redrawn; a second click never sends a second order. Never checked against a real session showing a dialog.
- **Event stream.** `GET /api/events` is a long-lived Server-Sent Events stream of the `rpc` events of the sessions the panel keeps. It needs the token in the `x-token` header (never in the URL) and the panel's own host; at most 8 clients are served at once (the next one gets a 503). The server stores nothing for it: a new client gets only the stream preamble, then an `rpc` event whenever a session emits one, and a heartbeat comment every 15 s. **The panel's own vocabulary (RP235).** An `rpc` frame of kind `event` carries a `record` whose `type` is a panel name, never a name of pi: the server (`toPanel` in `server/rpchost.js`) is the only place that knows both. The names are `run_start`, `run_end`, `run_settled` (a run starts, ends, and pi will not continue by itself), `stream` (one step of the assistant's message: `index` is its block, `part` is `text`, `thinking`, `other` or `reset` for a new message, `phase` is `start`, `delta` or `end`; only a text block carries its `delta` or `content`), `tool_start` and `tool_end` (with the tool's `name`), `subagent_start` and `subagent_end`, `retry_start` (`attempt`, `max`, `delayMs`) and `retry_end` (`attempt`, `success`), `compact_start` and `compact_end` (`reason`: `manual`, `threshold` or `overflow`), and `other` for any event the page does not use (it carries nothing; the page still redraws on it). No argument, result, reasoning text or error text of pi leaves the server.
- **Message history (RP83).** In the message box of the chat, **↑** brings back the last message you sent to that session, another ↑ the one before, and so on; **↓** walks forward and, past the newest, gives back what you were typing. The arrows only act on the first line (↑) or the last line (↓) of the box, with no selection and no Shift, Ctrl, Alt or Meta, so editing a multi-line message works as always; typing in a recalled text, sending, or opening another repo ends the browsing. The history is the `user` messages of the chat plus the ones still pending, without empty entries or repeats in a row, one per repo, and it lives in the page only (nothing is stored or sent).
- **Chat over RPC (RPC2-1).** The composer talks to the live session of the repo through `/api/rpc/*`: **Send** starts the session first when it is not started (the label says *Starting…*, it can take up to a minute) and then posts `{ id, text }` to `/api/rpc/prompt`; the answer is shown while it is written (escaped, from the `rpc` events), **Stop** posts `/api/rpc/abort` (RP239: while pi waits to retry a failed request on its own, «Retrying · in 4s», the server first sends pi `abort_retry`, so the wait ends at once, and then the usual abort; a failed `abort_retry` never keeps Stop from stopping), and when the run settles the history is read once and replaces the streaming bubble. Enter sends, Shift+Enter adds a new line (the tooltip of the box says so; there is no hint line); where the pointer is a finger (a phone) Enter is a new line too and only Send or Ctrl/Cmd+Enter sends (RP207), and the box has no placeholder while it is blocked (the state line says why); an error puts your text back. The server refuses an empty text, one over 20000 characters or one that starts with `!`. When pi asks a question the composer is off and the card above answers it. **Shell commands (RP245b, parity with the terminal):** a message that starts with `!` runs its command in the folder of the session with pi's `bash` order and its output goes to the conversation; one that starts with `!!` runs it without sending the output to the model. It goes to `POST /api/rpc/bash { id, text }` (never as a prompt; `/api/rpc/prompt` still refuses a text that starts with `!`); the output streams live into the thread (`bash_execution_update` becomes the panel event `bash_output`), and a long finished output is folded to its last 20 lines with **Show all**. Like a command with `/`, it waits for a free session (409 `Shell commands wait until the session is free: send it when the run ends`, the text stays in the box), only one runs at a time per session (409 `A shell command is already running in this session`; the page keeps the second text in the box and leaves the running bubble alone), and a bare `!` says `Write a command after ! or !!`. While it runs its bubble has **Stop** (`POST /api/rpc/abort-bash { id }`, pi's `abort_bash`; the bubble then says Cancelled). The panel waits up to 30 minutes (the page waits one minute more than the server, so the server's answer arrives first); past that it also stops the command in pi (409 `The shell command ran longer than 30 minutes and was stopped`, the bubble keeps its output, closed as Cancelled), so a later command never runs alongside it. Finished runs stay in the thread (RP252): pi writes each one to the session file (`bashExecution`) and `GET /api/chat` returns it as an item `{ role: 'system', kind: 'shell', command, output, exitCode, cancelled, truncated, exclude }` (the last 20,000 characters of its output, with `cut` saying how many earlier ones were left out), drawn like the live bubble and folded the same way. A command that is still running is not in the file yet: `GET /api/rpc/status` reports it as `bash: { command, exclude, output, running: true, since }` (the last 200,000 characters of its output) and every tab hears `bash_start` and `bash_end`, so after a reload or in another tab it shows with its output and its **Stop**. A command the person types with `!` is their own command, as in the terminal: the guards of the session watch the agent's tool calls, not these. It is not interactive: a command that asks for input or stays open does not fit here. The output is shown live; the history of the chat does not show it after a reload yet. **Writing while the session works (RP236).** A busy session still takes a message: **Enter** (or the round **Correct** button, which takes the place of Stop while the box has text) steers the agent on the fly, and **Alt+Enter** (or **Queue**) leaves it for when the run ends; on a phone Enter stays a new line and the two buttons do it. Both go to `/api/rpc/prompt` with `behavior` `steer` or `followUp`. What waits is drawn above the box (pi tells the whole queue with `queue_update`, which reaches the page as `queue`: the two lists of texts, at most 20 each and 4000 characters each), and **Clear queue** (`POST /api/rpc/clear-queue { id }`, pi `clear_queue`) takes the messages back into the box, so nothing written is lost. A session that is starting, asking or compacting still refuses, and the text stays in the box. **RP236b.** While the session works, a text that starts with `/` is not sent as a correction or queued: pi would run an extension command at once, even during a run, so the page keeps it in the box and the server refuses it with 409 `Commands wait until the session is free: send it when the run ends` (sent with no behavior, when the session is free, it goes as before). Clear queue gives every text back whole (the 20-per-list and 4000-character caps are only for what is drawn). A free session empties the drawn queue. **Stop** takes the queue back first (`/api/rpc/clear-queue`, its texts return to the box) and then aborts, because pi goes on with the queued messages after an abort; a Clear queue that fails never keeps Stop from stopping. Below the box, as direct buttons, the flow command that can run now (`/flow-next`, `/flow-ship`, `/flow-pr` or `/flow-base`) still goes through `POST /api/pi`.
- **Permission mode of a session (RP245c).** Gentle Shell announces the permission mode with the notice `gentle:mode` (`Permissions: NORMAL`, `AUTO`, `YOLO` or `SUPER-YOLO`, at the start of the session and on every change). The RPC client keeps it like the memory one and the host reduces it to one category (`normal`, `auto`, `yolo`, `super-yolo`); its text never leaves the server. `GET /api/rpc/status` reports `mode` and every tab gets an `rpc` event `{ kind: 'mode', mode }`. The head of the chat shows a chip only in `auto`, `yolo` or `super-yolo`, and says nothing in the normal mode. The panel still never changes the mode: `/gentle:mode` and `/gentle:yolo` stay in the terminal.
- **Memory of a session (RP110b).** The plugin that gives a session its memory (Engram) tells its state with a notice of the key `engram`; the RPC client used to drop every notice and now keeps ONLY that one, cut to its last 200 characters (the plugin ends it with the part that says the state, so a long project name cannot push it out). The host reduces its text to ONE category of a closed list: `ready` (`… · ready`), `offline` (`… · offline`), `error` (`… · error` or `… · ambiguous project`) and `disabled` (`memory disabled`); a call that went well (`… · ✓ saved #12`, `✓ 3 results`, `✓ loaded`) is a recovery and says `ready` (RP123), a call that failed (`… · ✗ <text>`) says `error`; a step in progress (`… · saving…`) and any text it does not know say nothing lasting and change nothing. It remembers the last category of each session (the notice arrives when the session starts, and the page may connect later) and publishes only a CHANGE, as `{ kind: "memory", memory }` on the same `rpc` event; `GET /api/rpc/status` and the answer of `start` carry `memory` only once it is known. **The text of the notice never leaves the server** (it can hold the name of the project or an error message), and the other notices (`setWidget`, `notify`, any other key) are still dropped. The chat draws a chip next to the state of the session: `memory ready` (quiet), `memory disabled` (yellow), `memory offline` and `memory error` (red); nothing without a known category or when the session is closed. Known limits: it shows what the plugin says, not a test that it saves and recovers (that needs a real session and spends tokens); and the chip shows what the plugin said LAST: if the memory comes back but no call is made, it keeps the old category until the next call (a successful one makes it `ready`).

### When each flow button appears

One rule set (`flowButtons` in `public/view.js`) decides the buttons of a repo's local card; the page and the tests share it. The column comes from Git state alone.

| State of the repo | Column | Button |
| --- | --- | --- |
| Changed or untracked files | Changes | `/flow-ship` (hidden while a declared state says the work is not ready, see "Show /flow-ship anyway") |
| Changed files with a non-empty index (staged files) | Changes | `/flow-ship --unstage` instead of `/flow-ship`, with the staging bar |
| A `/flow-ship` or `/flow-ship --unstage` failed (attention) | Changes or Committed | `Retry /flow-ship` (or `Retry /flow-ship --unstage` while files are staged), with the reason and what the session said |
| Clean, commits ahead, no open PR for the branch | Committed | `/flow-pr` |
| Clean, commits ahead, an open PR from this branch | Committed | `/flow-pr (update PR)` |
| Branch already merged (or its remote branch deleted), clean tree | Merged (red mark) | `/flow-base`: starts from a fresh, updated base branch |
| Branch already merged, but files changed | Changes (red mark) | `/flow-base --stash` and no `/flow-ship`: the skill carries the uncommitted changes aside (stash, including untracked files), switches to the fresh base branch, updates it and restores them. It refuses and changes nothing when the work of the branch is not yet merged or its remote branch not yet deleted |
| Needs manual action (detached HEAD, commits on the base branch, merge or rebase in progress, diverged) | Wherever Git puts it | none |
| A `/flow-ship` is running | Changes or Committed | no `/flow-pr` and no `/flow-base` until it settles |
| Any command sent from the page is running (`/flow-ship`, `/flow-ship --unstage`, `/flow-pr`, `/flow-base`, `/flow-base --stash`, `fix-pr`, `put-in-conditions`) | Wherever Git puts it | the same buttons, disabled with a tooltip naming the running command, and `Merge`, `Re-run failed` and `Fix CI` of that repo disabled too; the status line says what is running |
| Open PR, checks failed | Pull requests (red) | `Fix CI` (any fix, in test or production code or configuration, as long as it serves the PR's own objective; for a transient failure it does not touch code and recommends `Re-run failed`; if the fix would change the PR's scope or needs a product decision it stops and asks), plus `Re-run failed` when a GitHub Actions run failed |
| Open PR, all checks passed and mergeable | Pull requests (first, green accent) | `Merge` |

**How a card returns after a fix.** `Fix CI` sends one order to the session (see below). The agent edits files and commits nothing, so the repo is dirty and its card moves to **Changes** with `/flow-ship`. `/flow-ship` commits and updates the PR in the same run, so the card goes straight to **Pull requests**; if its PR stage fails after the commit, the card stays in **Committed** with `/flow-pr (update PR)`. Nothing in the panel tracks this: each step is just the new Git state.

### Rooms

A room is a repo (a folder with its own `origin`) where you coordinate a group of repos (for example one room for your H2O projects and another for your tools). Repos do not declare which room they belong to, so the panel does, in `config.json`. You do not have to edit it: use the screen.

- **+ Room** (next to **+ Repo**) opens a dialog: a room name and its folder (the field suggests the folders of the repos already in the panel; a browser cannot open a native folder picker, so type or paste the path). Errors show inside the dialog.
- The card's **⋯** menu has an **Assign to room** group: one item per room (the current one is marked ✓) and **No room**. With no rooms it offers **Create a room…**.
- The Conformity tab's **Rooms** section has a **Remove room** button per room, with a confirmation.

By hand, the same data is (remember to escape backslashes in JSON, or use forward slashes):

```json
"rooms": [{ "name": "UPEN", "path": "C:\\Users\\you\\Developer\\upen\\upen-ceo", "repos": ["969522dd0c"] }]
```

`repos` holds repo ids (the `id` that `GET /api/config` shows for each repo). Rules: the name is trimmed, non-empty, at most 60 characters and unique (case-insensitive, the first wins); `path` must be absolute; `repos` keeps unique strings; a repo id belongs to at most one room (the first room wins). Reload the page after editing by hand.

- **Routes** (token required, like the rest): `POST /api/rooms/create` `{ name, path }`, `POST /api/rooms/remove` `{ name }` and `POST /api/rooms/assign` `{ id, room }` (`room` is a room name, or `null` to leave every room). They answer `{ rooms }`. `create` answers 400 with the reason when the name is empty, longer than 60 characters or already used, or when the path is not absolute, does not exist, is not a folder, has no `.git` or is not the folder of a repo of a group of the panel (RP218: a room is a repo of a group, so its folder has the chat and the git state of any repo; a slash or case difference in the path does not matter); `remove` and `assign` answer 404 for an unknown room or repo. `assign` takes the repo out of any other room first, and removing a repo from the panel also takes it out of its room.
- **Removing a room never touches files.** It deletes only the entry in `config.json` (its members become unassigned); the room folder and the repos are never created, edited or deleted by the panel.
- **Entries the panel does not understand are kept.** An entry under `rooms` that is not usable (not an object, a bad or duplicate name, a relative path) is ignored at runtime but written back to `config.json` exactly as it was on every save, in its place, so a typo cannot erase a room. `GET /api/config` lists them in `roomIssues` (short strings such as `rooms[2]: path must be absolute`; `[]` when all is fine) and the Conformity drawer shows "N entries in config.json under rooms are invalid and ignored" with the reasons. Fix the entry in the file by hand. A `rooms` value that is not a list is reported the same way, kept as is, and the panel refuses to create a room until you fix it.

- **Room requirements** (`roomRequirements` in `requirements.json`, evaluated against the room repo's remote base branch, all required): `room-base-branch`, `room-agents-file` (`AGENTS.md`), `room-enlaces-file` (the link map `ENLACES.md` at the root or under `estrategia/`, because the template does not fix the path) and `room-enlaces-sections` (a markdown heading for each of Proyectos, Contratos, Dependencias, Cola and barrido, matched case-insensitively inside the heading text; the detail lists which are missing). It only proves the headings exist, not that they are filled in. The repo that is the folder of a room is judged with these requirements in its card and in Conformity (matching the room path ignoring slashes and case), and it never receives the member order: its card menu does not offer "Put in conditions" and the server refuses it.
- **Member requirements** (a repo listed in a room; in `requirements.json` a requirement can have `"onlyInRoom": true`, omitted for repos outside every room, and `"levelInRoom"`, which replaces its level for members): `sala-region` (required: the `ciclo` block holds both `<!-- SALA -->` and `<!-- /SALA -->`) (since padrón 1.2 `ciclo-block` is required for every repo, so no real requirement uses `levelInRoom` any more; the mechanism stays for a future one). `ready` is unchanged: every required requirement, after that override, must pass. `GET /api/requirements?id=` adds `room: { name }` for a member; for any other repo the answer is the same as before. `requirements/INSTALL.md` tells the agent to keep the SALA region (both marker lines and everything between them) when the repo is a member of a room or when the order names `sala-region`, and to remove it only when neither applies.
- `GET /api/rooms` returns, per room, its requirement results, `lastCommit` (ISO date of the room's local `HEAD`, or `null`) and, since RP218, `id`: the id of its folder as a repo of a group, or `null` when it is not one (a room created before RP218 may be in that case). An added field: `API_VERSION` stays 15.
- The Conformity drawer does not say "All repositories conform." while the rooms load, fail to load, or any room has a required requirement that is not passing. RP218: the folder of a room is the room itself, not a project, so the roadmap audit and the Requirements list leave it out (the room is judged by its own requirements, in the Rooms section).
- **Not covered**: that a member repo is listed in `ENLACES.md` (free markdown, it would give false positives) and whether the room is behind (last sweep older than merged PRs). Nothing here edits the room or its members; the agent applies remedies and you deliver them with `/flow-ship` and `/flow-pr`.

`base` is the branch work is merged into. When omitted, the panel reads it from `origin/HEAD` and falls back to `main`. `roadmap` is the repo-relative path of its plan file (default `docs/ROADMAP.md`); unsafe values (absolute, starting with `-`, or containing `..`) are ignored.

### Adopted sessions

The panel keeps ONE adopted session per repo and per room (`sessions` in `config.json`). Sessions are read from Gentle Shell's folder (`~/.gentle-shell/agent/sessions/--<folder>--/<timestamp>_<id>.jsonl`, overridable with `REPO_PANEL_SESSIONS_DIR`); the listing reads only the first and last 64 KB of a file, and the chat history the last 512 KB. Routes (token required; `id` is a repo id or `room:<name>`, 404 when unknown):

- `GET /api/sessions?id=` answers `{ key, adopted, adoptedFound, sessions, live }`: `sessions` are the newest 20, `live` is `{ state: none | free | working | waiting, count }` from the RPC host (RPC2b-1: `idle` is `free`, `busy` and `starting` are `working`, `asking` is `waiting`, `closed` is `none`; a room key is always `none`).
- `POST /api/sessions/adopt` `{ id, session }` (400 when `session` is not one of the listed ids) and `POST /api/sessions/release` `{ id }`.
- `POST /api/rpc/start` also adopts the session id it runs under when the repo has none adopted (an adopted one is never replaced), so the chat reads its history; `POST /api/sessions/adopt` and `release` stay.
- `GET /api/chat?id=<repoId | room:Name>&session=<optional>&limit=<optional>` is the read-only history of a session, for the chat panel. It reads ONLY the last 512 KB of the session file (the first, possibly partial, line is dropped; a file can be 25 MB) and answers `{ key, sessionId, found, items, truncated, updatedAt }`. `session` defaults to the adopted one; an explicit one must match the id pattern and be one of the listed sessions of the folder (400 otherwise); an unknown key is 404; with no adopted session and none given the answer is `sessionId: null, found: false, items: []`. `items` are oldest first, at most `limit` (default 30, maximum 100): `{ role: "user" | "assistant", text, at, tools }` (the `text` is cut at 50 000 characters, RP162: a cut item also carries `cut`, the integer number of characters left out, and the bubble says «Message cut: N more characters, see the rest in the terminal»), plus `thinking: true` on an assistant item where the model reasoned (the chat shows «thinking…»; it is only the mark), and `stop: "aborted" | "error"` on an assistant item whose turn was stopped or failed (from the `stopReason` of the message: only that category travels, never its `errorMessage`; a stopped turn with no text is an item too). A compaction of the context is an item `{ role: "system", kind: "compaction", text: "", at, tools: [] }` in its place, without its summary. An item with tools also carries `toolInfo`, one entry per tool in the order of `tools`: `{ name, ok, ms, arg }` plus, once the result is there, the NUMBERS `size` (the characters of the result text) and, for an `edit`, `add` and `del` (the lines its unified diff adds and removes): never any text of the result or of the diff (`ok` true or false from the result, `null` while it has no result; `ms` its duration or `null`; `arg` the main argument of a KNOWN tool as ONE line of at most 80 characters: the path of read/edit/write/ls (never a URL), the pattern of grep/find, the host of a fetched URL (`https://host/…`, http, https or ftp only: never its user, password, path or query), the NAME of a subagent; a web search or a subagent label shows nothing). A shell command (`bash`) is NOT cleaned with patterns, because no pattern list knows every form a secret takes (two independent checks found 23 and then 12 forms that got through): it is rebuilt from vocabularies known in advance (`server/redact.js`). Shown: a known program, only at the start of a command or after an operator (`git`, `npm`, `node`, `ls`, `curl`...), the first subcommand of a few CLIs (`git`, `npm`, `docker`...), flag NAMES made of letters (never their values), a file with a known extension or an absolute path, `NAME=…` for an uppercase environment name, and the host of a URL. A quoted run, an unknown program and every other word become `…`. The patterns (authorization headers, secret-named flags and variables, `user:password@`, private keys, GitHub / `sk-` / Slack / AWS / Google / npm / JWT token formats, long random-looking strings) still run on every summary as a second layer. Accepted limits: the NAME of an absolute path or of a host and the text of a grep or find pattern are shown as they are (they are names the agent works with, not values it passes to a command), so a secret used AS a file name, a host name or a search term is not hidden. Also shown: the first word after a known CLI (`git`, `npm`...) when it is only lowercase letters and hyphens, the NAME (not the value) of an uppercase environment variable, and a word glued to a known extension (`echo x.md`). Nothing else of the arguments (the body of a write, the old and new text of an edit) and none of the result text is included. The thinking text and the tool results are never included, a tool is its NAME plus `toolInfo`, and tool-only assistant messages are folded into the `tools` of the next assistant item with text (a trailing run becomes a final item with empty text, the session is still working). Text is capped at 4000 characters per item (with `…`) and control characters other than line feed and tab become spaces (CR and CRLF become LF, the blocks of one message are joined with a blank line, so line breaks are kept). `truncated` is true when older messages exist beyond the 512 KB window or the `limit`; `found` is false when the file does not exist; a corrupt line is skipped. The route never writes anything.
- `GET /api/chat/result?id=<repoId | room:Name>&call=<tool call id>` (token required) is the cleaned START of the text of one tool result, for the click on a chip. It answers 403 unless `chat.showResults` is `true` in `config.json` (off by default) and 403 for the result of `read` (the contents of a file); 400 for a call id that is not 1 to 80 letters, digits, `_`, `.`, `:` or `-`; 404 for an unknown chat or for a call that has no result in the recent 512 KB of the adopted session. It answers `{ call, name, ok, text, truncated, size }`: `text` is at most 300 characters from the START of the result, with terminal sequences (colours, titles, cursor) and control characters removed, every line break (LF, CR, CRLF, NEL, U+2028, U+2029) ending a line, every line of the form `UPPERCASE_NAME=value` (also `export`, `set`, `declare -x`, `$env:NAME=` and spaces around the `=`) losing its value, and the patterns of `server/redact.js` applied as a second layer (they are not enough alone: that is why the switch is off by default). A tool is refused when its name, read as a person would (accents, invisible characters, spaces and punctuation inside it ignored), is `read`, has `read` among its words (`read_file`, `mcp__fs__read_file`, `ReadManyFiles`) or holds a file-reading compound (`readFile`, `readTextFile`, `fileRead`), but not `thread`, `Reader` or `readme`. Also refused by name: `cat`, `view`, `slurp` and the common file getters (`view_file`, `open_file`, `get_file_contents`, `fetch_file`, `load_file`...). Accepted limits of free text: a lowercase variable name, a prefix such as `+ ` or `12:` before an assignment, `password: value` in JSON or YAML, the continuation lines of a value in quotes or a heredoc that spans several lines, less common ways to set a variable (`Set-Item Env:`, `setenv`, `ENV[NAME]=`), a secret as prose, a homoglyph or an unusual name of a tool that prints a file, and the output of any other tool that prints a file (`bash` running `cat`). It is never part of `GET /api/chat`: with the switch on, that answer only adds `results: true` and an `id` (the call id) to each chip of `toolInfo`, and with it off the answer is exactly what it was.
- `GET /api/settings` and `POST /api/settings` (token required) are the options of the panel that the page may read and write, over a CLOSED list kept in `server/settings.js` (today only `chat.showResults`). `GET` answers `{ options: [{ key, value, default }] }` and nothing else of `config.json` (never the port, the groups and their paths, the rooms or the sessions). `POST` takes `{ key, value }`: a key that is not in the list, a key that is not text, a value of another type than the one the entry says (`chat.showResults` takes only `true` or `false`) or a body that is not an object is a 400 and the file is not touched; a write changes only what the entry says and keeps every other key of `config.json` as it was; it answers the list as it is now. Anything else is changed by hand in `config.json`.
- The **Settings** tab (the fourth, after Conformity; never the tab the page opens on) lists the options in a grouped list: Chat, Pi, Delivery, Visual and Director. Each row says where it is saved: «Panel» (in `config.json`, for every browser: the privacy switch `chat.showResults` through `POST /api/settings`, and «pi to use» through `POST /api/pi-runtime`, the same selector as in Conformity) or «This browser» (the preferences the page already kept: merge method, delete the branch after merging, clean repos as a column, diff view; they never go to the server and the controls of the bar stay in step). The defaults shown are the real ones (delete the branch and clean repos as a column are on). What is not built yet (the variables passed to the sessions, the agents in parallel of the Director) is shown disabled and marked «Planned».
- **One copy of each message (RP155).** While a tool runs, the history already holds the message the assistant wrote before it (it is saved as soon as it ends) and the live bubble of the session still keeps the same text until the run ends, so the chat used to show it twice. The live bubble is now not drawn when it says the same as the last answer of the assistant with text that comes after your last message in the history (spaces collapsed, the way the pending messages compare); when the history does not have the message yet it is drawn, so there is no gap, and while the copy is hidden the `working…` line stays so the chat never looks stopped. The live text also holds only the message being written now: every message starts with it empty (the page used to keep the text of the earlier messages of the run too, so a run with several messages showed all of them together). Known limit: two messages that are really identical and follow each other hide the live copy until the run ends, and then the history shows both.
- **One address per screen in Summary (RP133).** The address of the page follows the open repo and its zone: `#/repo/<id>/<zone>` with the zone `chat` or `repo` (when reading, no zone means chat), the list is the empty address, and `#conformity` still opens Conformity. Opening a repo, changing the zone and closing the chat write an entry in the browser history, so Back and Forward walk those screens and a link reopens the same place. The address is untrusted: only an id that is in the list of repos counts (exact text, letters, digits, `_` and `-`, up to 64 characters), nothing is decoded (a `%` is refused), evaluated or drawn as markup, and anything else is ignored and the address bar goes back to what is open. A chat that has no address (a room) leaves the bar alone. The zone has no buttons yet (they come with the mobile layout): it changes with the address.
- **Subagent working** (RP152, RP171): while a subagent runs in the open session, the chat shows ONE bubble at the end of the thread, with a drawn arrow, `Subagent working · NAME` (`2 subagents working` when there are two) and a clock mm:ss that starts when the first one started and moves by itself every second (the clock is hidden from screen readers: the bubble announces only that it appears and that it ends). The name is the one the history already carries for the pending `subagent_run` call (letters, digits, `.`, `_` and `-`, up to 40; anything else is left out), never read from the live events, whose arguments the server still never forwards. When the subagent ends one line stays in the thread, `Subagent NAME finished · M:SS` (`failed` after an error), and it comes back when the history is read again. The bubble replaces the chip of the composer, the chip of the `subagent_run` tool and the grey «working…» bubble (there is only one of those, and none while a subagent bubble shows). It goes away with the end of the run, an abort, a closed session or a (re)connect: what the page does not know is never shown as working. It never says slow, it only shows (it never holds or releases a delivery button), and a subagent started in the background ends its call at once, so it is not shown while it keeps running.
- **Context meter** (RP139): in the head of the chat (RP197; it was in the foot, next to the state of the session) the chat shows how much of the context window the session uses, for example `ctx 62%` (the word `ctx` is hidden the accessible way: the icon and the number stay); the memory chip is there only while the memory is NOT ready, and the CI chip only while the checks run or fail (silence when all is well); in the ⋮ menu the memory (also when it is ready), the context and the checks of the PR are icons with no text, side by side, each with its name and a tone; the help text says `Context used by this session: 124k of 200k tokens`. In the head of the chat on a wide screen the chip also adds the totals of the session (RP239), for example `ctx 42% · 34k tok · $0.12`, and its help ends with the exact totals, for example `This session so far: 34,012 tokens, $0.12`; from one million on the chip reads the tokens in M (`97.4M tok`); a cost under one cent reads `<$0.01`, exactly 0 reads `$0.00`, and an unknown total is simply left out. The phone row keeps the percentage alone. Right after a compaction the figure is unknown and it reads `ctx —` (never 0%). The chip is quiet below 70%, warns from 70% and warns strongly from 90% (icon, number and words in the help, never colour alone), and nothing is drawn while the session is closed or starting. `GET /api/rpc/context?id=` (token and host check, like `/api/rpc/status`) asks the live session for `get_session_stats` and answers ONLY `{ tokens, percent, window, cost, sessionTokens }` (finite non-negative numbers or null, percent clamped to 0..100; `cost` is the cost of the session so far, up to a million, and `sessionTokens` its total tokens, a safe integer, and both are kept even when the window is unknown; any failure or odd answer is all null; 409 when the repo has no session). The page reads it when a chat opens, when a run ends and when a compaction ends, never on a timer. It is read-only: it changes no pi setting and leaves auto-compaction as it is.
- **Quick replies** (RP166): when the assistant writes its options as text on the last line of its last message («Answer with `a`, `b` or `c`.»), a button per option appears in a thin row above the message box (outside the scroll of the chat, RP209) and a click sends exactly that option, through the same path as the message box; with a question and no options a Reply button moves the cursor to the box. They appear only while the session is idle with no dialog pending, never on a cut message, and nothing is sent without a click.
- **Yes and No** (RP246): when the last line of the last assistant message is a yes/no question written as text (it ends with `?`, does not start with an asking word such as qué, cómo, cuál, por qué, what, how or which, and offers no either-or with «o» or «or»), the quick replies offer **Sí** and **No** (or **Yes** and **No** when the question is not in Spanish) next to **Reply**. A click sends exactly that word, through the same path and checks as the other quick replies; an open question keeps only **Reply**.
- **Chat chips as drawn icons** (RP156): the state of the session, the memory, the context and the subagent chips draw their icons as SVG (the same family as the rest of the page) instead of text characters: each state of the session has its own shape, the memory chip has an icon, the context is an arc as long as the percent (a triangle from 70%, a cross from 90%) and the subagent chip draws its arrow. When the chat is narrow (about 480 px or less) the chips keep only their icon, the context number and the subagent time; the words stay for screen readers and in the help text, and «Close session» reads «Close». If the row does not fit it wraps to a second line instead of cutting a button. While the session is starting, the icon of «Starting…» turns like the spinner of the CI (it stops with the reduced-motion preference); «Working…» and «Compacting…» keep their pulse (RP174).
- **CI in the state label** (RP170): the state label function can say `Verifying Checks · N running · P/T` with a turning icon (a red `Checks Failed` when they failed, with no animation) when it is given the CI of the PR of the current branch, but since RP191 no screen gives it one: the foot bar of the chat shows the session state only, the checks are in the chat head, and the PR line of the card shows the turning icon instead of the dots.
- **Compact by hand** (RP140): a `Compact` item of the ⋮ menu of the head of the chat (RP195; it was a small button next to the `ctx` chip) compacts the context of the session of the open chat, at any moment the session is live (idle or answering); it is not drawn while the session is closed, starting, asking you something or already compacting. While it lasts the state reads `Compacting…` instead of `Idle` or `Working…` (also when the session started the compaction by itself) and a message cannot be sent. Compacting an answer in progress stops that answer first, so on a busy session the page asks `The session is answering. Compacting stops that answer first. Compact anyway?` and sends nothing if you decline. `POST /api/rpc/compact` (body `{ id, force? }`, token and host check) is decided by the server alone: only an idle session gets the command (a busy one only with `force` exactly `true`), a second call while one is running is a 409, the page never chooses instructions for the compaction, and the answer is only `{ compacted: true }` or a fixed message (already compacted, too small, failed, timed out). A timeout does not release the in-progress mark while the session still says it is compacting: its end event does, and a second compact stays refused meanwhile. On success the history is read again (the `Context compacted` marker) and the context is measured again. The panel never changes auto-compaction: it stays as it is and no pi setting is written.

### Claude usage bar

The header shows how much of your Claude limits you have used (RP96): two compact meters, **5h** and **7d** (the 5-hour and the 7-day window; there is no monthly or per-model figure in the data), each with a fill bar, the percent used and a countdown to its reset (`2h 29m`, `4d 14h`). A thin **pace mark** on each bar shows how much of the window has already run: if the fill is past the mark you are using it faster than the clock. The fill is green under 70%, yellow from 70% and red from 90% (RP144), and those two also carry a `⚠`, so the warning never depends on colour alone; grey is kept for old data. A dash (`5h –`) means that window already reset or was not reported. Grey meters with a small yellow dot in front (RP147) mean the data is old: the file was last updated 15 minutes ago or more, and the dot's tooltip says how old (`Usage data is 20 min old`). `Claude usage: no data` means there is no usable file yet. Hover it, click it or focus it with the keyboard to open a popover with each window's wide bar, `N% used`, `Resets in …`, the exact reset time, how much of the window has run, a written warning when it runs ahead of the clock, and how old the data is; Esc closes it. Under 760 px (RP192, thinner in RP211) each window is a thin 26 px ring instead, with no name: the percent inside, the arc in the same colour as the bar, a short tick for how much of the window has run and the time left to the reset next to it, without a space (`2h29m`, `4d14h`); the ring's accessible name still says the window and when it resets (the bar and the text percent are hidden there; the popover is unchanged). It only reads `GET /api/usage`: nothing about that route or the extension changed.

The data comes from a small file that an extension of the agent writes (`~/.gentle-shell/agent/claude-usage.json`); set `REPO_PANEL_USAGE_FILE` to read another path. The panel only reads it, on every request, through `GET /api/usage` (answer: `available`, `five`, `seven`, `updatedAt`, `stale`). The page asks every 30 seconds while the tab is visible. Sessions that were already open must be restarted to load that extension, or they never write the file.

## Responsiveness

- **Interactive lane.** What the person does is served first: every POST (except the read-only `POST /api/queue` and `POST /api/conformity`) and any GET sent with `x-priority: user` (the page sends it when a card's chat is opened). Such a request may use up to 2 child processes over the cap and goes before waiting automatic refresh work. The periodic refresh stays in the background lane.
- **`REPO_PANEL_MAX_PARALLEL`.** Caps the child processes (git, gh) the panel runs at once, so a refresh of many repositories does not starve the machine. A positive integer; default 8 (absent, invalid, 0 or negative values fall back to it).
- **`GET /api/perf`** (needs the token, does not record itself). Answers `{ routes, queue }`. Per route, over its last 200 requests: `n`, `p50`, `p95` and `max` in ms, `waitP50` (median wait for a process slot), `procsAvg` (processes per request), `executions` (handler runs; identical concurrent GETs share one) and `priorities` (counts of `user` and `background`). `queue` is `{ active, max, waitingBackground, waitingUser }`.
- **Server-Timing.** Every JSON answer carries `Server-Timing: total;dur=<ms>` and, when the request waited for a slot, `queue;dur=<ms>`.
- **Slow log.** A request of 1500 ms or more prints one console line (route, ms, queue wait, process count) at most once per route every 10 s. Nothing else of the request is logged.
- **Summary store (RP78).** `GET /api/summary` no longer builds the board per request: the server keeps every repo's facts in memory (`server/summarystore.js`) and answers a snapshot at once with no Git or `gh` call. Each fact has its own age: the local state and the repo state are read every 15 s, the pull requests, the roadmap and the last commit every 60 s, a pool of 3 repos at a time, in the background lane; a read that does not answer in 90 s counts as failed. Nothing is read until a page asks for the first time (no client, no work), so a server started only for a request stays passive. The session of a row is the RPC host's live state, read when the snapshot is built (RPC2b-1; `starting` counts as working). RP161: when a live session still waits for background jobs (a `bash_background` job, a `monitor` or a background `subagent_run`) the session carries `jobs`, an integer from 1 to 99 (`{ state, jobs }`); with none the field is absent and the row is the one of always. The server counts them from the session file the chat already reads (the last 512 KB, `server/jobs.js`): a start with no end after it is pending, paired by its `outputPath` (jobs and monitors) or its `taskId` (subagents), which never leave the server; a monitor that tells while it runs is not an end, and a notice with any status other than `running`, a `job_stop` or the result of a subagent is. Only the starts written after the panel started the session count (`startedAtOf` of the RPC host), a closed or unknown session has none, and what the code cannot understand counts as no job. Only the number travels: no path, label or word of the file. The page does not use it yet (RP163). A repo whose facts were not all read yet is a `loading` row (a calm "Loading…" card with no action, counted as idle, sorted last); a failed read keeps the last good value and the row carries `stale: { facts }`, the card is marked busy (`aria-busy`) and its tooltip says "Updating: <facts>" (RP94b: there is no "Updating…" text; also set when a fact is older than 3 times its interval). A fact that never succeeded gives the usual error row. `?fresh=1` reads every fact of every repo again before answering. When nobody asked for the Summary for 60 s the loop slows down to 30 s and 300 s, and a request speeds it up again. `server.js` starts the loop; creating a server does not. Hot repos (the current branch has an open pull request) re-read their pull requests every 15 s and their local state every 10 s while a page is active, and after a merge, re-run, fetch, a command to the session or a chat message the server re-reads that repo at once and once more 5 s later.
- **Board from memory (RP80).** `GET /api/board?since=N` answers at once, from the Summary store's memory and with no Git or `gh` call, `{ rev, repos, refreshing }`: the repos whose facts changed after revision `N` (all of them for `0`; `400` for a `since` that is not an integer >= 0, `404` without a store). Each repo carries its `rev`, the last-success time `at` of each fact, `errors`, `stale` and the values `local`, `prs`, `roadmap`, `state` and the new sixth fact `req` (the requirements, read every 60 s like the pull requests and never part of the Summary). `POST /api/board/refresh` answers `{ started: true }` at once and re-reads everything (or only `{ id }`) in the background. F5 paints from that memory immediately and re-reads in the background (the page tracks the repos the server reports in `refreshing`; RP181: the header shows no indicator for it); after a command sent from the page ends, or a fetch or merge, the page asks the server to catch up that repo and its own direct reads win over an older board fact. A server restart (a lower `rev`) is followed, not ignored. The old per-repo routes are unchanged: if the board answers 404 or fails three times in a row, the page falls back to them and retries the board slowly. `API_VERSION` stays 15.
- **A calmer page (RP181).** The header has no Updating indicator any more (it was on all the time and told nothing; the "Updating…" of the Tasks tab, which answers a button, stays). Instead a quiet yellow notice, "Not updating. The data may be out of date. Check the panel server or your connection.", shows only when the page is visible and more than 90 s have passed since the later of the last good answer of the server (or any byte of the event stream) and the moment the page became visible, so waking the phone does not flash it; it goes away by itself at the next good answer, and a failed read of the Summary keeps its own note. When you come back to the app (the page becomes visible, `pageshow` from the back-forward cache, or the browser goes `online`) the page asks for the Summary and the chat at once. There is no pull-to-refresh gesture.
- **After an action (RP86b).** When the person's own action ends (a flow button, a fetch, the end of a session) the page used to read five routes of that repo directly (`/api/local`, `/api/prs`, `/api/roadmap`, `/api/requirements`, `/api/state`) and ask the board to catch up. While the board answers, it now reads directly only `local`, `prs` and `state` (what an action changes, and the freshest signal after one: the board is polled every 3 s); the roadmap (about 240 KB on a big repo) and the requirements arrive by the board, as long as the page already holds them for that repo (a repo with no roadmap is held: the server answers `{ available: false }`; a failed read, which leaves `null` or a failed state, is not held and is read again). A fact the page does not hold, a board that is down or never answered, and a refresh that is not an action keep the five direct reads. Measured on this repo: the five in parallel took a median of 1,841 ms and `local` plus `prs` alone 1,039 ms.
- **Request timeouts.** The page gives up on a GET after 25 s and on a POST after 70 s ("Request timed out"); the Summary, which builds the whole board, has its own 90 s limit until RP78. Switching or closing the chat card cancels its pending reads.
- **Identical reads are shared.** Two identical GETs in flight run once, per lane: an interactive request never joins a background one that may have waited in the queue.
- **A malformed URL answers 400** (and a wrong Host 403) and never takes the server down.
- **Known limits.** The background lane has no aging: an endless chain of interactive requests would delay it (human clicks never do). With the default limit of 8 the wait of an interactive request for a process slot is about 0 ms.
- **`scripts/measure-panel.js`.** `node scripts/measure-panel.js [--port 4398] [--json]` starts its own temporary panel on its own port (a copy of your config, no browser polling it) and times the Summary, each per-repo route, a full refresh and the wait of an interactive read during it. It only sends GET requests: it never runs an action or sends anything to a session.

## Merge behaviour

- Clicking **Merge** merges immediately, with no confirmation (like GitHub's own button). It is only enabled when the PR is green and mergeable.
- Merging goes through the GitHub API, so your local branches and working tree are never touched.
- **The repo decides the merge method (RP226).** `POST /api/merge` asks GitHub which methods the repo allows (`mergeCommitAllowed`, `squashMergeAllowed`, `rebaseMergeAllowed`, cached 10 minutes with the repo data). The **Merge method** setting is only the request: when the repo prohibits it, the panel uses the first allowed one in the order squash, rebase, merge, and the answer adds `method` (the one used) and `requested`; the toast says `merged with squash (merge is not allowed here)`. When the request is allowed, or `gh` does not report the flags, the answer is the usual `{ merged: true, branch }`. A repo that allows no method gets `409` and nothing is sent to GitHub. The panel never changes a repo's settings; `API_VERSION` stays 15.
- The server re-checks readiness right before merging and pins the merge to the PR head SHA, so a late push cancels it.
- *Delete branch* is offered only when the repo does not already delete merged branches (`deleteBranchOnMerge`). If GitHub already removed the branch, that is treated as success, and local branches whose remote disappeared show as "remote branch deleted" instead of an error.
- A repo whose current branch (other than the base) already landed gets a red **Merged: run /flow-base** mark and goes to the top of its column. The panel flags it when the remote branch is gone or a merged PR came from that branch, and not when a new open PR reuses the branch name.
- `GET /api/roadmap?id=<repo>` returns the parsed `docs/ROADMAP.md` read with `git show origin/<base>:<path>`, never from the working tree, so a unit counts as done only once its PR is merged. Run a fetch to see newer data. A repo without the file answers `available: false` (not an error).
- `GET /api/summary` (token required; read-only; `?fresh=1` skips the cache) returns `{ rows, counts, attention, generatedAt }`, one row per configured repo, built only from what the other routes read (`localState`, `prState`, `roadmapState` with its derived states, `readState`, the session screens, `lib.workQueue`; the session comes from the RPC host). A row always has every field and a value that is not known is `null`, never invented: `{ id, name, group, room, branch, progress: { total, completada, enRevision, bloqueada, pendiente, enCurso }, session: { state }, next: { id, entrega, resultadoVisible } | null, blocking: [{ unit, waitsFor, external }], lastMovement: { at, what }, action: { kind, label, pr } | null, error, needs, rank }`. `needs` is true when the repo is in `attention` (an asking session, a PR with failing checks, or a `Bloqueada` unit only when the repo has no takeable next unit; false for error rows) and `rank` is its urgency, lower is more urgent, from one definition in `server/summary.js` that reuses `lib.QUEUE_RANK`: 0 a session asking you, 1 failing CI, then the "Go work on" kinds in their own order (2 `merge`, 3 `branch` and `manual`, 4 `waiting`, 5 `deliver`, 6 `start`), 7 a working session, 8 a blocked repo, 9 everything else and error rows. `progress` counts each roadmap row once: `enRevision` and `enCurso` come from the derived states (not the hand-written column) and a derived `Lista` row stays in `pendiente`; the values are `null` when the repo has no readable roadmap. `session.state` maps the session: `none` (closed), `free` (idle), `working` (busy), `waiting` (asking a question) and `unknown` (a state the vocabulary does not know; `starting` is `working`). `blocking` has at most 3 entries: the `Bloqueada` rows (`waitsFor` their table dependencies, `external` the dependencies that are not rows) and, when no unit can be taken, the first `Pendiente` row with its unmet dependencies. `lastMovement` is the date and subject of the local `HEAD` commit (both `null` when Git cannot say). `action` is the first entry of the "Go work on" queue for that repo (`merge`, `branch`, `manual`, `waiting`, `deliver` or `start`; `pr` only for `merge`), except that a session in `waiting` gives `{ kind: "answer", label: "Answer the question in the session" }`; it is `null` when there is nothing to do. `counts` classifies each repo once (`waiting`, `working`, `blocked` by `blocking`, otherwise `idle`; error rows are not counted) and `attention` lists the repos with an asking session, a PR with failing checks or a blocked unit with no takeable next unit, with a `why`. A repo with a `Bloqueada` unit AND a next unit it can take does not need attention (`blocking`, `counts.blocked` and `rank` do not change). **A repo whose Git or `gh` read fails gets a row with `error` set and nulls; the others are unaffected.** Repos are read six at a time, and the whole response is cached for 10 seconds. `API_VERSION` does not change.
- **When GitHub degrades (RP278).** Every `gh` call of a merge has its own short bound (20 s for the reads and the branch delete, 30 s for the merge itself), and waits at most 20 s for a free place among the panel's GitHub and Git work: past that it answers 503 *The panel is busy with other GitHub and Git work: try the merge again in a minute* and the call leaves the queue (it never runs later). An answer that is empty or cut, the Go error *unexpected end of JSON input*, a 5xx of GitHub (*Server Error*) or a call killed by its bound gives the fixed message *GitHub did not answer in time: check the PR on GitHub before retrying*, never a raw parse error. When the merge call fails that way the panel reads the PR up to 3 times, 2 s apart: `MERGED` is the usual success, and if no read works the answer is *GitHub did not confirm the merge: check the PR on GitHub before retrying*. A clear refusal of GitHub (for example *Head branch was modified*) still shows its own first line after one read, as before. Only the merge path uses these bounds; every other call waits for its place as before.
- Branch protection and required reviews on GitHub still apply.

While it is open (and Summary is visible and the page is not hidden) the panel reads `GET /api/sessions?id=` and, when a session is adopted, `GET /api/chat?id=` every 5 s, and redraws only when the answer changed; a failed read keeps the last data with a small "Chat unavailable" note. States: with no adopted session it lists up to 5 sessions with an **Adopt** button and a **Start panel session** button (the explicit buttons of `POST /api/sessions/adopt` and `/start`; a 409 shows the server's message); an adopted session whose file does not exist yet shows "The session is loading…"; otherwise the messages appear as bubbles (each message is shown with a safe Markdown subset: paragraphs, headings, lists, code blocks, bold, italic, links to http/https and tables (RP124: a header line, a separator line with the same number of cells and `:---`, `---:` or `:---:` for the alignment, then the rows; the outer bars are optional, a row is cut or padded to the width of the head, a wide table scrolls inside its own box, and at most 30 columns and 300 rows are drawn as a table, the rest shows as plain text; bars without a separator line stay plain text); the raw HTML of a message is never inserted, and the message text keeps its line breaks) (you at the right, the session at the left, with the time) and the folded tools as a dashed line `▸ N tools · a, b, c (+k)`. The header shows only the repo name (the session id is just its tooltip) and the close button; the state of the session (free, working with a pulsing dot, asking you something, closed, no session) is shown inside the message box, top left, with the colours of the cards, and the animation stops with `prefers-reduced-motion`. When the session of the repo asks something, the chat shows the card of RPC2-3 (see its bullet above), built from the RPC dialog. The chat WRITES to the session over RPC (RPC2-1): Send, Stop and the answer cards; the history under it is still read, read-only, from the session files. `API_VERSION` stays 15.

**Chats open at once (RP79).** The page keeps the last 8 chats it read (one per repo, in memory only) and, when you switch card, shows that chat immediately with the state "unknown" while it reads again in the background. The question card and its answer buttons never come from the cache: they appear only with the fresh read. The two reads (`/api/sessions` and `/api/chat`) now run in parallel.

**Actions react at once (optimistic).** A command button makes the card say "working" in the same instant (the server state shows again when the command ends), and a chat message leaves the box and appears as a pending bubble ("You · sending…", then ✓) until the history shows it; if the send fails the text comes back to the box. After a merge the Merge button stays disabled ("Merged ✓") until GitHub no longer lists the PR or 90 s have passed, and a merge in flight pauses only the refresh of its own repo. A repo with a command in flight asks for its session state every 3 s, so the end of the command is noticed quickly, and it keeps refreshing its pull requests as before.

**Colours of the action buttons.** Every action button is soft (a light tint, never a solid fill) and its colour tells the effect: blue starts work (`/flow-next`, `+ Repo`), amber hands over your work or asks for your answer (`/flow-ship`, and Open on a card that waits for an answer), green publishes (`/flow-pr`, Merge), violet opens a new cycle (`/flow-base`) and orange fixes (`Fix CI`, formerly `Fix with pi`). Gray buttons are secondary, and a disabled button is always gray and dimmed. Urgency is shown by the card, not by a solid button; only the answer, waiting and `Fix CI` buttons get a slightly stronger tint.

**When /flow-next is offered (RP138).** On the card, in the chat and in the Go work on strip, `/flow-next` shows when the repo has a next unit, a clean tree, nothing unpushed, a branch that is not stale and no open pull request that belongs to a unit. A pull request belongs to a unit when the id of a row of `docs/ROADMAP.md` is a whole token of its title or of its head branch (the rule that computes *En revisión*); the one release-please keeps open, or a bot's, is nobody's task and does not hide the button. With no usable roadmap every open pull request counts. The server computes it in `server/summary.js` and the page in `public/tabs.js`, both with `taskPrs` of `public/view.js`; restart the server to pick the change up.

## Computed unit states

The roadmap file only holds `Pendiente`, `En curso`, `Completada` and `Bloqueada`. The panel adds three states computed from Git and GitHub, never written in the file. A unit is linked to work by its ID as a complete token in a branch name or in an open PR title (`p2` matches `p2-header` and `feat/p2_x`, not `p20-x`, `p2.1-x` or `rp3b-x` for `rp3`).

- Precedence per unit: `En revisión` > `Lista` > `En curso` (derived) > the state written in the file. `Completada` and `Bloqueada` units are never overridden.
- `En revisión`: an open PR has the ID in its title or head branch.
- `Lista`: the current branch has the ID and the tree has changes or commits over the base, or another local branch with the ID has commits over `origin/<base>`.
- `En curso` (derived): a local branch with the ID exists, but it has no commits over the base and the tree is clean. A row written as `En curso` in the file creates no derived entry; it is only replaced when it becomes `Lista` or `En revisión`.
- `siguiente` skips every unit that has a derived state.
- A branch merged by squash still counts as not merged for Git, so it can only affect units that are not `Completada`, and it is ignored when its remote branch was deleted.

- The `put-in-conditions` order was never typed into a real session: not verified that the agent can read a file outside the repo from the order (it now goes by RPC `prompt`).

- The requirements and prerequisites blocks of the Conformity drawer have no browser test: their rendering (collapsed passing list, remedy lines, loading and failed messages) and the badge count were not seen on screen. Unit tests cover the checks, the routes and `conformityView`.

## Page code

The page is plain scripts with no build step. `index.html` loads them one after the other and they share the global scope (the state `S`, the helpers and every function), so the order matters: every file except the last only defines things, and touches the page when one of its functions is called, never while it loads. Three files are pure (data in, HTML out) and the page tests share them: `public/view.js`, `public/highlight.js` (the syntax colors of the file and diff viewer: JavaScript and TypeScript, JSON, CSS, HTML, Markdown and shell, files up to 2,000 lines; the text of a file is always escaped, the only markup it adds is a token span) and `public/resumen.js`. The rest is split by layer, in load order:

- `public/notify.js`: a pure library loaded with `view.js` and `resumen.js` before the page scripts and also required by the server: which kind of attention a Summary row asks for, the text of a notice, the check of a `notify` event and the decision of what to show (RP178).
- `public/data.js`: the requests to the server (with their pool) and the reads of each repo.
- `public/feed.js`: the event stream, the board data and the refresh ticks.
- `public/tabs.js`: the derived state, the "go work on" queue and the Summary and Conformity tabs.
- `public/chat.js`: the chat, its composer, the notes pad and the three-block layout. It also keeps the list of the chat in place (RP183): the list is repainted with `innerHTML` and the browser can reset its scroll to the first messages (when something arrives at the end, or when the keyboard opens), so a snapshot of the position is taken before a repaint and when the box is touched, focused or loses the focus, and restored after (now and one frame later; on every resize of the visible area for 1.5 s after the mark). Pinned to the end (under 24 px) it stays pinned, so the last message is never covered by the keyboard; reading higher up it stays where it was, and only a jump to zero is undone, so it never fights a finger that is scrolling. The cause was not reproduced on a device: the fix does not depend on what resets the scroll.
- `public/board.js`: the Work board and its cards.
- `public/actions.js`: the click handlers (`data-act`): merge, re-run, rooms and the usage bar.
- `public/sw.js` and `public/manifest.webmanifest`: not page scripts; the browser fetches them (the service worker of the push, RP179, and the manifest that lets a phone install the app). The push settings live in `actions.js`, `tabs.js` and `resumen.js`.
- `public/viewport.js`: on a touch screen it sets `--vvh` to the visible height (`visualViewport`), so the one-zone layout does not move when the keyboard opens (RP180); it also brings a shifted page back to the top, but only while a field has the focus (the keyboard), and leaves a pinch-zoomed page alone (RP182: it used to do it on every event, which made Settings jump back up at the end of a scroll). The inner scrollers (chat, column, Summary, file tree, options) keep the scroll to themselves with `overscroll-behavior: contain`. Fields are 16 px on touch screens so iOS does not zoom into them.
- `public/app.js`: only the boot (the state, the document listeners, the timers and the first load). It loads last because it is the one that runs at load.

A new page script goes into `index.html`, into the closed list of static files in `server/http.js` and into `test/pagesrc.js`, in that order of loading.

## Notifications (RP178)

The panel tells you when a repo starts to need you, so you do not have to look at it. `server/notifier.js` reads the Summary every 3 seconds and, when the kind of attention of a repo **changes**, sends a `notify` event on `GET /api/events`. The kinds are: the agent **asks a question** (`answer`), the **CI fails** (`ci`), the work is done and **`/flow-ship`** can run (`deliver`), a PR is ready to **merge** (`merge`) and the repo is clean for **`/flow-next`** (`start`).

- **When it speaks.** Never at the first look at a repo (a repo that already waited for you when the server started says nothing), never twice for the same state, and only after a kind holds for two looks in a row (so a flicker of the session says nothing). A look that cannot say (still loading, an error, an unknown session) keeps what was known. A repo that is added later is a baseline too.
- **What the page does.** Nothing while the panel is in view (visible and focused: the card already says it). Otherwise it shows a notice, plays a short sound (two notes: falling for a question or a failing CI, rising for something ready) and, when you allowed it, a system notification; clicking the notification opens that repo's chat. Settings has a **Notifications** section (this browser only) with a switch per kind, the sound, the system notification, the button to allow it and a **Send a test notice** button that ignores the view and the switches.
- **The sound** is made by the page, so a browser only plays it after you have clicked on the page once; the system notification needs the permission that button asks for.
- **What it does not do.** It works only while at least one page is connected to the event stream: with none open it reads nothing (asking the Summary would wake the store, which then reads Git of every repo all the time), and when the last page leaves it forgets what it knew, so the next page starts from a baseline and never gets old news. A phone also freezes a page that is not on screen, so an iPhone only hears a notice while the panel is open: the notice with the phone locked or the panel closed is RP179 (Web Push).

## Remote access (phone)

The server still listens on `127.0.0.1` only. To use the panel from a phone, put [Tailscale](https://tailscale.com) on the PC and on the phone (same account), run `tailscale serve --bg 4310` on the PC (it gives you an HTTPS address such as `https://my-pc.tail1234.ts.net`) and add this to `config.json`:

```json
"remote": { "host": "my-pc.tail1234.ts.net", "secret": "a-long-random-text-of-at-least-16-characters" }
```

- **Host.** `remote.host` is accepted as the `Host` in addition to `127.0.0.1` and `localhost` (compared exactly, case aside). It is read on every request, so editing it needs no restart. Without `remote`, or with a host and no usable `secret` (shorter than 16 characters), that host is refused (403), exactly as any unknown host.
- **Login once.** On the remote host the page asks for the `secret` one time (`POST /login`, JSON `{ "secret": "..." }`). It answers a cookie (`HttpOnly`, `SameSite=Strict`, `Secure` when the request came through HTTPS, 180 days) signed with it and kept by no one on the server: it survives a restart and **changing `remote.secret` ends every session**. After five wrong attempts in a row the login is closed for 15 minutes (429). Everything else on the remote host (page, assets, API, `/api/events`) answers 401 without the cookie, except `/health`. The API still needs the per-run token, which the page gets together with the cookie; after a restart, reload the page. Opening the panel through `127.0.0.1` never asks for a login.
- **Origin.** Every `POST` that carries an `Origin` header naming another host (or `null`) is refused with 403, on both hosts. Requests with no `Origin` (scripts, tests) are unchanged.
- **On the iPhone.** Open the HTTPS address in Safari, log in and use *Share → Add to Home Screen*; log in again inside that installed app (iOS keeps its cookies apart from Safari's). There are no extra confirmations for irreversible actions: the phone does what the PC does.

## Push notifications (RP179)

The notices of RP178 can also reach a device with **no page open** (the phone locked, the browser closed) through Web Push. It is off until you turn it on, per device.

- **Turn it on.** Open **Settings → Push notifications → Enable** and accept the permission. On an **iPhone** the app must be installed first: in Safari open the HTTPS address of the remote access (above), *Share → Add to Home Screen*, open the **installed app**, then Settings, Push notifications, Enable. Safari alone cannot receive a push. On a PC, Edge and Chrome work from the normal tab. **Disable** forgets the device; **Send a test push** checks the whole path.
- **How it travels.** The server sends an empty, signed (VAPID, `node:crypto`, no library) push to the push service of Apple, Google, Microsoft or Mozilla, and the service wakes the service worker (`public/sw.js`), which asks the panel for the text and shows it. So the phone needs internet; the sound is the system one on iOS. If the worker cannot get the text it shows a generic notice (iOS cancels a subscription whose push shows nothing). The server only sends to the endpoints of those four services, to at most 20 devices; pending texts are kept 10 minutes and at most 10 per device.
- **Where it lives.** `push.json`, next to `config.json`, holds the VAPID key pair and the subscribed devices. It contains the **private key**, so it is ignored by Git: never commit or share it. `GET /api/push/key` answers only the public key.
- **The cost.** While at least one device is subscribed the notifier keeps reading the Summary even with no page open, so the store stays awake and reads Git of every repo all the time. Unsubscribe every device to go back to idle.

## Security

The server binds to `127.0.0.1` only, rejects unknown `Host` headers (DNS rebinding; the only one added is the `remote.host` of the section above, behind its login), refuses cross-site POSTs by `Origin`, requires a random per-run token on every API call, and only operates on repositories listed in `config.json`. The one place where the panel writes inside a repo is the notes file (`POST /api/notes`, RP93): a fixed path, never one sent by the page, refused through links, and out of Git.
