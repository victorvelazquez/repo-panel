# Repo Panel

A local, single-window dashboard for the repos you work on. It answers one question: **what is left for me to do?**

- A kanban board with one card per pending thing, in columns: **Clean · Changes · Committed · Pull requests · Merged**. A repo with local changes and a ready PR shows up in both columns.
- **Pull requests.** Every open PR lives in one **Pull requests** column (green top border): the ones **ready to merge** come first (with a green accent on the left of the card), then the ones that need a fix (red), then the ones whose checks are still running or that wait for review. Inside each group the order is the one GitHub gives.
- **Clean, Merged, Idle and Needs attention.** **Clean** is a column by default, first on the board: the compact rows of repos with nothing to do, plus the cards that need a person (a manual action, a failed `/flow-commit` with a clean tree). Repos whose branch already merged (`Merged: run /flow-base`, clean tree, nothing ahead) have their own purple **Merged** column. If you prefer a quieter board, untick **Clean column** in the header: the rows move to a collapsible **Idle · N repos** bar under the board (closed by default, its state is remembered; not drawn when no repo is idle) and the cards that need a person go to a red **Needs attention** column, leftmost, that exists only while it has cards. Tick it again (or press **Show as column** in the Idle bar) to go back; Merged stays in both layouts.
- **Merge feedback.** After you press **Merge** the button is disabled and reads `Merging…`, then `Merged ✓`, and stays that way until the repo has been refreshed and the card moves away; a failed merge enables it again at once.
- Per repo: uncommitted files, `+/−` lines, unpushed commits, and a full diff viewer.
- Per open PR: CI status and a **Merge** button that only enables when every check is green and GitHub reports the PR as mergeable. PRs with failed checks, conflicts or an outdated branch stay in **Pull requests**, marked red as needing attention (the separate **Needs attention** column is for repos, not PRs).
- Repos organised in groups (personal, work, commercial…), shown as a colored tag on each card, with a group filter and a name search.
- A roadmap block on each repo card (in progress or next unit, progress bar, a problems badge and, on click, the roadmap header). It reads `docs/ROADMAP.md` from the remote base branch, not the working tree; repos without that file look unchanged.
- The states `Lista`, `En revisión` and `En curso` (derived) are computed from Git and GitHub, never written in the file. A unit is linked to a branch or an open PR by its ID inside the branch name or the PR title; those units are skipped when picking the next one (`siguiente`).
- A **Go work on** strip above the board lists the next actions in order: a PR ready to merge, a repo whose branch already merged (`/flow-base`; with uncommitted changes it is only that, never also "Deliver changes"), changes not delivered yet, and a clean repo with a next roadmap unit. Clicking a chip filters the board to that repo. A manual order in `priority` (see Configuration) wins over the automatic one.
- The strip also has two chips for repos that must not be delivered yet: **Manual action** (red) for a repo that needs a person's hands (detached HEAD, commits on the base branch, a merge or rebase in progress, a diverged branch, or a `/flow-commit` that needs attention) and **Waiting for you** (blue) for a repo whose declared state is `needs-input` or `blocked`, with its next step. Such repos are no longer told to deliver changes; the full text is in the chip's tooltip.
- The **Conformity** tab (with a count badge) is a full-width view, not a drawer: it hides the shared filters (they never applied to it), is never saved as the tab to reopen, and a repo name in it filters the board and takes you back to the tab you came from. It lists every repo, whatever the filters, that has no usable `docs/ROADMAP.md` or whose file has problems, with the line of each problem. Info-level problems (such as a dependency outside the table) are not listed. It is built from the roadmap read from the remote base branch, so unpushed edits do not show. Opening the panel at `http://127.0.0.1:<port>/#conformity` opens that drawer on load.
- The Conformity tab also shows the **requirements** a repo must meet to show well in the panel, listed in `requirements.json` at the panel root, and the **prerequisites** of this machine (`git`, `gh` logged in, `orca`). Failing, outdated and unavailable requirements come first, with their level (`required` or `recommended`), their category and a remedy (the instruction an AI agent applies in that repo, shown as a second line); passing ones are collapsed. The panel only **detects**: it reads the remote base branch and never edits a file of another repo; applying a remedy is the agent's job, through `/flow-commit` and `/flow-pr`. Whether `flow-skills` is registered in pi is not checked. The required `manual-leftovers` requirement detects what the order cannot name by itself: a manual section of `AGENTS.md` outside the blocks (for example a `## Orquestación` with Puerta, Avisos a Dirección, Tamaño, Verificación según el riesgo or Contratos entre proyectos) that restates what an installed block already says, or the old `/flow-branch`; it removes every block region and looks at what is left (headings of level 2 to 4 with those exact titles, and the text `/flow-branch`), and the detail lists at most 5 findings. It exists because the order only names the ids that fail, so a repo whose `registro` and `ciclo` pass would otherwise never be asked to apply the "replace the WHOLE section" rule of `requirements/INSTALL.md` step 3.
- A card of a repo that lacks a **required** requirement shows a compact "N requirements missing" warning (the tooltip lists the ids) with a ✕ to hide it. A gap that is only recommended shows nothing on the card (the drawer still lists it), and nothing is shown while the requirements load or if they failed to load. Hiding the warning keeps the repo on the panel with the basic features; the choice is saved as `dismissed` in `config.json`.
- A **⋯** menu on each card holds "Put in conditions", present only while some requirement is not passing, and "Hide warning" / "Show warning"; its last item is "Remove from panel…" (RP94: it replaced the loose ✕ button, asks before it removes and deletes nothing from disk or GitHub). "Put in conditions" asks `POST /api/pi` with the key `put-in-conditions`; the server builds ONE line from the repo's requirements (the ids that are not passing, required first) that tells the agent in the open session to read `requirements/INSTALL.md` (absolute path, in double quotes, with the user's authorization to read that one file outside the repo) and apply those ids. It needs Orca and exactly one idle session, like the other buttons, and it refuses with 409 when everything already passes or the requirements could not be read. `confirmed` only means the prompt left the idle state; it does not prove the agent read or applied anything.
- **Answering a question from the panel (RP73).** When the one open session of a repo asks a question, the pinned card of the chat can offer one button per option. It is offered only when the whole screen of the session shows a marker (`→` or `>`) on a recognised list of 2 to 8 short options (1 to 80 characters, each under the marker at the same indentation, directly above the footer line); a list with descriptions, a blank row inside the list or anything else gets no buttons and stays for the terminal. The browser posts `{ id, fingerprint, index }` to `POST /api/dialog/answer` (any other key is a 400) and the server presses keys in a closed loop: it reads the screen again, refuses if the question is not the one on the card (the fingerprint of the question rows and the labels), then sends ONE down arrow at a time and reads after each, aborting unless the marker moved exactly one row and nothing else in the dialog changed, then ONE Enter, and reads up to 8 times for the dialog to go away or be replaced by another question (otherwise 409 "The question is still open: check the terminal"; the Enter is never resent). The only bytes ever sent are the down arrow and Enter, as `orca terminal send --text=<key>`; no text from the browser reaches a terminal. Refused with nothing sent: an affirmative option when the command shown is cut off (an ellipsis or a row over 200 characters; a negative option such as Deny is still allowed), a question that changed since the card, several open sessions, a command already in flight for the repo, and the same question answered less than 10 seconds ago. Everything else is answered in the terminal.
- **Changes tab (RP64).** The same right panel has a third tab, Changes: the single code viewer. Click the **● N files** chip of a card (on the Summary or on the Work board; from Work the page goes to the Summary first) to open that repo on Changes. It shows the list of changed files (status, path, added and deleted lines; click one to see only that file, **All files** brings the rest back) and the code of the uncommitted diff with two line-number gutters (old and new), hunk headers and the added and deleted lines coloured. It reads the existing `GET /api/diff` each time you switch to the tab, keeps the last good answer if a later read fails, and draws at most 2000 code rows (then a "+N more lines" note). It replaced the old diff drawer; the Conformity drawer is unchanged. The composer is hidden on this tab and nothing is ever sent from it.
- **Files tab (RP65).** The right panel has a fourth tab, Files: a tree of the repo's files (folders folded, except the ones that hold a changed file) and, below it, the file you pick, in the same numbered-lines look as Changes, with its **changed lines highlighted** (an untracked file is changed on every line). It reads only: `GET /api/files?id=<repo>` lists what git knows (tracked plus untracked and not ignored) and `GET /api/file?id=<repo>&path=<path>` reads one of those files. Files that look like secrets are shown (your decision), but a path is served only when it is a plain repo-relative path, is exactly an entry of git's listing, is a regular file (a symlink is never followed) whose real path stays inside the repo, and is not under `.git`; ignored files (such as `.env`) are never listed or served, and a refused request always gives the same `File not found`. Files over 1 MiB and binary files show a note instead of text. Known limits: the file is re-opened after the checks (a local process that can write inside the repo could race it), and each read runs two `git ls-files`.
- **Tasks tab (RP63).** The right panel of the Summary has two tabs, Chat and Tasks. Click the progress bar of a card (it is a button; Enter works too) to open that repo on Tasks, which lists the rows of its `docs/ROADMAP.md` grouped as In review, Ready, In progress, Next (highlighted), Pending, Blocked and Completed (folded until you open it). Each row says its PR, its branch or what it is waiting for; a filter box narrows the list by ID or text and keeps its value while the page redraws. It reads the existing `GET /api/roadmap` once each time the chat is opened and keeps the last good answer if a later read fails; the composer is hidden on this tab and nothing is ever sent from it.
- **Rooms.** A room is a repo where you coordinate a group of repos (for example `upen-ceo`). A repo assigned to a room shows a room tag next to its group tag, with a dot: green when a session is open in the room folder and idle, yellow when it is busy, gray when there is none, when several are open or when Orca could not be asked; the tooltip says which and gives the date of the room's last commit. The Conformity drawer has a **Rooms** section with each room's session, requirements and members. Repos outside every room look exactly as before. See Rooms below.
- A red banner at the top of the page appears when the server process is older than the page (for example after `git pull` without a restart). `GET /health` answers `{ "app": "repo-panel", "api": <n> }`; the page compares `api` with its own version and warns on a mismatch or a missing field. If the Conformity report cannot be computed, the drawer says so instead of claiming conformity.
- A **/flow-commit** button on cards with changes types that command into the session you already have open for that repo, through the Orca CLI. It sends only when exactly one session is open in that repo's worktree and it is idle with an empty prompt; otherwise it refuses and says why (no session, several sessions, busy, text already typed, Orca not running). **How a session is recognised:** by its screen, never by the terminal title (Orca renames the same live session: `pi`, `Windows PowerShell`, `π - name`, `Terminal 1`). The panel runs a fresh `orca terminal show` on each connected, writable terminal of the repo's worktree and looks at the last 8 non-empty lines for the prompt bars of Gentle Shell: `▎ <glyph> waiting for input` (idle when the next bar line is `▎   type, or / for commands`, otherwise text is typed) or `▎ <glyph> working…` (busy); the glyph alternates (`✿`, `❁`) and does not matter. A plain `pi` run without Gentle Shell, or a busy verb other than `working…`, is NOT detected: the panel then says there is no session and refuses to send. Each check costs one `orca terminal show` per terminal of the worktree, plus one `list`. Orca cannot confirm delivery, so the panel checks that the session left the idle prompt and says `not confirmed` when it did not. The browser sends a command key, never text, and only `/flow-commit`, `/flow-commit --unstage` (key `flow-commit-unstage`), `/flow-pr`, `/flow-base`, `/flow-base --stash` (key `flow-base-stash`), `/flow-next` (key `flow-next`), `put-in-conditions` and `fix-pr` exist on the server. The panel never adds `--unstage` on its own: only the button sends it. The server also refuses a second send of the SAME command key to the same repo for 45 seconds after a confirmed one (409 "That command was already sent N s ago; wait for it to finish"; in memory, per repo path and key, other keys are not affected, and the busy, typed-text, no-session and unknown-command refusals keep their messages and win over it). The reason a double click got through before is unconfirmed (a subagent's screen may read as idle), so this guard is a safety net, not a diagnosis. `fix-pr` also takes `pr`, the integer number of an open pull request of that repo (`POST /api/pi` `{ id, command: "fix-pr", pr }`; `API_VERSION` 12): the server looks the PR up itself, refuses with 400 when `pr` is missing or not a positive integer and with 409 when the PR does not exist, is not open or has no failing checks, then builds ONE line from the PR number, title, head branch and up to 5 failing check names (control characters replaced by a space, double quotes dropped, title capped at 120 and each name at 60 characters). The order tells the agent to find out why with `gh`, switch to the PR branch only if the tree is clean (otherwise stop and ask), fix whatever is needed (production code, test code or configuration) as long as it serves the original objective of that PR (its title, description and commits), run the tests, and not commit, push or open pull requests. It is also told not to use `git mv` or `git add` and to leave the git index empty (`put-in-conditions` carries the same sentence, and so does `requirements/INSTALL.md`), because `/flow-commit` refuses to start when files are staged. When the failure is unrelated to that objective or looks transient (infrastructure, a flaky run, a runner problem) it must not edit code: it says so and recommends **Re-run failed**; when the right fix would change the PR's scope or needs a product decision it stops and asks. It goes through the same safeguards as the other buttons (exactly one idle session, one send at a time per repo).
- Quick actions: open on GitHub, `git fetch --prune`, re-run failed checks, refresh.

Not verified: the `/flow-pr` button, the manual-action bar, the "Show /flow-commit anyway" item and the committing/attention lines were checked through their pure helpers, a render smoke test with a stubbed page and real throwaway Git repos, but not in a browser; the verdict was not run against a real session end to end; and nothing was tried with many repos (each repo polled after a `/flow-commit` costs one `orca terminal list` per refresh).

The panel observes, merges when you click, and can hand `/flow-commit` to your open session; committing and opening PRs are still done by that session, not by the panel.

## Requirements

The panel shells out to `git` and the GitHub CLI, so both must be installed and working before you start. There are no npm dependencies and nothing else to install.

1. **Node.js 20+** (`node --version`).
2. **Git** on your `PATH`, with access to your repos' remotes (`git fetch` must work from the terminal).
3. **GitHub CLI** ([install](https://cli.github.com)) logged in to the account that can see your repos:
   ```bash
   gh auth login
   gh auth status     # must show "Logged in"
   ```
   The token needs the `repo` scope (PRs, CI status, merging) and `workflow` to re-run failed checks. `gh auth login` grants `repo` by default; add `workflow` with `gh auth refresh -s workflow`.

4. *(Optional)* The `orca` CLI on your `PATH`, only for the `/flow-commit` button.

Quick check that everything is ready: `node --version && git --version && gh auth status`. PRs, CI status and Merge depend on `gh`; the local git view only needs `git`.

## Quick start

```bash
git clone <this-repo-url> repo-panel
cd repo-panel
npm start          # then open http://127.0.0.1:4310
```

Other commands:

```bash
npm run open       # same as start, and opens the browser (Windows only)
npm test           # run the test suite (node --test through scripts/run-tests.js)
```

`npm test` forwards every extra argument to `node --test` (`npm test -- --test-name-pattern foo`). On Windows it also reads the definition of the real `repo-panel` and `repo-panel-tray` scheduled tasks (read-only: every action, the triggers and the restart count) before and after the run and fails with a loud message if either changed, even when every test passed. When all is fine it adds one line: `task guard: repo-panel and repo-panel-tray unchanged`. If PowerShell cannot read the tasks the line says so and the run is not failed.

## Start automatically at logon (Windows)

```powershell
powershell -ExecutionPolicy Bypass -File scripts/install-autostart.ps1    # install
powershell -ExecutionPolicy Bypass -File scripts/uninstall-autostart.ps1  # remove
```

This registers a per-user scheduled task (no admin needed) that runs the panel hidden at every logon and retries every minute if it fails. The port never changes, so the URL stays stable and you can pin it as a browser app. Launching the panel while it is already running just exits quietly. If another program owns the port, the launch fails with a clear message instead of picking a different port.

`install-autostart.ps1 -DryRun` shows what it would register without registering it, and `uninstall-autostart.ps1 -DryRun` says what it would remove without removing it. The installer needs a real `node.exe` on PATH (not an npm, volta or fnm `.cmd`/`.ps1` shim).

All four scripts that register or remove a task (`install-autostart`, `uninstall-autostart`, `install-tray`, `uninstall-tray`) refuse to run, even with `-DryRun`, from a copy that lives inside the OS temp folder: they print `... refused: this copy lives inside the OS temp folder (<folder>); install from the real repository folder.` to stderr and exit with code 2. The tasks are per-user and global to the machine, so a throwaway copy (a test, a worker) that registered one would silently overwrite the real task with paths into a folder that is about to disappear.

### Restart after an update

The page files are read from disk on every request, but the server code is loaded only when the process starts. After `git pull` (or any update of the panel) the server must be restarted, or the page will talk to old code and show the red out-of-date banner.

The autostart task is called `repo-panel` (it runs `conhost.exe --headless node server.js`). `Stop-ScheduledTask` alone does **not** stop the Node process: it stays alive holding the port, and a new start exits silently with "repo-panel is already running". Restart by ending the process that listens on the port and then starting the task:

```powershell
Get-NetTCPConnection -LocalPort 4310 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }; Start-ScheduledTask -TaskName repo-panel
```

Use the `port` from `config.json` if you changed it. To check: open `/health`, it must show the current `api`, and the red banner must disappear after reloading the page.

#### Tray icon (Windows)

To avoid doing that by hand, `scripts/tray.ps1` puts an icon in the notification area (next to Docker and the like). It is a hidden PowerShell script (Windows PowerShell 5.1 or PowerShell 7, no dependencies). The task starts it through `conhost.exe --headless`, like the panel task, so there is no console window at all: with a plain hidden `powershell.exe`, closing its console window killed the icon (task result `0xC000013A`). A task installed before this change keeps the old command; run `install-tray.ps1` again from the real repository folder to switch.

```powershell
.\scripts\install-tray.ps1      # registers the per-user task repo-panel-tray at logon (no admin)
Start-ScheduledTask -TaskName repo-panel-tray   # start it now, without logging out
.\scripts\uninstall-tray.ps1    # removes the task (close a running tray with its "Quit tray" item)
```

`install-tray.ps1 -DryRun` (and `uninstall-tray.ps1 -DryRun`) only print what they would do. You can also run `powershell -File scripts\tray.ps1` by hand; a second launch exits quietly (one tray at a time). The port is read from `config.json` (or `REPO_PANEL_CONFIG`, or `-ConfigPath`), default 4310; an unreadable config uses the default.

- The icon is green when `http://127.0.0.1:<port>/health` answers `repo-panel`, gray when it does not (checked every 5 seconds); the tooltip says `repo-panel: running (port N)` or `repo-panel: stopped`.
- Right-click menu: **Open panel** (also the double-click), **Restart panel**, **Start panel** (enabled only when stopped) and **Quit tray** (the panel keeps running).
- **Restart panel** ends only the processes listening on the port whose command line runs this repo's `server.js` (a path inside this folder, or the `node server.js` form of the autostart task that also answers `/health` as `repo-panel`). If something else holds the port it ends nothing and says so. Then it runs the `repo-panel` task, or, if that task does not exist, `conhost.exe --headless node server.js` in this folder, waits up to 15 seconds for `/health` and reports the result in a balloon tip.
- It only talks to `127.0.0.1`. Errors show as a balloon tip; the tray keeps running.
- `scripts\tray.ps1 -SelfTest` prints the facts the menu uses (port, health, listeners, owned listeners, task) as one JSON line and opens no window; `-SelfTestRestart` runs the end-and-relaunch logic and refuses unless `REPO_PANEL_CONFIG` is inside the temp folder. The tests use these two modes.
- Windows only. Not verified by the tests (they cannot see the desktop): that the icon is visible, its colors, the right-click menu, the balloon tips, and clicking **Open panel** / **Restart panel** in the real menu. If the tray process is killed (not quit), Windows may keep a ghost icon until the mouse passes over it.

## Configuration

On first run there is nothing to configure: click **+ Repo** to add a single folder, or to scan a parent folder for every repo inside it. The panel saves your choices to `config.json`, which is git-ignored so your local paths are never committed.

You can also create `config.json` by hand; copy `config.example.json` as a starting point:

| Key | Meaning | Default |
| --- | --- | --- |
| `port` | Port to listen on | `4310` |
| `priority` | Optional list of repo names (e.g. `["repo-panel", "api"]`) that go first in the "Go work on" strip, in that order; case-insensitive, unknown names ignored | none |
| `dismissed` | Optional list of repo ids whose "requirements missing" warning is hidden; written by the panel (`POST /api/dismiss` `{ id, on }`), invalid entries and duplicates ignored | none |
| `sessions` | Optional map of the session the panel adopted, `{ "<repoId>" or "room:<name>": { "id", "name", "adoptedAt" } }`; written by `POST /api/sessions/adopt` and `/start`, cleared by `/release`; entries with an invalid id (only `A-Za-z0-9._-`, 1 to 80 characters) are ignored | none |
| `rooms` | Optional list of rooms, `[{ "name", "path", "repos": [repoId] }]`; written by the panel's **+ Room** screen and the card menu, or by hand (see Rooms) | none |
| `groups` | Named groups of repos (`{ "name", "repos": [{ "path", "base", "roadmap" }] }`); `base` and `roadmap` are optional | `[]` |

`POST /api/queue` takes the per-repo facts from the browser (it does not rerun any git or gh command) and orders them: repos in `priority` first, then merge, branch, deliver and start, keeping board order within each kind. `POST /api/conformity` takes each repo's roadmap availability and problems and returns the repos that do not conform.

### Requirements

`requirements.json` is `{ "version", "blocks", "requirements": [{ "id", "title", "category", "level", "check", "remedy" }] }`. `blocks` holds the version each Orquestación block must have (`<!-- orquestacion:NAME vX.Y -->` ... `<!-- /orquestacion:NAME -->`). The checks are pure functions in `checks.js`; the server reads the files from `origin/<base>` (`AGENTS.md`, the roadmap, `docs/ORQUESTACION.md`) and `checks.js` decides.

**Changing the text of a block means bumping its version.** The panel marks a repo `outdated` only when the version in its `AGENTS.md` differs from the one in `blocks`, so an edit to `requirements/blocks/*.md` without a bump leaves every repo on the old rule with no warning. To change a block: edit its text, raise the version in its opening marker and in `blocks` of `requirements.json`, then refresh `requirements/blocks.lock.json` with `UPDATE_BLOCK_LOCK=1 node --test test/rp36-block-versions.test.js`. That file records the version and a hash of each block's text; `test/rp36-block-versions.test.js` fails when the text changed and the version did not, and when the lock is stale. The refresh itself REFUSES a text change under the same version (otherwise refreshing would defeat the guard); `UPDATE_BLOCK_LOCK=force` accepts it and is only for a block nobody has installed yet. Repos with the old version then show the requirement as `outdated` and "Put in conditions" reapplies only that block.

**The padrón is the version of the whole set of rules.** `padron` in `requirements.json` (and in the title of `requirements/INSTALL.md`, which the test keeps equal) covers the procedure the agent follows, not only the blocks. The order sent to the agent cites it (`for repo-panel (padrón X.Y)`), each repo records it in `docs/ORQUESTACION.md` with the line `- **Padrón del panel:** X.Y`, and the required requirement `padron-record` compares the two. So when the procedure changes without any block changing, raise `padron` (the same lock hashes `INSTALL.md` and `requirements/EXAMPLES.md`) and every repo shows `padron-record` as `outdated`. The worked examples in `requirements/EXAMPLES.md` are run by `test/rp41-standard.test.js` against the panel's own validator, so they cannot drift from what it accepts.

- Categories: `verificable` (the panel decides and can show it as passing), `parcial` (shows evidence, a person confirms) and `criterio` (never passing, only a reminder). Only `verificable` requirements can pass; a repo is `ready` only when every `required` one passes. `recommended` ones never affect `ready`.
- Result status: `pass`, `fail`, `outdated` (the block has another version, or is the old unversioned section), `unavailable` (could not be read: no repo, no base branch, missing file, or an unknown check type). Unavailable is never shown as passing or as failing.
- The old unversioned `## Orquestación` section (or the `orquestacion:bloque` marker) counts as an outdated `registro` block that asks to be updated, not as a missing one.
- The agent's instructions live in the panel folder, not in another project: `requirements/INSTALL.md` (the procedure: apply only the ids named in the order, never delete rules, stop and ask the user on a conflict with the repo's `AGENTS.md`, work on a task branch, never commit, push or open PRs) and `requirements/blocks/registro.md`, `requirements/blocks/ciclo.md` and `requirements/blocks/estado.md` (the exact text of the versioned blocks). Each `remedy` points at them. The roadmap table is the exception: the block does not define it, so `INSTALL.md` step 7 and the `roadmap-file` and `roadmap-table` remedies spell out its exact column names (`ID`, `Entrega`, `Depende de`, `Estado`; optional `Resultado visible`, `Notas`, `Ficha`), the same list the validator requires (`lib.RM_REQUIRED`). **One mechanism to create and manage tasks.** The `tareas` block (`requirements/blocks/tareas.md`, in Spanish, a required requirement installed into each repo's `AGENTS.md`) states it: every task is a row of `docs/ROADMAP.md`, created `Pendiente`, taken with `siguiente`, closed in the same diff, and nothing parallel is allowed. Step 7 of `INSTALL.md` tells the agent to migrate whatever other task system a repo has (`planning/`, a roadmap elsewhere, task lists kept in files) into that table, keeping the old files as fichas; to remove from `AGENTS.md` the instructions about how to create or manage tasks and the repo's own rules about branches, commits and pull requests (the panel's `/flow-base`, `/flow-commit` and `/flow-pr` decide those; the lines saying what a production, release or hotfix branch is for stay) and to list what it removed; never to invent dependencies (a task without one gets `—`); and to stop and ask only when a task's ID or state cannot be derived. With no tasks it writes only the row `U0`. A checklist kept inside each change (OpenSpec `tasks.md`, fichas) is not a task list: it stays where it is as history, and only what is still pending is imported, as ONE row per change that says `sin verificar` (the agent cannot tell from the code whether pending work is done: an audit can reopen a step on purpose and a gate is a decision). When a row marked `sin verificar` is taken, the `tareas` block tells the agent to verify it first, with evidence (merged PRs, commits, passing tests, receipts) and the person's OK; it never marks `Completada` by itself, because a wrong `Completada` hides work and unblocks other rows by mistake. The panel never edits another repo: the agent does, and the user delivers it with `/flow-commit` and `/flow-pr`.
- Two more requirements belong to the agent state (see Agent state); `estado-block` is `recommended` (it never changes `ready`) and `panel-ignored` is `required` since padrón 1.3, because every repo ignores `.panel/`: `estado-block` (AGENTS.md on the base branch has a closed `<!-- panel:estado v1.0 -->` ... `<!-- /panel:estado -->` block; the check declares its marker namespace, `"namespace": "panel"`, and the Orquestación blocks keep the default) and `panel-ignored` (Git ignores `.panel/state.json` in the repo's **working tree**: it runs `git check-ignore -q .panel/state.json` there, so it is a local fact, not read from the base branch; exit 0 is `pass`, 1 is `fail`, anything else, such as a missing folder, is `unavailable`). `panel-ignored` does not apply to rooms. Its remedy appends `.panel/` to `.git/info/exclude` (never `.gitignore`, never committed), so there is nothing to deliver with `/flow-commit`.
- A file that cannot be read from the base branch for any reason other than "not on that ref" is reported as `unavailable` (reason `error`), is not cached, and is never counted as failing or passing.
- `GET /api/requirements?id=<repoId>` returns `{ available, base, results, summary }`; `GET /api/prerequisites` returns `{ items: [{ id, ok, detail }] }` for `git`, `gh` and `orca` (a missing tool is `ok: false`, not an error).
- The Conformity tab says "All repositories conform." only when the roadmap report is empty **and** the requirements of every repo and the prerequisites were loaded and every repo is `ready`. While they load it says it is computing; if they fail to load it says so.

### Agent state

Work is often unfinished while the repo already shows changes (the agent is waiting for a decision), and after switching sessions it is easy to forget what to do next. So each agent session declares its state in a small file that the panel reads, and ends its replies with one clear line.

- **File**: `.panel/state.json` in the repo's working tree, ignored with `.git/info/exclude` (see `panel-ignored`), never committed. `{ "state", "next", "detail", "at" }`: `state` is `working` (still in progress), `needs-input` (waits for a decision of yours), `ready-to-commit` (done and verified), `ready-to-pr` (committed, ready for a pull request) or `blocked` (cannot continue; `detail` says why); `next` is one line saying what you should do now; `detail` is optional longer text; `at` is an ISO 8601 date-time.
- **The `estado` block** (`requirements/blocks/estado.md`, in Spanish like the other blocks, installed into the repo's `AGENTS.md` by "Put in conditions") tells the agent to rewrite the file after every action that writes files or needs a decision, and to end its reply with one line `Siguiente: <next>`.
- **Reader**: `GET /api/state?id=<repoId>` (token required, 404 for an unknown id) returns `{ available, state, next, detail, at, stale, reason }`. `available: false` has a `reason`: `missing` (no file), `invalid` (unparsable JSON, not an object, unknown `state`, `next` not a string or over 300 characters, `detail` over 4000, `at` not an ISO date-time or more than 5 minutes in the future), `unsafe` (`.panel` or the file is a symlink or link, not a regular file, or over 64 KB; checked with `lstat` before reading and never followed) or `error` (any other read failure). It never throws. An empty or whitespace-only `next` is `invalid`, and `next` is trimmed. `GET /api/local` only gains the additive fields listed under Delivering.
- **Stale**: `stale` is true when `at` is older (whole seconds) than the repo's last activity: the newest of the local `HEAD` commit date and the modification time of each changed or untracked file (the state file itself excluded, at most 200 files). A stale state is returned but flagged. If Git cannot say, it is not flagged.
- **Card**: with a valid, fresh state the card shows its `next` line (one line, full text, `detail` and `at` in the tooltip) with a dot: working yellow, needs-input blue, ready-to-commit and ready-to-pr green, blocked red. A stale state shows only a small gray "outdated" marker, never the old text. The `/flow-commit` button of a card with changes is hidden unless there is no usable state or the usable state is `ready-to-commit`, or you chose **Show /flow-commit anyway** (below); the server-side checks of the button (one idle session, lock) are unchanged. The line is only shown on cards with changes or unpushed commits.
- **Expiry of `working`**: a declared `working` older than 30 minutes (by its own `at`) counts as expired: the card shows only the gray "outdated" marker and the commit button is usable again, because an agent that crashed would otherwise hide it forever. `needs-input`, `blocked` and `ready-to-pr` never expire by time.
- **Show /flow-commit anyway**: when a declared state hides the commit button, the card's **⋯** menu offers this item. It brings the button back for that repo until the page is reloaded (kept in the page, never persisted). A merged branch with changes never shows it: that card offers `/flow-base --stash` instead of `/flow-commit`. The red stale mark names the real button in its tooltip (`/flow-base`, or `/flow-base --stash` with the uncommitted changes it carries).
- **A missing, invalid, unsafe, failed or stale state never blocks anything**: the panel behaves as before. The state can only hide the commit button.
- **Not verified**: the panel cannot tell whether an agent follows the block and writes the file (a model may skip it or write a wrong time, which makes its state look stale); and the line and dots were only checked with unit tests of the helpers, not in a browser.

### Delivering: /flow-pr, manual action and the verdict

The Committed column means "clean tree with commits not delivered yet". That alone is not enough to hand the branch to `/flow-pr`, so the card checks more and says when a person has to step in.

- **`GET /api/local`** gains three additive fields and changes nothing else: `head` (full SHA of `HEAD`, `null` for an unborn branch or on any Git error), `inProgress` (`null`, or `merge`, `rebase`, `cherry-pick` or `revert`, detected from the git dir with `git rev-parse --git-path`, so worktrees and submodules work; it never throws) and `base` (the base branch: the configured one, else `origin/HEAD`, else `main`). `API_VERSION` is now 8.
- **/flow-pr button.** A Committed card shows `/flow-pr` only when ALL hold: no changed or untracked file, commits ahead (also on a branch with no upstream), the branch is not the base and not detached, nothing needs manual action, the repo is not flagged stale (`Merged: run /flow-base`) and no `/flow-commit` verdict is running or needs attention. When an open PR from the current branch already exists, the label is **`/flow-pr (update PR)`**, because `/flow-pr` creates the PR or updates the open one. Otherwise there is no button. Committed cards no longer carry `/flow-commit`: with a clean tree there is nothing to commit; the button stays on Changes cards.
- **Needs manual action.** Commits are made only through `/flow-commit`, and PRs through `/flow-pr`. A card shows a red bar "Needs manual action: …", hides both buttons, goes to the top of its column and counts in the ⚠ problems filter (like a stale card) when: there are commits ahead while the current branch IS the base ("Commits on main: move them to a task branch"); HEAD is detached; a merge, rebase, cherry-pick or revert is in progress; or the branch diverged from its upstream (commits both ahead and behind). It does not fire for a clean branch that is only behind, a base branch with nothing ahead, or a task branch with commits ahead. A repo whose local state cannot be read keeps its existing error card.
- **Verdict after /flow-commit.** When a `/flow-commit` is sent from the page, the page remembers `{ at, head, files }` for that repo (in the page only: no history, nothing persisted, lost on reload) and polls the new read-only `GET /api/pi-status?id=<repoId>` on the normal refresh cycle, only for such repos. It answers `{ state }`: `closed`, `idle`, `busy`, `ambiguous` or `unknown`, from `orca terminal list` and a fresh `show` exactly as the room presence (never `send`; an Orca failure is `unknown`, never `closed`; token required; 404 for an unknown repo).
  - **running** ("committing…"): the session is busy; or the session state is unknown or ambiguous and less than 15 minutes passed; or less than 30 seconds passed since sending (an idle prompt right after sending may not have started yet).
  - **ok**: the tree is clean (untracked files included), `HEAD` differs from the one recorded and there are commits ahead. The record is cleared and the card lives in Committed with its `/flow-pr` button. The session being busy still wins, so the verdict waits for it.
  - **attention** (red bar with the reason and a ✕ to dismiss; `/flow-pr` is NOT offered while it shows): the session is idle or closed but N files are still uncommitted, or `HEAD` did not change, or the session closed before a commit, or `HEAD` changed but nothing is left to deliver; or 15 minutes passed with an unknown session and nothing changed.
  - It is judged from Git and the session state, never from terminal text, and the panel does not judge the quality of the commits.
- **In progress for every command (`API_VERSION` 13).** The same record, `{ cmd, at, head, branch, files, ahead }` (a fresh `GET /api/local` is read right before sending), is kept for `/flow-commit`, `/flow-commit --unstage`, `/flow-pr`, `/flow-base` and `/flow-base --stash`; `fix-pr`, `put-in-conditions` and `flow-next` keep only `{ cmd, at }`. The result of every command is judged from Git and the session state, never from terminal text (`flowVerdict` in `public/view.js`; `/flow-commit` keeps its `commitVerdict` above, and `--unstage` also needs an empty index):
  - **`/flow-pr`**: ok when the tree is clean, the branch has an upstream with nothing ahead and an open PR whose head is the current branch exists; attention "No open pull request for <branch> after /flow-pr" when the session is idle or closed after 30 seconds and that is not true.
  - **`/flow-base` and `/flow-base --stash`**: ok when the repo is on the base branch with nothing ahead or behind (the plain variant also clean); attention "Still on <branch> after /flow-base" when the session is idle after 30 seconds and the branch did not change.
  - **`fix-pr` and `put-in-conditions`**: only running while the session is busy; once it is idle the record is dropped with no verdict (a failure answer from the session is a legitimate outcome) and the card refreshes.
  - A closed session while running is attention ("The session closed while the command was running"); an unknown session for more than 15 minutes with nothing changed is attention.
  - While a verdict is **running** the status line says "committing…", "creating pull request…", "updating base branch…", "fixing pull request…" or "putting repo in conditions…" and EVERY flow button of that repo's cards, plus `Merge`, `Re-run failed` and `Fix CI`, is disabled with a tooltip naming the running command. When the session goes from busy to not busy the page refreshes that repo at once (the same refresh as the timer, so the card changes column without waiting) before it judges the result, and an ok record is cleared. An attention bar stays until dismissed (✕).
- **Staged files.** `GET /api/local` gains two additive fields, `stagedCount` (paths with a change in the index, renames included, untracked files never) and `stagedPaths` (those paths, sorted, at most 20), from the same `git status --porcelain=v2` read. `/flow-commit` refuses to start when the index is not empty, so a dirty card with staged files shows a bar ("N files are staged: /flow-commit needs an empty index. The button clears the index (git reset, your changes stay in the working tree) and then continues with the normal commit in the same run.") and offers `/flow-commit --unstage` instead of `/flow-commit`. That option is the flow-skills runtime's explicit one: a mixed reset, only when you press the button.
- **Why it failed.** `GET /api/pi-status?id=<repoId>&tail=1` also returns `tail`: the last up to 6 non-empty lines of the session screen above the prompt bars and the footer (control characters replaced by a space, each line capped at 200 characters, 800 in total; `''` when the screen cannot be read). Without `tail=1` the answer is exactly as before. The page asks for it once per sent command, only when the verdict is attention, and shows it small and muted inside the red bar (escaped, never as HTML; the full text is the tooltip). It is informational: it never decides anything. A failed `/flow-commit` or `/flow-commit --unstage` labels its button `Retry /flow-commit` (or `Retry /flow-commit --unstage` while files are staged).
- **Animated progress (`API_VERSION` 14).** The in-progress line of a card ("committing…", "creating pull request…", "updating base branch…", "fixing pull request…", "putting repo in conditions…") has a pulsing dot and an animated ellipsis, and the line is a polite live region (`role="status"`, `aria-live="polite"`). A pull request whose checks are still running shows the chip `verifying checks · 2 running · 2/4` with the same pulsing dot (the tooltip still lists every check); the chips for passed, failed and no checks are unchanged. It is CSS only, with no timers. Because the page re-renders the board on every draw, each animated element gets an inline negative `animation-delay` from the clock (`animDelay` in `public/view.js`) so the animation does not jump. With `prefers-reduced-motion: reduce` every animation is off and the text stays.
- **A session waiting for your answer (`asking`).** After a command a session can stop at a selection dialog (for example "Review consent"). `lib.piScreenAsk` recognises the family of selection-dialog footers: within the last 14 non-empty lines there is ONE line (at most 140 characters, case-insensitive) holding a key `enter` or `return` next to an action `confirm`, `select`, `submit` or `accept`, an exit key `esc`, `escape` or `ctrl+c`, and `cancel` (for example `Enter confirm  Esc cancel`, or `↑↓ navigate  enter select  escape/ctrl+c cancel` under a dialog such as `Allow guarded git operation?`); text of an old dialog higher up, or anything else, is not asking. Such a terminal IS a session and `asking` wins over idle, busy and typed. `GET /api/pi-status` then answers `{ state: "asking", ask }`, where `ask` (only in this state) is the last up to 12 non-empty lines of the dialog, control characters replaced by a space, 200 characters per line and 900 in all. The card keeps the buttons disabled and shows a static highlighted line "waiting for your answer in the session" (the `ask` text is the tooltip, escaped); it never turns into "Needs attention" because of time, and the repo appears in the "Go work on" strip as "Waiting for you: Answer the question in the session". The panel only shows this notice: it NEVER answers or presses a key in the dialog, and `POST /api/pi` refuses with 409 "The session is waiting for your answer to a question" and sends nothing. Room presence counts an asking session as `busy`.
- **Clicks are never lost.** The page writes a region (the board, the "Go work on" strip, the Conformity tab) only when its HTML changed, and a redraw waits for the release of a held mouse button (at most 1.5 s), so nothing under the pointer is replaced between the press and the release. Before, every read of every repo redrew the whole board about 150 times a minute at rest and a press that spanned a redraw never produced its `click`.
- **The buttons wait for the session.** A repo with uncommitted changes shows `/flow-commit` (and `--unstage`) disabled with «checking the session…» from its first paint until the first answer of `GET /api/pi-status` (success or failure), for at most 20 s (`LIVE_CHECK_MS` in `public/view.js`); then the normal rules apply. The page asks for the live state at once when a repo is first seen dirty and when the tab becomes visible again, and a hidden tab keeps what it knew. «Show /flow-commit anyway» lifts the hold. When you press any `/flow-*` button the repo behaves as if that command were already running (the button disabled, the progress line shown, with the reason «Sending the order to the session») from the click until the answer, however often the card is redrawn; a second click never sends a second order. Checked in a headless Edge against a scratch server with a fake `orca`, never against a real session showing a dialog.
- **Case recorder (passive).** The panel does not recognise every question a session can ask (a dialog whose footer is outside the family above), so the card can look busy. While that is not fixed, whenever a terminal it looks at shows a question-like screen (a footer line with a key and an action word, `Agents N waiting`, or `asked:` in the last 14 non-empty lines) the server appends ONE JSON line to `.panel/casos-preguntas.jsonl` (git-ignored): `{ at, folder, handle, state, recognized, signals, lines, screen }`, where `recognized` says whether `lib.piScreenAsk` already handled it and `screen` is the whole screen (the last 40 non-empty lines, `lib.piScreenTail`), so a long list of options can be studied. The same question is written once per terminal (the screen is part of the key, so the same last lines under a different list count as a new case; digits such as timers are ignored; it is written again after the screen left the question) and at most once every 30 s per terminal; at 1 MiB it stops and says so once on the console. It only observes: it never answers or presses a key, and the answers of `/api/pi-status`, `POST /api/pi` and the room dots do not change. `REPO_PANEL_CASES_FILE` points it to another file; an empty value or `off` disables it. Lines are sanitized (control characters replaced by a space, 200 characters per line, the last 14 lines), but screen text can include commands or paths, so the file stays local: do not share it unreviewed. Only `server.js` started as the program installs the recorder; importing a module or running `npm test` never does. The server also watches the sessions of every repo and room by itself every 60 s (about 5 s after it starts), so the page does not need to be open and a clean repo is covered too; it runs only while the recorder is on (so `REPO_PANEL_CASES_FILE=off` disables it as well), it does one `orca terminal list` plus one `orca terminal show` per terminal of each repo, nothing else, and `REPO_PANEL_WATCH_MS` (milliseconds, at least 10000) changes the interval while `0`, `off` or an invalid value turn the watcher off.
- **Live cache and warmer.** The read-only readers (the status of a repo, the summary and the sessions panel) keep each terminal's last read in memory and reuse it while the terminal's `lastOutputAt` in `orca terminal list` has not changed and the read is under 30 s old; a failed read and a question on screen are always read again, and anything that writes (sending a command, answering a question, the chat) always reads fresh. To keep that cache warm the server lists Orca and reads every repo and room every 3 s by itself (read-only, started only when `server.js` runs as the program); `REPO_PANEL_WARM_MS` (milliseconds, at least 1000) changes the interval while `0`, `off` or an invalid value turn the warmer off. Read-only status calls also share one terminal list for a second. `GET /api/perf` also reports `liveCache: { hits, misses, size, listHits, listMisses }`.
- **Event stream.** `GET /api/events` is a long-lived Server-Sent Events stream of the live state of every repo's session, so the page does not have to ask. It needs the token in the `x-token` header (never in the URL) and the panel's own host; at most 8 clients are served at once (the next one gets a 503). A new client first gets a `snapshot` with the last state of every repo, then a `live` event whenever one changes, and a heartbeat comment every 15 s. While at least one client listens the warmer reads every second instead of every 3 s. The page keeps its normal polling as a slow safety net while the stream is open (60 s for the live state, 30 s for the open chat) and exactly as before when it is not, so an old server or a refused stream changes nothing for the person.
- **Message history (RP83).** In the message box of the chat, **↑** brings back the last message you sent to that session, another ↑ the one before, and so on; **↓** walks forward and, past the newest, gives back what you were typing. The arrows only act on the first line (↑) or the last line (↓) of the box, with no selection and no Shift, Ctrl, Alt or Meta, so editing a multi-line message works as always; typing in a recalled text, sending, or opening another repo ends the browsing. The history is the `user` messages of the chat plus the ones still pending, without empty entries or repeats in a row, one per repo, and it lives in the page only (nothing is stored or sent).
- **Free text to the adopted session (`POST /api/chat/send` `{ id, text }`, `POST /api/chat/clear` `{ id }`; token required).** The server cleans the text (CR/CRLF become LF; every control character except LF and TAB is removed: ESC, NUL, DEL, C1, U+2028/2029 and the bidi and zero-width controls, so a typed `ESC[201~` becomes plain text), trims it and refuses with 400 when it is empty, longer than 4000 characters (never truncated) or starts with `!` (pi runs those as shell commands). It sends ONE `orca terminal send --text=<text> --enter` (the `--text=` form, so a message that starts with `--` is never read as an Orca option) only when the repo has an adopted session (409 otherwise; room keys answer 400 for now), exactly one live session whose prompt is idle (no asking dialog, nothing typed, not busy), and, when the adopted session has a name, that name shows as ` • <name>` at the end of a footer line BELOW the prompt bars (a line of the conversation above them does not count). One send per repo at a time (the same guard as the command buttons, so a command and a message never go out together), and the same text is not accepted twice to the same repo within 5 s (the panel remembers at most 50 recent texts). It never uses `--interrupt` and never resends. Delivery is verified by polling the adopted session's history for up to 15 s: the answer is `{ sent, delivered, leftInBox }`, where `leftInBox` means the text is still typed in the prompt (the panel never resends it). `delivered: false` means "could not confirm", NOT "not sent": the history window is the last 64 KB and 100 items, and a text with unusual characters may be stored differently (both sides are compared in the same Unicode form, NFC). `clear` sends one Ctrl+U (no Enter) only while text is typed and answers `{ cleared }`. The chat has a composer (Enter sends, Shift+Enter adds a new line) that is enabled only when the adopted session is free; a message is never resent (an error keeps your text, and text left in the prompt box offers **Clear the box**), and (RP85) the bar of the box shows, as direct buttons, the flow command that can run now (`/flow-next`, `/flow-commit`, `/flow-pr` or `/flow-base`, the same one the card offers; the tooltip says why), disabled while an order of that repo is on its way; when none can run nothing is shown, and the session state above the box says why. The old **/ Actions** menu is gone.

### When each flow button appears

One rule set (`flowButtons` in `public/view.js`) decides the buttons of a repo's local card; the page and the tests share it. The column comes from Git state alone.

| State of the repo | Column | Button |
| --- | --- | --- |
| Changed or untracked files | Changes | `/flow-commit` (hidden while a declared state says the work is not ready, see "Show /flow-commit anyway") |
| Changed files with a non-empty index (staged files) | Changes | `/flow-commit --unstage` instead of `/flow-commit`, with the staging bar |
| A `/flow-commit` or `/flow-commit --unstage` failed (attention) | Changes or Committed | `Retry /flow-commit` (or `Retry /flow-commit --unstage` while files are staged), with the reason and what the session said |
| Clean, commits ahead, no open PR for the branch | Committed | `/flow-pr` |
| Clean, commits ahead, an open PR from this branch | Committed | `/flow-pr (update PR)` |
| Branch already merged (or its remote branch deleted), clean tree | Merged (red mark) | `/flow-base`: starts from a fresh, updated base branch |
| Branch already merged, but files changed | Changes (red mark) | `/flow-base --stash` and no `/flow-commit`: the skill carries the uncommitted changes aside (stash, including untracked files), switches to the fresh base branch, updates it and restores them. It refuses and changes nothing when the work of the branch is not yet merged or its remote branch not yet deleted |
| Needs manual action (detached HEAD, commits on the base branch, merge or rebase in progress, diverged) | Wherever Git puts it | none |
| A `/flow-commit` is running | Changes or Committed | no `/flow-pr` and no `/flow-base` until it settles |
| Any command sent from the page is running (`/flow-commit`, `/flow-commit --unstage`, `/flow-pr`, `/flow-base`, `/flow-base --stash`, `fix-pr`, `put-in-conditions`) | Wherever Git puts it | the same buttons, disabled with a tooltip naming the running command, and `Merge`, `Re-run failed` and `Fix CI` of that repo disabled too; the status line says what is running |
| Open PR, checks failed | Pull requests (red) | `Fix CI` (any fix, in test or production code or configuration, as long as it serves the PR's own objective; for a transient failure it does not touch code and recommends `Re-run failed`; if the fix would change the PR's scope or needs a product decision it stops and asks), plus `Re-run failed` when a GitHub Actions run failed |
| Open PR, all checks passed and mergeable | Pull requests (first, green accent) | `Merge` |

**How a card returns after a fix.** `Fix CI` types one order into the open session (see below). The agent edits files and commits nothing, so the repo is dirty and its card moves to **Changes** with `/flow-commit`. After `/flow-commit` the repo is ahead and the card moves to **Committed**, where an open PR from the branch already exists, so the button reads `/flow-pr (update PR)`. `/flow-pr` pushes the fix to the same PR and its card goes back to **Pull requests** while the checks run. Nothing in the panel tracks this: each step is just the new Git state.

### Rooms

A room is a repo (a folder with its own `origin`) where you coordinate a group of repos (for example one room for your H2O projects and another for your tools). Repos do not declare which room they belong to, so the panel does, in `config.json`. You do not have to edit it: use the screen.

- **+ Room** (next to **+ Repo**) opens a dialog: a room name and its folder (the field suggests the folders of the repos already in the panel; a browser cannot open a native folder picker, so type or paste the path). Errors show inside the dialog.
- The card's **⋯** menu has an **Assign to room** group: one item per room (the current one is marked ✓) and **No room**. With no rooms it offers **Create a room…**.
- The Conformity tab's **Rooms** section has a **Remove room** button per room, with a confirmation.

By hand, the same data is (remember to escape backslashes in JSON, or use forward slashes):

```json
"rooms": [{ "name": "UPEN", "path": "C:\\Users\\you\\Developer\\upen\\upen-ceo", "repos": ["969522dd0c"] }]
```

`repos` holds repo ids (the `id` that `GET /api/config` shows for each repo). Rules: the name is trimmed, non-empty, at most 60 characters and unique (case-insensitive, the first wins); `path` must be absolute; `repos` keeps unique strings; a repo id belongs to at most one room (the first room wins). Reload the page after editing by hand.

- **Routes** (token required, like the rest): `POST /api/rooms/create` `{ name, path }`, `POST /api/rooms/remove` `{ name }` and `POST /api/rooms/assign` `{ id, room }` (`room` is a room name, or `null` to leave every room). They answer `{ rooms }`. `create` answers 400 with the reason when the name is empty, longer than 60 characters or already used, or when the path is not absolute, does not exist, is not a folder or has no `.git`; `remove` and `assign` answer 404 for an unknown room or repo. `assign` takes the repo out of any other room first, and removing a repo from the panel also takes it out of its room.
- **Removing a room never touches files.** It deletes only the entry in `config.json` (its members become unassigned); the room folder and the repos are never created, edited or deleted by the panel.
- **Entries the panel does not understand are kept.** An entry under `rooms` that is not usable (not an object, a bad or duplicate name, a relative path) is ignored at runtime but written back to `config.json` exactly as it was on every save, in its place, so a typo cannot erase a room. `GET /api/config` lists them in `roomIssues` (short strings such as `rooms[2]: path must be absolute`; `[]` when all is fine) and the Conformity drawer shows "N entries in config.json under rooms are invalid and ignored" with the reasons. Fix the entry in the file by hand. A `rooms` value that is not a list is reported the same way, kept as is, and the panel refuses to create a room until you fix it.

- **Room requirements** (`roomRequirements` in `requirements.json`, evaluated against the room repo's remote base branch, all required): `room-base-branch`, `room-agents-file` (`AGENTS.md`), `room-enlaces-file` (the link map `ENLACES.md` at the root or under `estrategia/`, because the template does not fix the path) and `room-enlaces-sections` (a markdown heading for each of Proyectos, Contratos, Dependencias, Cola and barrido, matched case-insensitively inside the heading text; the detail lists which are missing). It only proves the headings exist, not that they are filled in. The repo that is the folder of a room is judged with these requirements in its card and in Conformity (matching the room path ignoring slashes and case), and it never receives the member order: its card menu does not offer "Put in conditions" and the server refuses it.
- **Member requirements** (a repo listed in a room; in `requirements.json` a requirement can have `"onlyInRoom": true`, omitted for repos outside every room, and `"levelInRoom"`, which replaces its level for members): `sala-region` (required: the `ciclo` block holds both `<!-- SALA -->` and `<!-- /SALA -->`) (since padrón 1.2 `ciclo-block` is required for every repo, so no real requirement uses `levelInRoom` any more; the mechanism stays for a future one). `ready` is unchanged: every required requirement, after that override, must pass. `GET /api/requirements?id=` adds `room: { name }` for a member; for any other repo the answer is the same as before. `requirements/INSTALL.md` tells the agent to keep the SALA region (both marker lines and everything between them) when the repo is a member of a room or when the order names `sala-region`, and to remove it only when neither applies.
- **Active** means: `GET /api/rooms` returns, per room, its requirement results and `presence.state`: `closed` (no pi screen in any terminal of the room folder), `idle`, `busy`, `ambiguous` (two or more pi screens) or `unknown` (Orca could not be asked, or a `show` failed and no pi screen was seen elsewhere; never reported as closed), plus `lastCommit` (ISO date of the room's local `HEAD`, or `null`). Sessions are recognised by their screen (a fresh `orca terminal show` per terminal of the room folder, whatever the terminal title), as for the buttons; a prompt with text typed in it counts as idle. Only `list` and `show` are used, never `send`.
- The Conformity drawer does not say "All repositories conform." while the rooms load, fail to load, or any room has a required requirement that is not passing.
- **Not covered**: that a member repo is listed in `ENLACES.md` (free markdown, it would give false positives) and whether the room is behind (last sweep older than merged PRs). Nothing here edits the room or its members; the agent applies remedies and you deliver them with `/flow-commit` and `/flow-pr`.

`base` is the branch work is merged into. When omitted, the panel reads it from `origin/HEAD` and falls back to `main`. `roadmap` is the repo-relative path of its plan file (default `docs/ROADMAP.md`); unsafe values (absolute, starting with `-`, or containing `..`) are ignored.

### Adopted sessions

The panel keeps ONE adopted session per repo and per room (`sessions` in `config.json`). Sessions are read from Gentle Shell's folder (`~/.gentle-shell/agent/sessions/--<folder>--/<timestamp>_<id>.jsonl`, overridable with `REPO_PANEL_SESSIONS_DIR`); only the first and last 64 KB of a file are read. Routes (token required; `id` is a repo id or `room:<name>`, 404 when unknown):

- `GET /api/sessions?id=` answers `{ key, adopted, adoptedFound, sessions, live }`: `sessions` are the newest 20, `live` is `{ state: none | free | working | waiting | unknown, count }` from one `orca terminal list`; an Orca failure is `unknown`, never `none`.
- `POST /api/sessions/adopt` `{ id, session }` (400 when `session` is not one of the listed ids) and `POST /api/sessions/release` `{ id }`.
- `POST /api/sessions/start` `{ id }` opens a terminal that runs `gentle-shell -n <panel:repo | sala:room> --session-id <panel-slug | sala-slug>` and adopts that id. It answers 409 when the folder already has a live session (adopt it instead) or Orca cannot be listed. It never sends text to a session.
- `GET /api/chat?id=<repoId | room:Name>&session=<optional>&limit=<optional>` is the read-only history of a session, for the chat panel. It reads ONLY the last 64 KB of the session file (the first, possibly partial, line is dropped; a file can be 25 MB) and answers `{ key, sessionId, found, items, truncated, updatedAt }`. `session` defaults to the adopted one; an explicit one must match the id pattern and be one of the listed sessions of the folder (400 otherwise); an unknown key is 404; with no adopted session and none given the answer is `sessionId: null, found: false, items: []`. `items` are oldest first, at most `limit` (default 30, maximum 100): `{ role: "user" | "assistant", text, at, tools }`. Only text goes out: the thinking blocks, the tool arguments and the tool results are never included, a tool is only its NAME, and tool-only assistant messages are folded into the `tools` of the next assistant item with text (a trailing run becomes a final item with empty text, the session is still working). Text is capped at 4000 characters per item (with `…`) and control characters other than line feed and tab become spaces (CR and CRLF become LF, the blocks of one message are joined with a blank line, so line breaks are kept). `truncated` is true when older messages exist beyond the 64 KB window or the `limit`; `found` is false when the file does not exist; a corrupt line is skipped. The route never talks to Orca and never writes anything.

### Claude usage bar

The header shows how much of your Claude limits you have used (RP96): two compact meters, **5h** and **7d** (the 5-hour and the 7-day window; there is no monthly or per-model figure in the data), each with a fill bar, the percent used and a countdown to its reset (`2h 29m`, `4d 14h`). A thin **pace mark** on each bar shows how much of the window has already run: if the fill is past the mark you are using it faster than the clock. Gray is normal, yellow is 70% or more and red 90% or more, and those two also carry a `⚠`, so the warning never depends on colour alone. A dash (`5h –`) means that window already reset or was not reported. A dimmed bar with `20 min ago` means the data is old: the file was last updated 15 minutes ago or more. `Claude usage: no data` means there is no usable file yet. Hover it, click it or focus it with the keyboard to open a popover with each window's wide bar, `N% used`, `Resets in …`, the exact reset time, how much of the window has run, a written warning when it runs ahead of the clock, and how old the data is; Esc closes it. On a narrow header only the percents stay. It only reads `GET /api/usage`: nothing about that route or the extension changed.

The data comes from a small file that an extension of the agent writes (`~/.gentle-shell/agent/claude-usage.json`); set `REPO_PANEL_USAGE_FILE` to read another path. The panel only reads it, on every request, through `GET /api/usage` (answer: `available`, `five`, `seven`, `updatedAt`, `stale`). The page asks every 30 seconds while the tab is visible. Sessions that were already open must be restarted to load that extension, or they never write the file.

## Responsiveness

- **Interactive lane.** What the person does is served first: every POST (except the read-only `POST /api/queue` and `POST /api/conformity`) and any GET sent with `x-priority: user` (the page sends it when a card's chat is opened). Such a request may use up to 2 child processes over the cap and goes before waiting automatic refresh work. The periodic refresh stays in the background lane.
- **`REPO_PANEL_MAX_PARALLEL`.** Caps the child processes (git, gh, Orca) the panel runs at once, so a refresh of many repositories does not starve the machine. A positive integer; default 8 (absent, invalid, 0 or negative values fall back to it).
- **`GET /api/perf`** (needs the token, does not record itself). Answers `{ routes, queue }`. Per route, over its last 200 requests: `n`, `p50`, `p95` and `max` in ms, `waitP50` (median wait for a process slot), `procsAvg` (processes per request), `executions` (handler runs; identical concurrent GETs share one) and `priorities` (counts of `user` and `background`). `queue` is `{ active, max, waitingBackground, waitingUser }`.
- **Server-Timing.** Every JSON answer carries `Server-Timing: total;dur=<ms>` and, when the request waited for a slot, `queue;dur=<ms>`.
- **Slow log.** A request of 1500 ms or more prints one console line (route, ms, queue wait, process count) at most once per route every 10 s. Nothing else of the request is logged.
- **Summary store (RP78).** `GET /api/summary` no longer builds the board per request: the server keeps every repo's facts in memory (`server/summarystore.js`) and answers a snapshot at once, with no Orca, Git or `gh` call. Each fact has its own age: the local state and the repo state are read every 15 s, the pull requests, the roadmap and the last commit every 60 s, a pool of 3 repos at a time, in the background lane; a read that does not answer in 90 s counts as failed. A session state that the live warmer has not refreshed for 30 s is shown as unknown. Nothing is read until a page asks for the first time (no client, no work), so a server started only for a request stays passive. The session state is never read by the store: the live warmer feeds it (until its first answer a session is `unknown`). A repo whose facts were not all read yet is a `loading` row (a calm "Loading…" card with no action, counted as idle, sorted last); a failed read keeps the last good value and the row carries `stale: { facts }`, shown as a small "Updating…" marker (also set when a fact is older than 3 times its interval). A fact that never succeeded gives the usual error row. `?fresh=1` reads every fact of every repo again before answering. When nobody asked for the Summary for 60 s the loop slows down to 30 s and 300 s, and a request speeds it up again. `server.js` starts the loop; creating a server does not. Hot repos (the current branch has an open pull request) re-read their pull requests every 15 s and their local state every 10 s while a page is active, and after a merge, re-run, fetch, a command to the session or a chat message the server re-reads that repo at once and once more 5 s later.
- **Board from memory (RP80).** `GET /api/board?since=N` answers at once, from the Summary store's memory and with no Orca, Git or `gh` call, `{ rev, repos, refreshing }`: the repos whose facts changed after revision `N` (all of them for `0`; `400` for a `since` that is not an integer >= 0, `404` without a store). Each repo carries its `rev`, the last-success time `at` of each fact, `errors`, `stale` and the values `local`, `prs`, `roadmap`, `state` and the new sixth fact `req` (the requirements, read every 60 s like the pull requests and never part of the Summary). `POST /api/board/refresh` answers `{ started: true }` at once and re-reads everything (or only `{ id }`) in the background. F5 and Refresh paint from that memory immediately and re-read in the background, with the Refresh button busy while the server reports repos in `refreshing`; after a command sent from the page ends, or a fetch or merge, the page asks the server to catch up that repo and its own direct reads win over an older board fact. A server restart (a lower `rev`) is followed, not ignored. The old per-repo routes are unchanged: if the board answers 404 or fails three times in a row, the page falls back to them and retries the board slowly. `API_VERSION` stays 15.
- **Request timeouts.** The page gives up on a GET after 25 s and on a POST after 70 s ("Request timed out"); the Summary, which builds the whole board, has its own 90 s limit until RP78. Switching or closing the chat card cancels its pending reads.
- **Identical reads are shared.** Two identical GETs in flight run once, per lane: an interactive request never joins a background one that may have waited in the queue.
- **A malformed URL answers 400** (and a wrong Host 403) and never takes the server down.
- **Known limits.** The background lane has no aging: an endless chain of interactive requests would delay it (human clicks never do). With the default limit of 8 the wait of an interactive request for a process slot is about 0 ms, but the Orca program it runs still takes 0.5 to 2 s while a full refresh is running (RP77 reads Orca less).
- **`scripts/measure-panel.js`.** `node scripts/measure-panel.js [--port 4398] [--json]` starts its own temporary panel on its own port (a copy of your config, no browser polling it) and times the Summary, each per-repo route, a full refresh and the wait of an interactive read during it. It only sends GET requests: it never runs an action or sends anything to a session.

## Merge behaviour

- Clicking **Merge** merges immediately, with no confirmation (like GitHub's own button). It is only enabled when the PR is green and mergeable.
- Merging goes through the GitHub API, so your local branches and working tree are never touched.
- The server re-checks readiness right before merging and pins the merge to the PR head SHA, so a late push cancels it.
- *Delete branch* is offered only when the repo does not already delete merged branches (`deleteBranchOnMerge`). If GitHub already removed the branch, that is treated as success, and local branches whose remote disappeared show as "remote branch deleted" instead of an error.
- A repo whose current branch (other than the base) already landed gets a red **Merged: run /flow-base** mark and goes to the top of its column. The panel flags it when the remote branch is gone or a merged PR came from that branch, and not when a new open PR reuses the branch name.
- `GET /api/roadmap?id=<repo>` returns the parsed `docs/ROADMAP.md` read with `git show origin/<base>:<path>`, never from the working tree, so a unit counts as done only once its PR is merged. Run a fetch to see newer data. A repo without the file answers `available: false` (not an error).
- `GET /api/summary` (token required; read-only; `?fresh=1` skips the cache) returns `{ rows, counts, attention, generatedAt }`, one row per configured repo, built only from what the other routes read (`localState`, `prState`, `roadmapState` with its derived states, `readState`, the session screens, `lib.workQueue`). A row always has every field and a value that is not known is `null`, never invented: `{ id, name, group, room, branch, progress: { total, completada, enRevision, bloqueada, pendiente, enCurso }, session: { state }, next: { id, entrega, resultadoVisible } | null, blocking: [{ unit, waitsFor, external }], lastMovement: { at, what }, action: { kind, label, pr } | null, error, needs, rank }`. `needs` is true when the repo is in `attention` (an asking session, a PR with failing checks, or a `Bloqueada` unit only when the repo has no takeable next unit; false for error rows) and `rank` is its urgency, lower is more urgent, from one definition in `server/summary.js` that reuses `lib.QUEUE_RANK`: 0 a session asking you, 1 failing CI, then the "Go work on" kinds in their own order (2 `merge`, 3 `branch` and `manual`, 4 `waiting`, 5 `deliver`, 6 `start`), 7 a working session, 8 a blocked repo, 9 everything else and error rows. `progress` counts each roadmap row once: `enRevision` and `enCurso` come from the derived states (not the hand-written column) and a derived `Lista` row stays in `pendiente`; the values are `null` when the repo has no readable roadmap. `session.state` maps the session: `none` (closed), `free` (idle), `working` (busy), `waiting` (asking a question) and `unknown` (ambiguous or unknown, including every repo when Orca cannot be listed, never `none`). `blocking` has at most 3 entries: the `Bloqueada` rows (`waitsFor` their table dependencies, `external` the dependencies that are not rows) and, when no unit can be taken, the first `Pendiente` row with its unmet dependencies. `lastMovement` is the date and subject of the local `HEAD` commit (both `null` when Git cannot say). `action` is the first entry of the "Go work on" queue for that repo (`merge`, `branch`, `manual`, `waiting`, `deliver` or `start`; `pr` only for `merge`), except that a session in `waiting` gives `{ kind: "answer", label: "Answer the question in the session" }`; it is `null` when there is nothing to do. `counts` classifies each repo once (`waiting`, `working`, `blocked` by `blocking`, otherwise `idle`; error rows are not counted) and `attention` lists the repos with an asking session, a PR with failing checks or a blocked unit with no takeable next unit, with a `why`. A repo with a `Bloqueada` unit AND a next unit it can take does not need attention (`blocking`, `counts.blocked` and `rank` do not change). **A repo whose Git or `gh` read fails gets a row with `error` set and nulls; the others are unaffected.** `orca terminal list` runs once for all repos (plus one `show` per terminal of each repo), repos are read six at a time, and the whole response is cached for 10 seconds. Nothing is sent to Orca. `API_VERSION` does not change.
- Branch protection and required reviews on GitHub still apply.

### Summary tab and scope

The page opens on a **Summary** tab (built by `public/resumen.js` from `GET /api/summary`); the Kanban board is the **Work** tab, unchanged, and **Conformity** is a full-width tab (RP60). The page has three fixed levels: the global bar (title, Refresh, Fetch all, + Room, + Repo and the **⚙ Merge** menu), the tab bar, and a view bar right below the tabs. The **⚙ Merge** menu holds the merge method and *delete branch*, used by the Merge buttons of Summary and Work; it closes with Escape or a click outside. On the left of the view bar are the shared controls, identical and in the same place on both tabs: the text filter, the group selector and the scope selector (All, each room with its repo count, No room). They filter the Summary cards and the Work board (and its "Go work on" strip) alike: the name contains the text (case-insensitive), the group equals the selected one, and the scope keeps the repos of that room or of no room. While a text or group filter is active the Summary pins no room cards. Right after the scope buttons, Summary has the *Needs attention · N* toggle (RP82; the age of the data is no longer shown, a failed read still shows the "Summary unavailable" note); on the right end of the view bar Work has *Clean column* and the problems button. The Summary is a list of cards that fit a column of 260 to 480 px (RP88): the list is a named container (`cards`), so the layout follows the width of the cards and not of the window. By default the card is stacked (the name with the session chip, the branch and the time of the last movement, the change chips on their own wrapping line, the progress bar with the next unit, and the action button at the full width); up to 320 px the time of the last movement is dropped; from 640 px it is the horizontal two-line card described next. The frame of that card, and of the board card in Work, is one function, `RepoCard(model, mode)` in `view.js` (RP88b): the card element, the branch line, the chips block and the order of the parts; what differs on purpose (the identity, the notices, the buttons) is passed in as ready HTML. The clean row of a repo with nothing to do is the same function in `compact` mode (RP88c). The cards show less (RP94, part a): no count next to the bars (the title and the aria-label of a bar still say how many are completed), no "↓ N behind" chip and no "no GitHub remote" chip; the clean row keeps its own "↓N". Line 1: the repo name, the branch, the change chips (`● N files +A −D`, which opens the same diff drawer as the board, `↑ N unpushed` with `· no upstream` when it applies, `↓ N behind`; none when the repo is clean or its local state is not loaded), the time of the last movement and the session state (icon and word). Line 2: a segmented progress bar with a short count (`30/74`; the full breakdown is in the `title` and the `aria-label`), the next unit on ONE ellipsis line (`Next · B2b — ...`, or `Waiting · T004 → T003` for a blocked repo with no next unit; the full text and the visible result are in the `title`) and ONE main button that reuses the board's own actions (`merge`, `/flow-base`, or the `/flow-commit`/`/flow-pr` button the card would show; disabled until the repo's local state is loaded). A card has a yellow left border when its session is asking you and a red one when the repo is blocked with no next unit. The order is stable and never depends on the state: room cards first (configuration order), then the repos in the order of the configuration, grouped by group; when more than one group is visible each group has a header button that collapses its cards (kept in memory only, not saved). A room card is pinned and not clickable yet: `★ name`, a "room" chip, the room session (idle is free, busy is working, closed is no session, anything else unknown), the aggregate bar of its member repos, "N projects · M need attention" and the time of its last commit; it shows in All (every room) and in its own scope, never in No room, and not while the room data has not loaded. The only Summary filter is ONE toggle button, *Needs attention · N* (N counts the repos that pass the shared filters; `aria-pressed` tells whether it is on; there is no "All" button, press it again to see everything). When on it shows only the rows with `needs` true, without group headers or room cards, ordered by `rank` (ties keep the stable order), so the most urgent is first. `/flow-next` (the primary button when a clean repo has a next unit) types `/flow-next` into the idle session of the repo through the same safeguards as the other keys; the agent then takes the next roadmap task and shows a summary, and the panel does not judge its result. `Open` (a session that asks, waits or needs manual action; the panel never answers a dialog here) only shows that repo in the Work tab. A row whose read failed shows its error and "no data", never zeros. The page reads `/api/summary` with the 60 s refresh and every 20 s while the Summary tab is visible, and (RP86) also within about a second after a repo's local state, PRs, roadmap or declared state CHANGES (grouped into one request, only while the Summary is shown and only once it has loaded; the first value of a fact is start-up, not a change), so a card no longer lags behind the board for up to 20 s after an action of yours; an answer older than one already applied is dropped. The cards of both tabs, the "Go work on" strip and the Files tab read one read model per repo (`V.repoModel`, joined by `modelOf` in `public/app.js`). It redraws only when the payload changed, and keeps the last data (with a small "Summary unavailable" note) when a read fails. No new route: `API_VERSION` stays 15.

**Chat panel (read-only).** Click a repo card (or focus it and press Enter or Space) to open ONE chat at the right of the cards; it follows the card you click, and the open card is marked with `aria-current` and a blue border. Buttons inside a card keep their own action, and the room card does not open it yet. Close it with the ✕ button or Escape (not while a dialog or menu is open). The chat exists only in the Summary tab; Work keeps the board at full width. The divider between cards and chat is dragged with the pointer, moves 24 px with the left and right arrows, and resets with a double click or Enter; the chat never gets narrower than 340 px nor the cards than 360 px, the ratio is saved in `localStorage` (`repo-panel.chatRatio`), the default is 40% of the width (50% under 1100 px), and under 720 px the chat is stacked below the cards without a divider. While it is open (and Summary is visible and the page is not hidden) the panel reads `GET /api/sessions?id=` and, when a session is adopted, `GET /api/chat?id=` every 5 s, and redraws only when the answer changed; a failed read keeps the last data with a small "Chat unavailable" note. States: with no adopted session it lists up to 5 sessions with an **Adopt** button and a **Start panel session** button (the explicit buttons of `POST /api/sessions/adopt` and `/start`; a 409 shows the server's message); an adopted session whose file does not exist yet shows "The session is loading…"; otherwise the messages appear as bubbles (each message is shown with a safe Markdown subset: paragraphs, headings, lists, code blocks, bold, italic and links to http/https; the raw HTML of a message is never inserted, and the message text keeps its line breaks) (you at the right, the session at the left, with the time) and the folded tools as a dashed line `▸ N tools · a, b, c (+k)`. The header shows only the repo name (the session id is just its tooltip) and the close button; the state of the session (free, working with a pulsing dot, asking you something, closed, no session) is shown inside the message box, top left, with the colours of the cards, and the animation stops with `prefers-reduced-motion`. When the live session of the repo is asking a question (and it is the only session open), the chat shows the question as it appears on the screen with the highlighted option marked (`GET /api/sessions` returns it as `live.dialog`) and tells you to answer it in the terminal: the panel sends no key. To build that dialog the server reads the whole rendered screen of an asking session (`orca terminal read --screen`, one read per asking terminal, only when it asks), so the card shows the title and the whole command, and it falls back to the last lines of `show` when that read fails; the case recorder stores that same screen. The read is read-only. **The panel sends no text to any session from the chat in this version**: it is read-only. `API_VERSION` stays 15.

**Chats open at once (RP79).** The page keeps the last 8 chats it read (one per repo, in memory only) and, when you switch card, shows that chat immediately with the state "unknown" while it reads again in the background. The question card and its answer buttons never come from the cache: they appear only with the fresh read. The two reads (`/api/sessions` and `/api/chat`) now run in parallel.

**Actions react at once (optimistic).** A command button makes the card say "working" in the same instant (the server state shows again when the command ends), and a chat message leaves the box and appears as a pending bubble ("You · sending…", then ✓ or "not confirmed") until the history shows it; if the send fails the text comes back to the box. After a merge the Merge button stays disabled ("Merged ✓") until GitHub no longer lists the PR or 90 s have passed, and a merge in flight pauses only the refresh of its own repo. A repo with a command in flight asks for its session state every 3 s, so the end of the command is noticed quickly, and it keeps refreshing its pull requests as before.

**Colours of the action buttons.** Every action button is soft (a light tint, never a solid fill) and its colour tells the effect: blue starts work (`/flow-next`, `+ Repo`), amber hands over your work or asks for your answer (`/flow-commit`, and Open on a card that waits for an answer), green publishes (`/flow-pr`, Merge), violet opens a new cycle (`/flow-base`) and orange fixes (`Fix CI`, formerly `Fix with pi`). Gray buttons are secondary, and a disabled button is always gray and dimmed. Urgency is shown by the card, not by a solid button; only the answer, waiting and `Fix CI` buttons get a slightly stronger tint.

## Computed unit states

The roadmap file only holds `Pendiente`, `En curso`, `Completada` and `Bloqueada`. The panel adds three states computed from Git and GitHub, never written in the file. A unit is linked to work by its ID as a complete token in a branch name or in an open PR title (`p2` matches `p2-header` and `feat/p2_x`, not `p20-x`, `p2.1-x` or `rp3b-x` for `rp3`).

- Precedence per unit: `En revisión` > `Lista` > `En curso` (derived) > the state written in the file. `Completada` and `Bloqueada` units are never overridden.
- `En revisión`: an open PR has the ID in its title or head branch.
- `Lista`: the current branch has the ID and the tree has changes or commits over the base, or another local branch with the ID has commits over `origin/<base>`.
- `En curso` (derived): a local branch with the ID exists, but it has no commits over the base and the tree is clean. A row written as `En curso` in the file creates no derived entry; it is only replaced when it becomes `Lista` or `En revisión`.
- `siguiente` skips every unit that has a derived state.
- A branch merged by squash still counts as not merged for Git, so it can only affect units that are not `Completada`, and it is ignored when its remote branch was deleted.

Known limits and what is not verified:

## Security

The server binds to `127.0.0.1` only, rejects unknown `Host` headers (DNS rebinding), requires a random per-run token on every API call, and only operates on repositories listed in `config.json`.
