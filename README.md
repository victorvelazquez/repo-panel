# Kletus.dev

A local, single-window dashboard for the repos you work on. It answers one question: **what is left for me to do?**

- A kanban board with one card per pending thing, in columns: **Clean · Changes · Committed · Pull requests · Merged**. A repo with local changes and a ready PR shows up in both columns.
- **Pull requests.** Every open PR lives in one **Pull requests** column (green top border): the ones **ready to merge** come first (with a green accent on the left of the card), then the ones that need a fix (red), then the ones whose checks are still running or that wait for review. Inside each group the order is the one GitHub gives.
- **Clean, Merged, Idle and Needs attention.** **Clean** is a column by default, first on the board: the compact rows of repos with nothing to do, plus the cards that need a person (a manual action, a failed `/flow-commit` with a clean tree). Repos whose branch already merged (`Merged: run /flow-base`, clean tree, nothing ahead) have their own purple **Merged** column. If you prefer a quieter board, untick **Clean column** in the header: the rows move to a collapsible **Idle · N repos** bar under the board (closed by default, its state is remembered; not drawn when no repo is idle) and the cards that need a person go to a red **Needs attention** column, leftmost, that exists only while it has cards. Tick it again (or press **Show as column** in the Idle bar) to go back; Merged stays in both layouts.
- **Merge feedback.** After you press **Merge** the button is disabled and reads `Merging…`, then `Merged ✓`, and stays that way until the repo has been refreshed and the card moves away; a failed merge enables it again at once.
- Per repo: uncommitted files, `+/−` lines, unpushed commits, and a full diff viewer.
- Per open PR: CI status and a **Merge** button that only enables when every check is green and GitHub reports the PR as mergeable. PRs with failed checks, conflicts or an outdated branch stay in **Pull requests**, marked red as needing attention (the separate **Needs attention** column is for repos, not PRs).
- Repos organised in groups (personal, work, commercial…), shown as a colored tag on each card, with a group filter and a name search.
- A roadmap block on each repo card (in progress or next unit, progress bar, a problems badge and, on click, the roadmap header). It reads `docs/ROADMAP.md` from the remote base branch, not the working tree; repos without that file look unchanged.
- The states `Lista`, `En revisión` and `En curso` (derived) are computed from Git and GitHub, never written in the file. A unit is linked to a branch or an open PR by its ID inside the branch name or the PR title; those units are skipped when picking the next one (`siguiente`).
- A **Go work on** strip above the board lists the next actions in order: a PR ready to merge, a repo whose branch already merged (`/flow-base`; with uncommitted changes it is only that, never also "Deliver changes"), changes not delivered yet, and a clean repo with a next roadmap unit. Clicking a chip filters the board to that repo. A manual order in `priority` (see Configuration) wins over the automatic one.
- The strip also has two chips for repos that must not be delivered yet: **Manual action** (red) for a repo that needs a person's hands (detached HEAD, commits on the base branch, a merge or rebase in progress, a diverged branch, or a `/flow-commit` that needs attention) and **Waiting for you** (blue) for a repo whose declared state is `needs-input` or `blocked`, with its next step. Such repos are no longer told to deliver changes; the full text is in the chip's tooltip.
- The **Conformity** tab (with a count badge) is a full-width view, not a drawer: it hides the shared filters (they never applied to it), is never saved as the tab to reopen, and a repo name in it filters the board and takes you back to the tab you came from. It lists every repo, whatever the filters, that has no usable `docs/ROADMAP.md` or whose file has problems, with the line of each problem. Info-level problems (such as a dependency outside the table) are not listed. It is built from the roadmap read from the remote base branch, so unpushed edits do not show. Opening the panel at `http://127.0.0.1:<port>/#conformity` opens that drawer on load.
- The Conformity tab also shows the **requirements** a repo must meet to show well in the panel, listed in `requirements.json` at the panel root, and the **prerequisites** of this machine (`git`, `gh` logged in, `pi`). Failing, outdated and unavailable requirements come first, with their level (`required` or `recommended`), their category and a remedy (the instruction an AI agent applies in that repo, shown as a second line); passing ones are collapsed. The panel only **detects**: it reads the remote base branch and never edits a file of another repo; applying a remedy is the agent's job, through `/flow-commit` and `/flow-pr`. Whether `flow-skills` is registered in pi is not checked. The required `manual-leftovers` requirement detects what the order cannot name by itself: a manual section of `AGENTS.md` outside the blocks (for example a `## Orquestación` with Puerta, Avisos a Dirección, Tamaño, Verificación según el riesgo or Contratos entre proyectos) that restates what an installed block already says, or the old `/flow-branch`; it removes every block region and looks at what is left (headings of level 2 to 4 with those exact titles, and the text `/flow-branch`), and the detail lists at most 5 findings. It exists because the order only names the ids that fail, so a repo whose `registro` and `ciclo` pass would otherwise never be asked to apply the "replace the WHOLE section" rule of `requirements/INSTALL.md` step 3.
- A card of a repo that lacks a **required** requirement shows one small warning with the number, "⚠ N" (RP94b: the tooltip and the aria-label say "N requirements missing" and list the ids); to hide it, use "Hide warning" in the card menu. A gap that is only recommended shows nothing on the card (the drawer still lists it), and nothing is shown while the requirements load or if they failed to load. Hiding the warning keeps the repo on the panel with the basic features; the choice is saved as `dismissed` in `config.json`.
- A **⋯** menu on each card holds "Put in conditions", present only while some requirement is not passing, and "Hide warning" / "Show warning"; its last item is "Remove from panel…" (RP94: it replaced the loose ✕ button, asks before it removes and deletes nothing from disk or GitHub). "Put in conditions" asks `POST /api/pi` with the key `put-in-conditions`; the server builds ONE line from the repo's requirements (the ids that are not passing, required first) that tells the agent in the open session to read `requirements/INSTALL.md` (absolute path, in double quotes, with the user's authorization to read that one file outside the repo) and apply those ids. It needs a started, idle session of the repo, like the other buttons, and it refuses with 409 when everything already passes or the requirements could not be read. `confirmed` only means the prompt left the idle state; it does not prove the agent read or applied anything.
- **Answering a question from the panel (RPC2-3).** When pi asks something (a permission such as *Allow guarded git push?*, a `select`, an `input` or an `editor`) the chat shows a card under the history with the title and the FULL message (the command) as escaped text, and the answer is a click: `POST /api/rpc/dialog` `{ id, requestId, ... }`, once (the buttons lock at the click). The server checks the SHAPE against the method of the pending dialog before it writes anything to the agent: `confirm` takes `{ confirmed: boolean }`, `select` takes `{ value }` only when it is one of the options it showed, `input` and `editor` take `{ value }` (LF and TAB only, up to 4000 characters), any of them takes `{ cancelled: true }`; anything else (an extra key, another shape, two shapes) is a fixed 400 and the dialog stays pending. A title is cut at 300 characters, a message at 4000 and options at 20 of 200; when anything is cut the dialog carries `truncated: true` and the card offers only **Deny** (or only **Cancel** for an *Allow…* select) with the note that the command is cut and has to be answered in the terminal, as it does for an empty message or one that ends with an ellipsis. **Deny** comes first, there is no «Allow always» and no key answers.
- **The right column is tabs; its Changes tab (RP92, RP128).** With the right column in (from 1100 px of layout, see RP89) the column is a row of TABS (RP128): Tasks, Changes, Status and Files, in the order of the cycle (a tab with nothing to show is not drawn). Only the open tab shows its name, the others are icons (and in a column narrower than 300 px none does); the arrows, Home and End move between them, and the open tab and the folded folders belong to the opening of the repo. It starts on the tab that fits the situation (RP148), decided once, as soon as the repo's facts are known: **Changes** with uncommitted changes, **Status** when the branch has an open pull request, **Tasks** when the tree is clean with nothing ahead to deliver, and Changes in any other case; a tab you choose with a click is never replaced, and the choice does not move by itself when the situation changes. The Changes tab lists the files with uncommitted changes of the open repo as a TREE of folders: the total on top (files, added and deleted lines), one row per folder with its count (a chain of single folders is one row, folders come first, each one can be folded), and for each file its name (the whole path is its tooltip; a long name is clipped), the added and deleted lines (`bin` for a binary file) and its status letter, at most 200 files with the rest counted. It is drawn from the facts the board already keeps fresh, so it reads nothing new and is never stale. Touching a file opens it in the diff tab of the centre block (RP90) and marks it in the tree. With the column in, the Changes tab of the chat is gone (the card replaces it) and the chip **● N files** of a card opens the repo on the chat, where the card is; under 1100 px, where there is no column, the Changes tab stays as before. The Files tab (RP65) is not touched. In the Changes tree a folder has a filled blue icon and a file an outline grey one; each level is indented 16 px (8 px in a narrow column) and a file sits one level to the right of its folder.
- **Diff tab (RP90).** The tab bar of the centre block gets ONE more tab, the last one, once a file is open in it: it is named after the file (the whole path is its tooltip), it has its own ✕ to close it, it is reused for every file you open (it never multiplies) and it stays in the bar when you go back to the chat, where touching it shows the diff again (the diff is read again each time you switch to it, because the files change). Changing repo drops it. It draws the diff viewer of the Changes tab for that one file, from the same `GET /api/diff` (the server did not change); a file that is not changed any more says so. A file is opened by touching it in the files card of the right column (RP92) or, where there is no column, in the list of the Changes tab, which always lists every file.
- **Open and New session (RP99).** With no session adopted for the repo the chat shows the list of the folder's sessions (up to 20, newest first, in a box that scrolls) with an **Open** button per session and a **New session** button. **Open** adopts that session and shows its history at once; the pi process starts when the first message is sent. **New session** calls `POST /api/rpc/start { id, new: true }` (`new` is `true` or absent, anything else is `400`): it starts a session with its OWN id (`panel-<folder>-<repo id>-<6 hex>`, so a new session never resumes an old one) and adopts it; it is `409` when the repo already has a live or an adopted session (close it first). While the list is in view the Send button is disabled and the box says why, so nothing starts or is adopted without being asked. A start takes up to five minutes, so while one is on its way (and while a session is live) `POST /api/sessions/adopt` is `409` (close it first) and the Open buttons are disabled: the chat never shows the history of one session while another one runs.
- **A session open in a terminal (RP100).** pi does not lock its session files (it creates the file with an exclusive flag the first time it writes and then appends lines), so two programs on the same session mix up its history and the panel cannot see your terminals. The hint it has is the last write of the session file, which the list already shows: a session written to less than 2 minutes ago gets the tag "Active a moment ago, it may be open in a terminal" and **Open** asks before adopting it. Only the page does this (the server does not change). A terminal that is open but quiet writes nothing and is not detected: it is a hint, not a guarantee.
- **Open the session in a normal terminal (RP118).** Next to *Close session* a *Terminal* button shows the line to run in PowerShell (or a POSIX shell) to open the session of the repo with the whole interface of pi: the folder of the repo and the launcher of the active runtime (Gentle Shell, not the original `pi`, which keeps its sessions elsewhere) with `--session-id` and the real id of the session, and a *Copy* button. The server writes the line (`GET /api/terminal?id=<repo id>`, token required, read only): the folder and the launcher go in single quotes, the id is only letters, digits, dot, dash and underscore, and it refuses what it cannot carry safely, such as a control character, a character that shows one thing and runs another (direction marks, zero-width characters, odd spaces) or, on Windows, a typographic quote or one of `& | < > ^ %` in the folder name (cmd.exe reads those as operators, so the block is labelled *PowerShell*: paste it there). It only shows the line: it does not open a terminal and does not close the session, so close it in the panel first (pi does not lock its session files, RP100).
- **Close session (RP98).** A **Close session** button, at the right of the session state inside the composer frame (the chat head stays the repo name and the ✕, RP72), shows while the repo has a session (adopted or live). It calls `POST /api/rpc/close { id }` (token required; the repo comes from the config by id; any other field is ignored): the pi process of that repo is stopped, also one that is still starting (its start, and any start that joined it, then fails with `409 The session was closed` and adopts nothing), the adoption of that repo is released (a session the browser names is never touched) and the answer is the closed status. The chat goes back to the list of the folder's sessions, where one can be adopted or a new one started. A session that is working or asking is confirmed first. The ✕ of the chat only hides it: the session keeps running. Closing frees one of the 6 live slots; one live session per repo.
- **Side by side (RP66c).** A **Side by side** button above the diff (in the Changes tab and in the diff tab) shows the changes in two columns, old on the left and new on the right: context on both sides, and a group of deleted lines next to a group of added ones, one by one. The choice is kept in the browser with the other preferences (`prefs.split`). When the code box is narrower than 700 px the two halves stack (deleted first, the context once), with CSS only, so nothing is redrawn. The colors and the escaping are the ones of the unified view.
- **Changes tab (RP64).** The same right panel has a third tab, Changes: the single code viewer. Click the **● N files** chip of a card (on the Summary or on the Work board; from Work the page goes to the Summary first) to open that repo on Changes. It shows the list of changed files (status, path, added and deleted lines; click one to open it in the diff tab of the centre block, RP90) and the code of the uncommitted diff with two line-number gutters (old and new), hunk headers and the added and deleted lines coloured. It reads the existing `GET /api/diff` each time you switch to the tab, keeps the last good answer if a later read fails, and draws at most 2000 code rows (then a "+N more lines" note). It replaced the old diff drawer; the Conformity drawer is unchanged. The composer is hidden on this tab and nothing is ever sent from it.
- **Files tab (RP65).** The right panel has a fourth tab, Files: a tree of the repo's files (folders folded, except the ones that hold a changed file) and, below it, the file you pick, in the same numbered-lines look as Changes, with its **changed lines highlighted** (an untracked file is changed on every line). It reads only: `GET /api/files?id=<repo>` lists what git knows (tracked plus untracked and not ignored) and `GET /api/file?id=<repo>&path=<path>` reads one of those files. Files that look like secrets are shown (your decision), but a path is served only when it is a plain repo-relative path, is exactly an entry of git's listing, is a regular file (a symlink is never followed) whose real path stays inside the repo, and is not under `.git`; ignored files (such as `.env`) are never listed or served, and a refused request always gives the same `File not found`. Files over 1 MiB and binary files show a note instead of text. Known limits: the file is re-opened after the checks (a local process that can write inside the repo could race it), and each read runs two `git ls-files`. The tree uses the same look as the Changes tree (RP146): a folder is a chevron, a filled blue folder icon and its name, a file is an outline grey icon one level to the right of its folder, with the same indent step (16 px, 8 px in a narrow column) and no guide lines; Modified stays yellow with its letter.
- **Notes server (RP93, the tab is RP93b).** `GET /api/notes?id=<repo id>` reads and `POST /api/notes` (`{ id, text, base }`) saves the notes of a repo: ONE fixed file, `.panel/notas.md` inside it; the page never sends a path and the repo comes from `config.json` by id. The answer carries the text and a `rev` (a hash of the content, empty when there is no file yet); a save sends the `rev` it last saw as `base`, and if the file changed outside since (Notepad, another tool) nothing is written and the answer is `{ conflict: true, text, rev }` with what is on disk. Before the first write, when Git does not ignore the file, the panel adds `.panel/` to that repo's `.git/info/exclude` (never twice, and put back exactly as it was if that does not hide the file), so the notes never show in `git status`; a notes file that Git already TRACKS is never written (409). The write is whole or nothing (a temp file, then a rename), saves of one repo run one at a time, the text is stored exactly as sent (at most 256 KB, counted in bytes), and `.panel` or the file being a link or not a regular file is refused (400), so nothing is read from or written outside the repo.
- **Footer and Status tab of the right column (RP129).** A footer stays at the bottom of the column in every tab: the branch, the commits ahead, a mark for the CI of the open pull request of THAT branch (it spins while checks run) and its **Merge** button. The pull request is the open one whose head is the current branch and never another one: on the base branch, on a detached HEAD, while pull requests load or fail to load, or in a repo with no GitHub remote there is none, and the button is off and says why in its tooltip. The button is the same Merge action of the cards (`data-act="merge"`, `POST /api/merge` with the method chosen in Settings, Delivery) and it follows the same rule, kept in ONE place (`mergeButton` in `public/view.js`, which the card of the board asks too): it is enabled only for a ready PR with no merge in flight or just done and no command running in the session. The server is still the real guard: it reads the PR again and refuses one that is not open or not ready. The Status tab shows that pull request (number as a link, state, title, branches and size), a summary of its checks, one row per check with its state (the state word goes away in a column narrower than 300 px) and, when some run failed, the same **Re-run failed** button of the cards; a yellow badge on the tab counts the pending checks. It reads what the board already has (`GET /api/prs`), adds no route and writes nothing.
- **Files in the right column, one viewer in the centre (RP130).** The explorer of the repo (and the list of changed files) is ALWAYS in the right column and never in the centre: its **Files** tab sits next to Changes and shows the tree of the repo (folders folded except the ones that hold a changed file, changed files marked, the open one highlighted). The centre is the place of action (the chat, Notes and ONE viewer tab): touching a file of Changes or of Files opens it in that tab, next to the chat, with its name and its own close button; a changed file picked in Changes shows its diff and a file picked in Files shows its content, and opening one replaces the other. Notes stay in the centre as a tab, as before. With the column in, the chat has no Files (or Tasks, or Changes) tab; under 1100 px there is no column, so the chat keeps its Files tab as before. It reads what already exists (`GET /api/files`, `GET /api/file`) and writes nothing. The column scrolls as a whole (RP132): the tree of Files takes its natural height with no scrollbar of its own, and the tab bar on top and the footer at the bottom stay in place with any long list (a window under about 570 px of height still scrolls the whole page).
- **Notes tab (RP93b).** The chat has a Notes tab (with or without the right column): a free-text notepad stored in the repo's `.panel/notas.md`, out of Git (RP93). It saves by itself about 800 ms after you stop typing and at once when you leave the tab, close the chat, open another repo or hide the page, one write at a time, and shows `Saving…`, `Saved` or `Not saved` (with a Retry button). If the file changed outside the panel nothing is written: you choose `Load the version on disk` or `Keep mine`. Unsaved text is never replaced by a read.
- **Choosing the pi (RPC1a).** The panel detects two installs of pi, Gentle Shell (launcher plus its `current` file, nothing is run) and the original `pi` on the PATH (its `--version` is read), and uses Gentle Shell first (`auto`) or the only one it finds. `GET /api/pi-runtime` lists them (`?check=1` also starts the active one in RPC mode once and ends it); `POST /api/pi-runtime` takes ONLY `{ runtime }`, `auto` or the id of a detected runtime, never a path. A custom `command` or `agentDir` can only be written by hand in the `pi` key of `config.json` and is validated (an absolute path or a bare name, no shell characters). The child gets a clean environment (no `PI_*`, `GENTLE_*` or `ENGRAM_*`), and the sessions folder follows the active runtime unless `REPO_PANEL_SESSIONS_DIR` is set. Conformity shows the pi in use and a selector.
- **Sessions over RPC (RPC1b).** The panel starts ONE `pi --mode rpc` per repo (the runtime chosen by RPC1a, in the repo folder from `config.json`, with the adopted `--session-id` or `panel-<folder>-<repo id>`: the first 8 letters and digits of the repo id are part of it (RP97), so two repos whose last folder has the same name never share one), at most 6 at once. Routes (token required): `POST /api/rpc/start`, `/api/rpc/prompt`, `/api/rpc/steer`, `/api/rpc/abort`, `/api/rpc/dialog` (answers only a dialog that is pending) `GET /api/rpc/status?id=` and `GET /api/rpc/states` (RPC2b-1: `{ states: { <repoId>: closed | starting | idle | busy | asking } }` for EVERY configured repo, `closed` by default, read from the host's memory: nothing is started; the page reads it on startup and on every reconnect of the stream); the page can send only a repo id and text, never a program, folder or argument. Events reach the page on the SSE stream as `event: rpc`; the stream carries nothing else (heartbeat comments aside). The sessions live inside the panel process: a restart ends them and they come back with the same `--session-id`. A start can take up to five minutes (4 s to over 60 s measured, with no pattern; 24 to 29 s when pi has to look for the session id among a repo's sessions; RP101 raised the cap from two minutes after a New session ran past it twice); one that runs out of time answers 504, so commands wait in a queue until the agent answers.
- **Tasks (RP63, RP91).** With the right column in (from 1100 px of layout, see RP89) the tasks of the open repo are the Tasks TAB of that column (RP91, RP128) and the chat has no Tasks tab; where there is no column the chat keeps its Tasks tab. Click the progress bar of a card (it is a button; Enter works too) to open that repo (on its Tasks tab, in the column or in the chat). In the column the list is COMPACT (RP128, redone in RP149): a summary («N of M done · K in progress») with a thin bar, then the groups In review, Ready, In progress, Next (highlighted), Pending, Blocked and Completed, each only when it has tasks, with ONE icon in its header and flat rows that are not buttons (the id and the title, and at the right of the same line the PR, the branch, what it waits for or the reason of a block; it drops to a second line only when it does not fit; a title takes 2 lines at most and ends in «…», the tooltip of the row has it whole). Pending shows 10 and «+N more» opens the rest in place, with the tasks that wait for another one last and dimmed; Blocked is open; only Completed is folded, and it starts folded with no row on show. The summary row, which stays under the tabs when the list scrolls, says when the list was read («Read 2 min ago», yellow from 15 minutes) and has a button that runs `git fetch` on that repo and reads the list again. The list is read again every time the Tasks tab is entered. The full list, in the chat's Tasks tab where there is no column, lists the rows of its `docs/ROADMAP.md` grouped as In review, Ready, In progress, Next (highlighted), Pending, Blocked and Completed (folded until you open it). Each row says its PR, its branch or what it is waiting for. There is no search box (RP148): the list is read in order. It reads the existing `GET /api/roadmap` each time the repo is opened (in the column, when it opens, and again each time the Tasks tab is entered or the refresh button is pressed; on the chat's tab, when the tab is first shown) and keeps the last good answer if a later read fails; on the tab the composer is hidden, and nothing is ever sent from the tasks.
- **Rooms.** A room is a repo where you coordinate a group of repos (for example `upen-ceo`). A repo assigned to a room shows a room tag with a dot (RP94b2: with ONE room defined the tag is only the dot, and the room name is in the tooltip and the aria-label; with several rooms it also shows the name, next to the group tag when that shows): RPC2b-1 made it always gray (a room has no session state any more); the tooltip gives the date of the room's last commit. The Conformity drawer has a **Rooms** section with each room's requirements, last commit and members. Repos outside every room look exactly as before. See Rooms below.
- A red banner at the top of the page appears when the server process is older than the page (for example after `git pull` without a restart). `GET /health` answers `{ "app": "repo-panel", "api": <n> }`; the page compares `api` with its own version and warns on a mismatch or a missing field. If the Conformity report cannot be computed, the drawer says so instead of claiming conformity.
- A **/flow-commit** button on cards with changes sends that command to the session of the repo over RPC (RPC2-2): the server calls `prompt` on the session the panel keeps for that repo. The session must be started and idle; otherwise it refuses with a fixed message (409 `The session is not started`, `The session is busy` or `The session is waiting for an answer`). The page starts a closed session first (it can take up to five minutes) and then sends, so a closed session never disables the button. The browser sends a command key, never text, and only `/flow-commit`, `/flow-commit --unstage` (key `flow-commit-unstage`), `/flow-pr`, `/flow-base`, `/flow-base --stash` (key `flow-base-stash`), `/flow-next` (key `flow-next`), `put-in-conditions` and `fix-pr` exist on the server. The panel never adds `--unstage` on its own: only the button sends it. The server also refuses a second send of the SAME command key to the same repo for 45 seconds after a confirmed one (409 "That command was already sent N s ago; wait for it to finish"; in memory, per repo path and key, other keys are not affected, and the not-started, busy, asking and unknown-command refusals win over it). The reason a double click got through before is unconfirmed (a subagent's screen may read as idle), so this guard is a safety net, not a diagnosis. `fix-pr` also takes `pr`, the integer number of an open pull request of that repo (`POST /api/pi` `{ id, command: "fix-pr", pr }`; `API_VERSION` 12): the server looks the PR up itself, refuses with 400 when `pr` is missing or not a positive integer and with 409 when the PR does not exist, is not open or has no failing checks, then builds ONE line from the PR number, title, head branch and up to 5 failing check names (control characters replaced by a space, double quotes dropped, title capped at 120 and each name at 60 characters). The order tells the agent to find out why with `gh`, switch to the PR branch only if the tree is clean (otherwise stop and ask), fix whatever is needed (production code, test code or configuration) as long as it serves the original objective of that PR (its title, description and commits), run the tests, and not commit, push or open pull requests. It is also told not to use `git mv` or `git add` and to leave the git index empty (`put-in-conditions` carries the same sentence, and so does `requirements/INSTALL.md`), because `/flow-commit` refuses to start when files are staged. When the failure is unrelated to that objective or looks transient (infrastructure, a flaky run, a runner problem) it must not edit code: it says so and recommends **Re-run failed**; when the right fix would change the PR's scope or needs a product decision it stops and asks. It goes through the same safeguards as the other buttons (a started, idle session and the duplicate guard).
- Quick actions: open on GitHub, `git fetch --prune`, re-run failed checks, refresh.
- **Automatic fetch (RP150).** While a page is open the server runs `git fetch --quiet --no-prune` on each repo in the background (every 1 minute for a repo whose branch has an open pull request, every 5 minutes for the others; the interval doubles after a failure, up to 15 minutes), so the roadmap read from `origin/<base>` stays current. One fetch process per repo at a time (a repo and its linked worktrees count as one), at most 2 automatic fetches in flight, a 30 s limit, no credential prompts, no git maintenance; a repo with no remote or with a git lock taken is skipped. It never prunes, even with `fetch.prune` set, and never touches your branch, index or working tree. A forced refresh does not start one, and `POST /api/fetch` still runs `git fetch --prune --quiet`. Restart the server to pick it up.

Not verified: the `/flow-pr` button, the manual-action bar, the "Show /flow-commit anyway" item and the committing/attention lines were checked through their pure helpers, a render smoke test with a stubbed page and real throwaway Git repos, but not in a browser; the verdict was not run against a real session end to end; and nothing was tried with many repos.

The panel observes, merges when you click, and can hand `/flow-commit` to your open session; committing and opening PRs are still done by that session, not by the panel.

## Requirements

The panel shells out to `git` and the GitHub CLI, so both must be installed and working before you start. There are no npm dependencies and nothing else to install.

1. **Node.js 20+** (`node --version`).
2. **Git** on your `PATH`, with access to your repos' remotes (`git fetch` must work from the terminal).
3. **GitHub CLI** ([install](https://cli.github.com)) logged in to the account that can see your repos:
   ```bash
   gh auth login
   gh auth status     # must show "Logged in"
   ```
   The token needs the `repo` scope (PRs, CI status, merging) and `workflow` to re-run failed checks. `gh auth login` grants `repo` by default; add `workflow` with `gh auth refresh -s workflow`.


Quick check that everything is ready: `node --version && git --version && gh auth status`. PRs, CI status and Merge depend on `gh`; the local git view only needs `git`.

## Quick start

```bash
git clone <this-repo-url> repo-panel
cd repo-panel
npm start          # then open http://127.0.0.1:4310
```

Other commands:

```bash
npm run open       # same as start, and opens the browser (Windows only)
npm test           # run the test suite (node --test through scripts/run-tests.js)
```

`npm test` forwards every extra argument to `node --test` (`npm test -- --test-name-pattern foo`). On Windows it also reads the definition of the real `repo-panel` and `repo-panel-tray` scheduled tasks (read-only: every action, the triggers and the restart count) before and after the run and fails with a loud message if either changed, even when every test passed. When all is fine it adds one line: `task guard: repo-panel and repo-panel-tray unchanged`. If PowerShell cannot read the tasks the line says so and the run is not failed.

## Start automatically at logon (Windows)

```powershell
powershell -ExecutionPolicy Bypass -File scripts/install-autostart.ps1    # install
powershell -ExecutionPolicy Bypass -File scripts/uninstall-autostart.ps1  # remove
```

This registers a per-user scheduled task (no admin needed) that runs the panel hidden at every logon and retries every minute if it fails. The port never changes, so the URL stays stable and you can pin it as a browser app. Launching the panel while it is already running just exits quietly. If another program owns the port, the launch fails with a clear message instead of picking a different port.

`install-autostart.ps1 -DryRun` shows what it would register without registering it, and `uninstall-autostart.ps1 -DryRun` says what it would remove without removing it. The installer needs a real `node.exe` on PATH (not an npm, volta or fnm `.cmd`/`.ps1` shim).

All four scripts that register or remove a task (`install-autostart`, `uninstall-autostart`, `install-tray`, `uninstall-tray`) refuse to run, even with `-DryRun`, from a copy that lives inside the OS temp folder: they print `... refused: this copy lives inside the OS temp folder (<folder>); install from the real repository folder.` to stderr and exit with code 2. The tasks are per-user and global to the machine, so a throwaway copy (a test, a worker) that registered one would silently overwrite the real task with paths into a folder that is about to disappear.

### Restart after an update

The page files are read from disk on every request, but the server code is loaded only when the process starts. After `git pull` (or any update of the panel) the server must be restarted, or the page will talk to old code and show the red out-of-date banner.

The autostart task is called `repo-panel` (it runs `conhost.exe --headless node server.js`). `Stop-ScheduledTask` alone does **not** stop the Node process: it stays alive holding the port, and a new start exits silently with "repo-panel is already running". Restart by ending the process that listens on the port and then starting the task:

```powershell
Get-NetTCPConnection -LocalPort 4310 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }; Start-ScheduledTask -TaskName repo-panel
```

Use the `port` from `config.json` if you changed it. To check: open `/health`, it must show the current `api`, and the red banner must disappear after reloading the page.

#### Tray icon (Windows)

To avoid doing that by hand, `scripts/tray.ps1` puts an icon in the notification area (next to Docker and the like). It is a hidden PowerShell script (Windows PowerShell 5.1 or PowerShell 7, no dependencies). The task starts it through `conhost.exe --headless`, like the panel task, so there is no console window at all: with a plain hidden `powershell.exe`, closing its console window killed the icon (task result `0xC000013A`). A task installed before this change keeps the old command; run `install-tray.ps1` again from the real repository folder to switch.

```powershell
.\scripts\install-tray.ps1      # registers the per-user task repo-panel-tray at logon (no admin)
Start-ScheduledTask -TaskName repo-panel-tray   # start it now, without logging out
.\scripts\uninstall-tray.ps1    # removes the task (close a running tray with its "Quit tray" item)
```

`install-tray.ps1 -DryRun` (and `uninstall-tray.ps1 -DryRun`) only print what they would do. You can also run `powershell -File scripts\tray.ps1` by hand; a second launch exits quietly (one tray at a time). The port is read from `config.json` (or `REPO_PANEL_CONFIG`, or `-ConfigPath`), default 4310; an unreadable config uses the default.

- The icon is green when `http://127.0.0.1:<port>/health` answers `repo-panel`, gray when it does not (checked every 5 seconds); the tooltip says `repo-panel: running (port N)` or `repo-panel: stopped`.
- Right-click menu: **Open panel** (also the double-click), **Restart panel**, **Start panel** (enabled only when stopped) and **Quit tray** (the panel keeps running).
- **Restart panel** ends only the processes listening on the port whose command line runs this repo's `server.js` (a path inside this folder, or the `node server.js` form of the autostart task that also answers `/health` as `repo-panel`). If something else holds the port it ends nothing and says so. Then it runs the `repo-panel` task, or, if that task does not exist, `conhost.exe --headless node server.js` in this folder, waits up to 15 seconds for `/health` and reports the result in a balloon tip.
- It only talks to `127.0.0.1`. Errors show as a balloon tip; the tray keeps running.
- `scripts\tray.ps1 -SelfTest` prints the facts the menu uses (port, health, listeners, owned listeners, task) as one JSON line and opens no window; `-SelfTestRestart` runs the end-and-relaunch logic and refuses unless `REPO_PANEL_CONFIG` is inside the temp folder. The tests use these two modes.
- Windows only. Not verified by the tests (they cannot see the desktop): that the icon is visible, its colors, the right-click menu, the balloon tips, and clicking **Open panel** / **Restart panel** in the real menu. If the tray process is killed (not quit), Windows may keep a ghost icon until the mouse passes over it.

## Configuration

On first run there is nothing to configure: click **+ Repo** to add a single folder, or to scan a parent folder for every repo inside it. The panel saves your choices to `config.json`, which is git-ignored so your local paths are never committed.

You can also create `config.json` by hand; copy `config.example.json` as a starting point:

| Key | Meaning | Default |
| --- | --- | --- |
| `port` | Port to listen on | `4310` |
| `priority` | Optional list of repo names (e.g. `["repo-panel", "api"]`) that go first in the "Go work on" strip, in that order; case-insensitive, unknown names ignored | none |
| `chat.showResults` | `true` lets the chat ask, with a click on a tool chip, for the START of the text of that tool's result (`GET /api/chat/result`). Off by default, and anything other than the value `true` is off. It is a switch of privacy: a result is free text and can hold secrets (the output of `cat .env` or `env`), and no list of patterns catches every form of one. Never shown: the result of `read`. Change it in the Settings tab, or by hand in this file | `false` |
| `dismissed` | Optional list of repo ids whose "requirements missing" warning is hidden; written by the panel (`POST /api/dismiss` `{ id, on }`), invalid entries and duplicates ignored | none |
| `sessions` | Optional map of the session the panel adopted, `{ "<repoId>" or "room:<name>": { "id", "name", "adoptedAt" } }`; written by `POST /api/sessions/adopt` and `/start`, cleared by `/release`; entries with an invalid id (only `A-Za-z0-9._-`, 1 to 80 characters) are ignored | none |
| `rooms` | Optional list of rooms, `[{ "name", "path", "repos": [repoId] }]`; written by the panel's **+ Room** screen and the card menu, or by hand (see Rooms) | none |
| `groups` | Named groups of repos (`{ "name", "repos": [{ "path", "base", "roadmap" }] }`); `base` and `roadmap` are optional | `[]` |

`POST /api/queue` takes the per-repo facts from the browser (it does not rerun any git or gh command) and orders them: repos in `priority` first, then merge, branch, deliver and start, keeping board order within each kind. `POST /api/conformity` takes each repo's roadmap availability and problems and returns the repos that do not conform.

### Requirements

`requirements.json` is `{ "version", "blocks", "requirements": [{ "id", "title", "category", "level", "check", "remedy" }] }`. `blocks` holds the version each Orquestación block must have (`<!-- orquestacion:NAME vX.Y -->` ... `<!-- /orquestacion:NAME -->`). The checks are pure functions in `checks.js`; the server reads the files from `origin/<base>` (`AGENTS.md`, the roadmap, `docs/ORQUESTACION.md`) and `checks.js` decides.

**Changing the text of a block means bumping its version.** The panel marks a repo `outdated` only when the version in its `AGENTS.md` differs from the one in `blocks`, so an edit to `requirements/blocks/*.md` without a bump leaves every repo on the old rule with no warning. To change a block: edit its text, raise the version in its opening marker and in `blocks` of `requirements.json`, then refresh `requirements/blocks.lock.json` with `UPDATE_BLOCK_LOCK=1 node --test test/rp36-block-versions.test.js`. That file records the version and a hash of each block's text; `test/rp36-block-versions.test.js` fails when the text changed and the version did not, and when the lock is stale. The refresh itself REFUSES a text change under the same version (otherwise refreshing would defeat the guard); `UPDATE_BLOCK_LOCK=force` accepts it and is only for a block nobody has installed yet. Repos with the old version then show the requirement as `outdated` and "Put in conditions" reapplies only that block.

**The padrón is the version of the whole set of rules.** `padron` in `requirements.json` (and in the title of `requirements/INSTALL.md`, which the test keeps equal) covers the procedure the agent follows, not only the blocks. The order sent to the agent cites it (`for repo-panel (padrón X.Y)`), each repo records it in `docs/ORQUESTACION.md` with the line `- **Padrón del panel:** X.Y`, and the required requirement `padron-record` compares the two. So when the procedure changes without any block changing, raise `padron` (the same lock hashes `INSTALL.md` and `requirements/EXAMPLES.md`) and every repo shows `padron-record` as `outdated`. The worked examples in `requirements/EXAMPLES.md` are run by `test/rp41-standard.test.js` against the panel's own validator, so they cannot drift from what it accepts.

- Categories: `verificable` (the panel decides and can show it as passing), `parcial` (shows evidence, a person confirms) and `criterio` (never passing, only a reminder). Only `verificable` requirements can pass; a repo is `ready` only when every `required` one passes. `recommended` ones never affect `ready`.
- Result status: `pass`, `fail`, `outdated` (the block has another version, or is the old unversioned section), `unavailable` (could not be read: no repo, no base branch, missing file, or an unknown check type). Unavailable is never shown as passing or as failing.
- The old unversioned `## Orquestación` section (or the `orquestacion:bloque` marker) counts as an outdated `registro` block that asks to be updated, not as a missing one.
- The agent's instructions live in the panel folder, not in another project: `requirements/INSTALL.md` (the procedure: apply only the ids named in the order, never delete rules, stop and ask the user on a conflict with the repo's `AGENTS.md`, work on a task branch, never commit, push or open PRs) and `requirements/blocks/registro.md`, `requirements/blocks/ciclo.md` and `requirements/blocks/estado.md` (the exact text of the versioned blocks). Each `remedy` points at them. The roadmap table is the exception: the block does not define it, so `INSTALL.md` step 7 and the `roadmap-file` and `roadmap-table` remedies spell out its exact column names (`ID`, `Entrega`, `Depende de`, `Estado`; optional `Resultado visible`, `Notas`, `Ficha`), the same list the validator requires (`lib.RM_REQUIRED`). **One mechanism to create and manage tasks.** The `tareas` block (`requirements/blocks/tareas.md`, in Spanish, a required requirement installed into each repo's `AGENTS.md`) states it: every task is a row of `docs/ROADMAP.md`, created `Pendiente`, taken with `siguiente`, closed in the same diff, and nothing parallel is allowed. Step 7 of `INSTALL.md` tells the agent to migrate whatever other task system a repo has (`planning/`, a roadmap elsewhere, task lists kept in files) into that table, keeping the old files as fichas; to remove from `AGENTS.md` the instructions about how to create or manage tasks and the repo's own rules about branches, commits and pull requests (the panel's `/flow-base`, `/flow-commit` and `/flow-pr` decide those; the lines saying what a production, release or hotfix branch is for stay) and to list what it removed; never to invent dependencies (a task without one gets `—`); and to stop and ask only when a task's ID or state cannot be derived. With no tasks it writes only the row `U0`. A checklist kept inside each change (OpenSpec `tasks.md`, fichas) is not a task list: it stays where it is as history, and only what is still pending is imported, as ONE row per change that says `sin verificar` (the agent cannot tell from the code whether pending work is done: an audit can reopen a step on purpose and a gate is a decision). When a row marked `sin verificar` is taken, the `tareas` block tells the agent to verify it first, with evidence (merged PRs, commits, passing tests, receipts) and the person's OK; it never marks `Completada` by itself, because a wrong `Completada` hides work and unblocks other rows by mistake. The panel never edits another repo: the agent does, and the user delivers it with `/flow-commit` and `/flow-pr`.
- Two more requirements belong to the agent state (see Agent state); `estado-block` is `recommended` (it never changes `ready`) and `panel-ignored` is `required` since padrón 1.3, because every repo ignores `.panel/`: `estado-block` (AGENTS.md on the base branch has a closed `<!-- panel:estado v1.0 -->` ... `<!-- /panel:estado -->` block; the check declares its marker namespace, `"namespace": "panel"`, and the Orquestación blocks keep the default) and `panel-ignored` (Git ignores `.panel/state.json` in the repo's **working tree**: it runs `git check-ignore -q .panel/state.json` there, so it is a local fact, not read from the base branch; exit 0 is `pass`, 1 is `fail`, anything else, such as a missing folder, is `unavailable`). `panel-ignored` does not apply to rooms. Its remedy appends `.panel/` to `.git/info/exclude` (never `.gitignore`, never committed), so there is nothing to deliver with `/flow-commit`.
- A file that cannot be read from the base branch for any reason other than "not on that ref" is reported as `unavailable` (reason `error`), is not cached, and is never counted as failing or passing.
- `GET /api/requirements?id=<repoId>` returns `{ available, base, results, summary }`; `GET /api/prerequisites` returns `{ items: [{ id, ok, detail }] }` for `git`, `gh` and `pi` (a missing tool is `ok: false`, not an error).
- The Conformity tab says "All repositories conform." only when the roadmap report is empty **and** the requirements of every repo and the prerequisites were loaded and every repo is `ready`. While they load it says it is computing; if they fail to load it says so.

### Agent state

Work is often unfinished while the repo already shows changes (the agent is waiting for a decision), and after switching sessions it is easy to forget what to do next. So each agent session declares its state in a small file that the panel reads, and ends its replies with one clear line.

- **File**: `.panel/state.json` in the repo's working tree, ignored with `.git/info/exclude` (see `panel-ignored`), never committed. `{ "state", "next", "detail", "at" }`: `state` is `working` (still in progress), `needs-input` (waits for a decision of yours), `ready-to-commit` (done and verified), `ready-to-pr` (committed, ready for a pull request) or `blocked` (cannot continue; `detail` says why); `next` is one line saying what you should do now; `detail` is optional longer text; `at` is an ISO 8601 date-time.
- **The `estado` block** (`requirements/blocks/estado.md`, in Spanish like the other blocks, installed into the repo's `AGENTS.md` by "Put in conditions") tells the agent to rewrite the file after every action that writes files or needs a decision, and to end its reply with one line `Siguiente: <next>`.
- **Reader**: `GET /api/state?id=<repoId>` (token required, 404 for an unknown id) returns `{ available, state, next, detail, at, stale, reason }`. `available: false` has a `reason`: `missing` (no file), `invalid` (unparsable JSON, not an object, unknown `state`, `next` not a string or over 300 characters, `detail` over 4000, `at` not an ISO date-time or more than 5 minutes in the future), `unsafe` (`.panel` or the file is a symlink or link, not a regular file, or over 64 KB; checked with `lstat` before reading and never followed) or `error` (any other read failure). It never throws. An empty or whitespace-only `next` is `invalid`, and `next` is trimmed. `GET /api/local` only gains the additive fields listed under Delivering.
- **Stale**: `stale` is true when `at` is older (whole seconds) than the repo's last activity: the newest of the local `HEAD` commit date and the modification time of each changed or untracked file (the state file itself excluded, at most 200 files). A stale state is returned but flagged. If Git cannot say, it is not flagged.
- **Card**: with a valid, fresh state the card shows its `next` line (one line, full text, `detail` and `at` in the tooltip) with a dot: working yellow, needs-input blue, ready-to-commit and ready-to-pr green, blocked red. A stale state shows only a small gray "outdated" marker, never the old text. The `/flow-commit` button of a card with changes is hidden unless there is no usable state or the usable state is `ready-to-commit`, or you chose **Show /flow-commit anyway** (below); the server-side checks of the button (one idle session, lock) are unchanged. The line is only shown on cards with changes or unpushed commits.
- **Expiry of `working`**: a declared `working` older than 30 minutes (by its own `at`) counts as expired: the card shows only the gray "outdated" marker and the commit button is usable again, because an agent that crashed would otherwise hide it forever. `needs-input`, `blocked` and `ready-to-pr` never expire by time.
- **Show /flow-commit anyway**: when a declared state hides the commit button, the card's **⋯** menu offers this item. It brings the button back for that repo until the page is reloaded (kept in the page, never persisted). A merged branch with changes never shows it: that card offers `/flow-base --stash` instead of `/flow-commit`. The red stale mark names the real button in its tooltip (`/flow-base`, or `/flow-base --stash` with the uncommitted changes it carries).
- **A missing, invalid, unsafe, failed or stale state never blocks anything**: the panel behaves as before. The state can only hide the commit button.
- **Not verified**: the panel cannot tell whether an agent follows the block and writes the file (a model may skip it or write a wrong time, which makes its state look stale); and the line and dots were only checked with unit tests of the helpers, not in a browser.

### Delivering: /flow-pr, manual action and the verdict

The Committed column means "clean tree with commits not delivered yet". That alone is not enough to hand the branch to `/flow-pr`, so the card checks more and says when a person has to step in.

- **`GET /api/local`** gains three additive fields and changes nothing else: `head` (full SHA of `HEAD`, `null` for an unborn branch or on any Git error), `inProgress` (`null`, or `merge`, `rebase`, `cherry-pick` or `revert`, detected from the git dir with `git rev-parse --git-path`, so worktrees and submodules work; it never throws) and `base` (the base branch: the configured one, else `origin/HEAD`, else `main`). `API_VERSION` is now 8.
- **/flow-pr button.** A Committed card shows `/flow-pr` only when ALL hold: no changed or untracked file, commits ahead (also on a branch with no upstream), the branch is not the base and not detached, nothing needs manual action, the repo is not flagged stale (`Merged: run /flow-base`) and no `/flow-commit` verdict is running or needs attention. When an open PR from the current branch already exists, the label is **`/flow-pr (update PR)`**, because `/flow-pr` creates the PR or updates the open one. Otherwise there is no button. Committed cards no longer carry `/flow-commit`: with a clean tree there is nothing to commit; the button stays on Changes cards.
- **Needs manual action.** Commits are made only through `/flow-commit`, and PRs through `/flow-pr`. A card shows a red bar "Needs manual action: …", hides both buttons, goes to the top of its column and counts in the ⚠ problems filter (like a stale card) when: there are commits ahead while the current branch IS the base ("Commits on main: move them to a task branch"); HEAD is detached; a merge, rebase, cherry-pick or revert is in progress; or the branch diverged from its upstream (commits both ahead and behind). It does not fire for a clean branch that is only behind, a base branch with nothing ahead, or a task branch with commits ahead. A repo whose local state cannot be read keeps its existing error card.
- **Verdict after /flow-commit.** When a `/flow-commit` is sent from the page, the page remembers `{ at, head, files }` for that repo (in the page only: no history, nothing persisted, lost on reload) and follows the session state: the `rpc` state events of the stream feed the verdict at once (busy is running, idle after busy is judged) and the read-only `GET /api/pi-status?id=<repoId>` on the normal refresh cycle stays as the fallback. It answers `{ state }`: `closed`, `starting` as `busy`, `idle`, `busy` or `asking`, from the session host (token required; 404 for an unknown repo).
  - **running** ("committing…"): the session is busy; or the session state is unknown or ambiguous and less than 15 minutes passed; or less than 30 seconds passed since sending (an idle prompt right after sending may not have started yet).
  - **ok**: the tree is clean (untracked files included), `HEAD` differs from the one recorded and there are commits ahead. The record is cleared and the card lives in Committed with its `/flow-pr` button. The session being busy still wins, so the verdict waits for it.
  - **attention** (red bar with the reason and a ✕ to dismiss; `/flow-pr` is NOT offered while it shows): the session is idle or closed but N files are still uncommitted, or `HEAD` did not change, or the session closed before a commit, or `HEAD` changed but nothing is left to deliver; or 15 minutes passed with an unknown session and nothing changed.
  - It is judged from Git and the session state, never from terminal text, and the panel does not judge the quality of the commits.
- **In progress for every command (`API_VERSION` 13).** The same record, `{ cmd, at, head, branch, files, ahead }` (a fresh `GET /api/local` is read right before sending), is kept for `/flow-commit`, `/flow-commit --unstage`, `/flow-pr`, `/flow-base` and `/flow-base --stash`; `fix-pr`, `put-in-conditions` and `flow-next` keep only `{ cmd, at }`. The result of every command is judged from Git and the session state, never from terminal text (`flowVerdict` in `public/view.js`; `/flow-commit` keeps its `commitVerdict` above, and `--unstage` also needs an empty index):
  - **`/flow-pr`**: ok when the tree is clean, the branch has an upstream with nothing ahead and an open PR whose head is the current branch exists; attention "No open pull request for <branch> after /flow-pr" when the session is idle or closed after 30 seconds and that is not true.
  - **`/flow-base` and `/flow-base --stash`**: ok when the repo is on the base branch with nothing ahead or behind (the plain variant also clean); attention "Still on <branch> after /flow-base" when the session is idle after 30 seconds and the branch did not change.
  - **`fix-pr` and `put-in-conditions`**: only running while the session is busy; once it is idle the record is dropped with no verdict (a failure answer from the session is a legitimate outcome) and the card refreshes.
  - A closed session while running is attention ("The session closed while the command was running"); an unknown session for more than 15 minutes with nothing changed is attention.
  - While a verdict is **running** the status line says "committing…", "creating pull request…", "updating base branch…", "fixing pull request…" or "putting repo in conditions…" and EVERY flow button of that repo's cards, plus `Merge`, `Re-run failed` and `Fix CI`, is disabled with a tooltip naming the running command. When the session goes from busy to not busy the page refreshes that repo at once (the same refresh as the timer, so the card changes column without waiting) before it judges the result, and an ok record is cleared. An attention bar stays until dismissed (✕).
- **Staged files.** `GET /api/local` gains two additive fields, `stagedCount` (paths with a change in the index, renames included, untracked files never) and `stagedPaths` (those paths, sorted, at most 20), from the same `git status --porcelain=v2` read. `/flow-commit` refuses to start when the index is not empty, so a dirty card with staged files shows a bar ("N files are staged: /flow-commit needs an empty index. The button clears the index (git reset, your changes stay in the working tree) and then continues with the normal commit in the same run.") and offers `/flow-commit --unstage` instead of `/flow-commit`. That option is the flow-skills runtime's explicit one: a mixed reset, only when you press the button.
- **Why it failed.** The red bar of a failed command shows only its reason. A failed `/flow-commit` or `/flow-commit --unstage` labels its button `Retry /flow-commit` (or `Retry /flow-commit --unstage` while files are staged).
- **Animated progress (`API_VERSION` 14).** The in-progress line of a card ("committing…", "creating pull request…", "updating base branch…", "fixing pull request…", "putting repo in conditions…") has a pulsing dot and an animated ellipsis, and the line is a polite live region (`role="status"`, `aria-live="polite"`). A pull request whose checks are still running shows the chip `verifying checks · 2 running · 2/4` with the same pulsing dot (the tooltip still lists every check); the chips for passed, failed and no checks are unchanged. It is CSS only, with no timers. Because the page re-renders the board on every draw, each animated element gets an inline negative `animation-delay` from the clock (`animDelay` in `public/view.js`) so the animation does not jump. With `prefers-reduced-motion: reduce` every animation is off and the text stays.
- **A session waiting for your answer (`asking`).** After a command a session can stop at a selection dialog (for example "Review consent"). The RPC host reports `asking` while a dialog of the agent is pending, and `GET /api/pi-status` then answers `{ state: "asking" }`. The card keeps the buttons disabled and shows a static highlighted line "waiting for your answer in the session"; it never turns into "Needs attention" because of time, and the repo appears in the "Go work on" strip as "Waiting for you: Answer the question in the session". The panel only shows this notice: it NEVER answers or presses a key in the dialog, and `POST /api/pi` refuses with 409 "The session is waiting for your answer to a question" and sends nothing.
- **Clicks are never lost.** The page writes a region (the board, the "Go work on" strip, the Conformity tab) only when its HTML changed, and a redraw waits for the release of a held mouse button (at most 1.5 s), so nothing under the pointer is replaced between the press and the release. Before, every read of every repo redrew the whole board about 150 times a minute at rest and a press that spanned a redraw never produced its `click`.
- **The buttons follow the session.** A repo with uncommitted changes shows `/flow-commit` (and `--unstage`) disabled with «the session is still working» or «waiting for your answer in the session» while the RPC session of the repo is busy or asking; a closed or idle session holds nothing, and neither does a repo whose session state is not known yet. «Show /flow-commit anyway» lifts the hold. The other delivery buttons follow the session too (RP159): `/flow-pr`, `/flow-base`, `/flow-base --stash`, `/flow-next` and Fix CI are disabled with the same reasons while the session is busy or asking, from the LIVE state of the session, whether or not a command of the page is being judged (Merge is not held: it does not talk to the session). On the cards of the Summary the buttons `/flow-base` and `/flow-next` used to be held only while the order was on its way and came back as soon as the answer arrived; they now stay held while the session works, with the reason as the tooltip. When you press any `/flow-*` button the repo behaves as if that command were already running (the button disabled, the progress line shown, with the reason «Sending the order to the session») from the click until the answer, however often the card is redrawn; a second click never sends a second order. Never checked against a real session showing a dialog.
- **Event stream.** `GET /api/events` is a long-lived Server-Sent Events stream of the `rpc` events of the sessions the panel keeps. It needs the token in the `x-token` header (never in the URL) and the panel's own host; at most 8 clients are served at once (the next one gets a 503). The server stores nothing for it: a new client gets only the stream preamble, then an `rpc` event whenever a session emits one, and a heartbeat comment every 15 s.
- **Message history (RP83).** In the message box of the chat, **↑** brings back the last message you sent to that session, another ↑ the one before, and so on; **↓** walks forward and, past the newest, gives back what you were typing. The arrows only act on the first line (↑) or the last line (↓) of the box, with no selection and no Shift, Ctrl, Alt or Meta, so editing a multi-line message works as always; typing in a recalled text, sending, or opening another repo ends the browsing. The history is the `user` messages of the chat plus the ones still pending, without empty entries or repeats in a row, one per repo, and it lives in the page only (nothing is stored or sent).
- **Chat over RPC (RPC2-1).** The composer talks to the live session of the repo through `/api/rpc/*`: **Send** starts the session first when it is not started (the label says *Starting…*, it can take up to a minute) and then posts `{ id, text }` to `/api/rpc/prompt`; the answer is shown while it is written (escaped, from the `rpc` events), **Stop** posts `/api/rpc/abort`, and when the run settles the history is read once and replaces the streaming bubble. Enter sends, Shift+Enter adds a new line; an error puts your text back. The server refuses an empty text, one over 20000 characters or one that starts with `!`. When pi asks a question the composer is off and the card above answers it. Below the box, as direct buttons, the flow command that can run now (`/flow-next`, `/flow-commit`, `/flow-pr` or `/flow-base`) still goes through `POST /api/pi`.
- **Memory of a session (RP110b).** The plugin that gives a session its memory (Engram) tells its state with a notice of the key `engram`; the RPC client used to drop every notice and now keeps ONLY that one, cut to its last 200 characters (the plugin ends it with the part that says the state, so a long project name cannot push it out). The host reduces its text to ONE category of a closed list: `ready` (`… · ready`), `offline` (`… · offline`), `error` (`… · error` or `… · ambiguous project`) and `disabled` (`memory disabled`); a call that went well (`… · ✓ saved #12`, `✓ 3 results`, `✓ loaded`) is a recovery and says `ready` (RP123), a call that failed (`… · ✗ <text>`) says `error`; a step in progress (`… · saving…`) and any text it does not know say nothing lasting and change nothing. It remembers the last category of each session (the notice arrives when the session starts, and the page may connect later) and publishes only a CHANGE, as `{ kind: "memory", memory }` on the same `rpc` event; `GET /api/rpc/status` and the answer of `start` carry `memory` only once it is known. **The text of the notice never leaves the server** (it can hold the name of the project or an error message), and the other notices (`setWidget`, `notify`, any other key) are still dropped. The chat draws a chip next to the state of the session: `memory ready` (quiet), `memory disabled` (yellow), `memory offline` and `memory error` (red); nothing without a known category or when the session is closed. Known limits: it shows what the plugin says, not a test that it saves and recovers (that needs a real session and spends tokens); and the chip shows what the plugin said LAST: if the memory comes back but no call is made, it keeps the old category until the next call (a successful one makes it `ready`).

### When each flow button appears

One rule set (`flowButtons` in `public/view.js`) decides the buttons of a repo's local card; the page and the tests share it. The column comes from Git state alone.

| State of the repo | Column | Button |
| --- | --- | --- |
| Changed or untracked files | Changes | `/flow-commit` (hidden while a declared state says the work is not ready, see "Show /flow-commit anyway") |
| Changed files with a non-empty index (staged files) | Changes | `/flow-commit --unstage` instead of `/flow-commit`, with the staging bar |
| A `/flow-commit` or `/flow-commit --unstage` failed (attention) | Changes or Committed | `Retry /flow-commit` (or `Retry /flow-commit --unstage` while files are staged), with the reason and what the session said |
| Clean, commits ahead, no open PR for the branch | Committed | `/flow-pr` |
| Clean, commits ahead, an open PR from this branch | Committed | `/flow-pr (update PR)` |
| Branch already merged (or its remote branch deleted), clean tree | Merged (red mark) | `/flow-base`: starts from a fresh, updated base branch |
| Branch already merged, but files changed | Changes (red mark) | `/flow-base --stash` and no `/flow-commit`: the skill carries the uncommitted changes aside (stash, including untracked files), switches to the fresh base branch, updates it and restores them. It refuses and changes nothing when the work of the branch is not yet merged or its remote branch not yet deleted |
| Needs manual action (detached HEAD, commits on the base branch, merge or rebase in progress, diverged) | Wherever Git puts it | none |
| A `/flow-commit` is running | Changes or Committed | no `/flow-pr` and no `/flow-base` until it settles |
| Any command sent from the page is running (`/flow-commit`, `/flow-commit --unstage`, `/flow-pr`, `/flow-base`, `/flow-base --stash`, `fix-pr`, `put-in-conditions`) | Wherever Git puts it | the same buttons, disabled with a tooltip naming the running command, and `Merge`, `Re-run failed` and `Fix CI` of that repo disabled too; the status line says what is running |
| Open PR, checks failed | Pull requests (red) | `Fix CI` (any fix, in test or production code or configuration, as long as it serves the PR's own objective; for a transient failure it does not touch code and recommends `Re-run failed`; if the fix would change the PR's scope or needs a product decision it stops and asks), plus `Re-run failed` when a GitHub Actions run failed |
| Open PR, all checks passed and mergeable | Pull requests (first, green accent) | `Merge` |

**How a card returns after a fix.** `Fix CI` sends one order to the session (see below). The agent edits files and commits nothing, so the repo is dirty and its card moves to **Changes** with `/flow-commit`. After `/flow-commit` the repo is ahead and the card moves to **Committed**, where an open PR from the branch already exists, so the button reads `/flow-pr (update PR)`. `/flow-pr` pushes the fix to the same PR and its card goes back to **Pull requests** while the checks run. Nothing in the panel tracks this: each step is just the new Git state.

### Rooms

A room is a repo (a folder with its own `origin`) where you coordinate a group of repos (for example one room for your H2O projects and another for your tools). Repos do not declare which room they belong to, so the panel does, in `config.json`. You do not have to edit it: use the screen.

- **+ Room** (next to **+ Repo**) opens a dialog: a room name and its folder (the field suggests the folders of the repos already in the panel; a browser cannot open a native folder picker, so type or paste the path). Errors show inside the dialog.
- The card's **⋯** menu has an **Assign to room** group: one item per room (the current one is marked ✓) and **No room**. With no rooms it offers **Create a room…**.
- The Conformity tab's **Rooms** section has a **Remove room** button per room, with a confirmation.

By hand, the same data is (remember to escape backslashes in JSON, or use forward slashes):

```json
"rooms": [{ "name": "UPEN", "path": "C:\\Users\\you\\Developer\\upen\\upen-ceo", "repos": ["969522dd0c"] }]
```

`repos` holds repo ids (the `id` that `GET /api/config` shows for each repo). Rules: the name is trimmed, non-empty, at most 60 characters and unique (case-insensitive, the first wins); `path` must be absolute; `repos` keeps unique strings; a repo id belongs to at most one room (the first room wins). Reload the page after editing by hand.

- **Routes** (token required, like the rest): `POST /api/rooms/create` `{ name, path }`, `POST /api/rooms/remove` `{ name }` and `POST /api/rooms/assign` `{ id, room }` (`room` is a room name, or `null` to leave every room). They answer `{ rooms }`. `create` answers 400 with the reason when the name is empty, longer than 60 characters or already used, or when the path is not absolute, does not exist, is not a folder or has no `.git`; `remove` and `assign` answer 404 for an unknown room or repo. `assign` takes the repo out of any other room first, and removing a repo from the panel also takes it out of its room.
- **Removing a room never touches files.** It deletes only the entry in `config.json` (its members become unassigned); the room folder and the repos are never created, edited or deleted by the panel.
- **Entries the panel does not understand are kept.** An entry under `rooms` that is not usable (not an object, a bad or duplicate name, a relative path) is ignored at runtime but written back to `config.json` exactly as it was on every save, in its place, so a typo cannot erase a room. `GET /api/config` lists them in `roomIssues` (short strings such as `rooms[2]: path must be absolute`; `[]` when all is fine) and the Conformity drawer shows "N entries in config.json under rooms are invalid and ignored" with the reasons. Fix the entry in the file by hand. A `rooms` value that is not a list is reported the same way, kept as is, and the panel refuses to create a room until you fix it.

- **Room requirements** (`roomRequirements` in `requirements.json`, evaluated against the room repo's remote base branch, all required): `room-base-branch`, `room-agents-file` (`AGENTS.md`), `room-enlaces-file` (the link map `ENLACES.md` at the root or under `estrategia/`, because the template does not fix the path) and `room-enlaces-sections` (a markdown heading for each of Proyectos, Contratos, Dependencias, Cola and barrido, matched case-insensitively inside the heading text; the detail lists which are missing). It only proves the headings exist, not that they are filled in. The repo that is the folder of a room is judged with these requirements in its card and in Conformity (matching the room path ignoring slashes and case), and it never receives the member order: its card menu does not offer "Put in conditions" and the server refuses it.
- **Member requirements** (a repo listed in a room; in `requirements.json` a requirement can have `"onlyInRoom": true`, omitted for repos outside every room, and `"levelInRoom"`, which replaces its level for members): `sala-region` (required: the `ciclo` block holds both `<!-- SALA -->` and `<!-- /SALA -->`) (since padrón 1.2 `ciclo-block` is required for every repo, so no real requirement uses `levelInRoom` any more; the mechanism stays for a future one). `ready` is unchanged: every required requirement, after that override, must pass. `GET /api/requirements?id=` adds `room: { name }` for a member; for any other repo the answer is the same as before. `requirements/INSTALL.md` tells the agent to keep the SALA region (both marker lines and everything between them) when the repo is a member of a room or when the order names `sala-region`, and to remove it only when neither applies.
- `GET /api/rooms` returns, per room, its requirement results and `lastCommit` (ISO date of the room's local `HEAD`, or `null`).
- The Conformity drawer does not say "All repositories conform." while the rooms load, fail to load, or any room has a required requirement that is not passing.
- **Not covered**: that a member repo is listed in `ENLACES.md` (free markdown, it would give false positives) and whether the room is behind (last sweep older than merged PRs). Nothing here edits the room or its members; the agent applies remedies and you deliver them with `/flow-commit` and `/flow-pr`.

`base` is the branch work is merged into. When omitted, the panel reads it from `origin/HEAD` and falls back to `main`. `roadmap` is the repo-relative path of its plan file (default `docs/ROADMAP.md`); unsafe values (absolute, starting with `-`, or containing `..`) are ignored.

### Adopted sessions

The panel keeps ONE adopted session per repo and per room (`sessions` in `config.json`). Sessions are read from Gentle Shell's folder (`~/.gentle-shell/agent/sessions/--<folder>--/<timestamp>_<id>.jsonl`, overridable with `REPO_PANEL_SESSIONS_DIR`); the listing reads only the first and last 64 KB of a file, and the chat history the last 512 KB. Routes (token required; `id` is a repo id or `room:<name>`, 404 when unknown):

- `GET /api/sessions?id=` answers `{ key, adopted, adoptedFound, sessions, live }`: `sessions` are the newest 20, `live` is `{ state: none | free | working | waiting, count }` from the RPC host (RPC2b-1: `idle` is `free`, `busy` and `starting` are `working`, `asking` is `waiting`, `closed` is `none`; a room key is always `none`).
- `POST /api/sessions/adopt` `{ id, session }` (400 when `session` is not one of the listed ids) and `POST /api/sessions/release` `{ id }`.
- `POST /api/rpc/start` also adopts the session id it runs under when the repo has none adopted (an adopted one is never replaced), so the chat reads its history; `POST /api/sessions/adopt` and `release` stay.
- `GET /api/chat?id=<repoId | room:Name>&session=<optional>&limit=<optional>` is the read-only history of a session, for the chat panel. It reads ONLY the last 512 KB of the session file (the first, possibly partial, line is dropped; a file can be 25 MB) and answers `{ key, sessionId, found, items, truncated, updatedAt }`. `session` defaults to the adopted one; an explicit one must match the id pattern and be one of the listed sessions of the folder (400 otherwise); an unknown key is 404; with no adopted session and none given the answer is `sessionId: null, found: false, items: []`. `items` are oldest first, at most `limit` (default 30, maximum 100): `{ role: "user" | "assistant", text, at, tools }`, plus `thinking: true` on an assistant item where the model reasoned (the chat shows «thinking…»; it is only the mark), and `stop: "aborted" | "error"` on an assistant item whose turn was stopped or failed (from the `stopReason` of the message: only that category travels, never its `errorMessage`; a stopped turn with no text is an item too). A compaction of the context is an item `{ role: "system", kind: "compaction", text: "", at, tools: [] }` in its place, without its summary. An item with tools also carries `toolInfo`, one entry per tool in the order of `tools`: `{ name, ok, ms, arg }` plus, once the result is there, the NUMBERS `size` (the characters of the result text) and, for an `edit`, `add` and `del` (the lines its unified diff adds and removes): never any text of the result or of the diff (`ok` true or false from the result, `null` while it has no result; `ms` its duration or `null`; `arg` the main argument of a KNOWN tool as ONE line of at most 80 characters: the path of read/edit/write/ls (never a URL), the pattern of grep/find, the host of a fetched URL (`https://host/…`, http, https or ftp only: never its user, password, path or query), the NAME of a subagent; a web search or a subagent label shows nothing). A shell command (`bash`) is NOT cleaned with patterns, because no pattern list knows every form a secret takes (two independent checks found 23 and then 12 forms that got through): it is rebuilt from vocabularies known in advance (`server/redact.js`). Shown: a known program, only at the start of a command or after an operator (`git`, `npm`, `node`, `ls`, `curl`...), the first subcommand of a few CLIs (`git`, `npm`, `docker`...), flag NAMES made of letters (never their values), a file with a known extension or an absolute path, `NAME=…` for an uppercase environment name, and the host of a URL. A quoted run, an unknown program and every other word become `…`. The patterns (authorization headers, secret-named flags and variables, `user:password@`, private keys, GitHub / `sk-` / Slack / AWS / Google / npm / JWT token formats, long random-looking strings) still run on every summary as a second layer. Accepted limits: the NAME of an absolute path or of a host and the text of a grep or find pattern are shown as they are (they are names the agent works with, not values it passes to a command), so a secret used AS a file name, a host name or a search term is not hidden. Also shown: the first word after a known CLI (`git`, `npm`...) when it is only lowercase letters and hyphens, the NAME (not the value) of an uppercase environment variable, and a word glued to a known extension (`echo x.md`). Nothing else of the arguments (the body of a write, the old and new text of an edit) and none of the result text is included. The thinking text and the tool results are never included, a tool is its NAME plus `toolInfo`, and tool-only assistant messages are folded into the `tools` of the next assistant item with text (a trailing run becomes a final item with empty text, the session is still working). Text is capped at 4000 characters per item (with `…`) and control characters other than line feed and tab become spaces (CR and CRLF become LF, the blocks of one message are joined with a blank line, so line breaks are kept). `truncated` is true when older messages exist beyond the 512 KB window or the `limit`; `found` is false when the file does not exist; a corrupt line is skipped. The route never writes anything.
- `GET /api/chat/result?id=<repoId | room:Name>&call=<tool call id>` (token required) is the cleaned START of the text of one tool result, for the click on a chip. It answers 403 unless `chat.showResults` is `true` in `config.json` (off by default) and 403 for the result of `read` (the contents of a file); 400 for a call id that is not 1 to 80 letters, digits, `_`, `.`, `:` or `-`; 404 for an unknown chat or for a call that has no result in the recent 512 KB of the adopted session. It answers `{ call, name, ok, text, truncated, size }`: `text` is at most 300 characters from the START of the result, with terminal sequences (colours, titles, cursor) and control characters removed, every line break (LF, CR, CRLF, NEL, U+2028, U+2029) ending a line, every line of the form `UPPERCASE_NAME=value` (also `export`, `set`, `declare -x`, `$env:NAME=` and spaces around the `=`) losing its value, and the patterns of `server/redact.js` applied as a second layer (they are not enough alone: that is why the switch is off by default). A tool is refused when its name, read as a person would (accents, invisible characters, spaces and punctuation inside it ignored), is `read`, has `read` among its words (`read_file`, `mcp__fs__read_file`, `ReadManyFiles`) or holds a file-reading compound (`readFile`, `readTextFile`, `fileRead`), but not `thread`, `Reader` or `readme`. Also refused by name: `cat`, `view`, `slurp` and the common file getters (`view_file`, `open_file`, `get_file_contents`, `fetch_file`, `load_file`...). Accepted limits of free text: a lowercase variable name, a prefix such as `+ ` or `12:` before an assignment, `password: value` in JSON or YAML, the continuation lines of a value in quotes or a heredoc that spans several lines, less common ways to set a variable (`Set-Item Env:`, `setenv`, `ENV[NAME]=`), a secret as prose, a homoglyph or an unusual name of a tool that prints a file, and the output of any other tool that prints a file (`bash` running `cat`). It is never part of `GET /api/chat`: with the switch on, that answer only adds `results: true` and an `id` (the call id) to each chip of `toolInfo`, and with it off the answer is exactly what it was.
- `GET /api/settings` and `POST /api/settings` (token required) are the options of the panel that the page may read and write, over a CLOSED list kept in `server/settings.js` (today only `chat.showResults`). `GET` answers `{ options: [{ key, value, default }] }` and nothing else of `config.json` (never the port, the groups and their paths, the rooms or the sessions). `POST` takes `{ key, value }`: a key that is not in the list, a key that is not text, a value of another type than the one the entry says (`chat.showResults` takes only `true` or `false`) or a body that is not an object is a 400 and the file is not touched; a write changes only what the entry says and keeps every other key of `config.json` as it was; it answers the list as it is now. Anything else is changed by hand in `config.json`.
- The **Settings** tab (the fourth, after Conformity; never the tab the page opens on) lists the options in a grouped list: Chat, Pi, Delivery, Visual and Director. Each row says where it is saved: «Panel» (in `config.json`, for every browser: the privacy switch `chat.showResults` through `POST /api/settings`, and «pi to use» through `POST /api/pi-runtime`, the same selector as in Conformity) or «This browser» (the preferences the page already kept: merge method, delete the branch after merging, clean repos as a column, diff view; they never go to the server and the controls of the bar stay in step). The defaults shown are the real ones (delete the branch and clean repos as a column are on). What is not built yet (the variables passed to the sessions, the agents in parallel of the Director) is shown disabled and marked «Planned».
- **One copy of each message (RP155).** While a tool runs, the history already holds the message the assistant wrote before it (it is saved as soon as it ends) and the live bubble of the session still keeps the same text until the run ends, so the chat used to show it twice. The live bubble is now not drawn when it says the same as the last answer of the assistant with text that comes after your last message in the history (spaces collapsed, the way the pending messages compare); when the history does not have the message yet it is drawn, so there is no gap, and while the copy is hidden the `working…` line stays so the chat never looks stopped. The live text also holds only the message being written now: every message starts with it empty (the page used to keep the text of the earlier messages of the run too, so a run with several messages showed all of them together). Known limit: two messages that are really identical and follow each other hide the live copy until the run ends, and then the history shows both.
- **One address per screen in Summary (RP133).** The address of the page follows the open repo and its zone: `#/repo/<id>/<zone>` with the zone `chat` or `repo` (when reading, no zone means chat), the list is the empty address, and `#conformity` still opens Conformity. Opening a repo, changing the zone and closing the chat write an entry in the browser history, so Back and Forward walk those screens and a link reopens the same place. The address is untrusted: only an id that is in the list of repos counts (exact text, letters, digits, `_` and `-`, up to 64 characters), nothing is decoded (a `%` is refused), evaluated or drawn as markup, and anything else is ignored and the address bar goes back to what is open. A chat that has no address (a room) leaves the bar alone. The zone has no buttons yet (they come with the mobile layout): it changes with the address.
- **Subagent working** (RP152): while a subagent runs in the open session, the chat shows `Subagent working · mm:ss` right after the state of the session (`2 subagents working` when there are two; the counter starts when the first one started and moves by itself every second). It is made only of the live events the page already receives (`tool_execution_start` and `tool_execution_end` of the tool `subagent_run`, whose arguments the server never forwards) and goes away with the end of the run, an abort, a closed session or a (re)connect: what the page does not know is never shown as working. It never says slow (that needs activity data), it does not show the name of the agent, and a subagent started in the background ends its call at once, so it is not shown while it keeps running.
- **Context meter** (RP139): next to the state of the session and the memory chip, the chat shows how much of the context window the session uses, for example `ctx 62%`; the help text says `Context used by this session: 124k of 200k tokens`. Right after a compaction the figure is unknown and it reads `ctx —` (never 0%). The chip is quiet below 70%, warns from 70% and warns strongly from 90% (icon, number and words in the help, never colour alone), and nothing is drawn while the session is closed or starting. `GET /api/rpc/context?id=` (token and host check, like `/api/rpc/status`) asks the live session for `get_session_stats` and answers ONLY `{ tokens, percent, window }` (finite non-negative numbers or null, percent clamped to 0..100; any failure or odd answer is all null; 409 when the repo has no session). The page reads it when a chat opens, when a run ends and when a compaction ends, never on a timer. It is read-only: it changes no pi setting and leaves auto-compaction as it is.
- **Compact by hand** (RP140): a small `Compact` button next to the `ctx` chip compacts the context of the session of the open chat, at any moment the session is live (idle or answering); it is not drawn while the session is closed, starting, asking you something or already compacting. While it lasts the state reads `Compacting…` instead of `Idle` or `Working…` (also when the session started the compaction by itself) and a message cannot be sent. Compacting an answer in progress stops that answer first, so on a busy session the page asks `The session is answering. Compacting stops that answer first. Compact anyway?` and sends nothing if you decline. `POST /api/rpc/compact` (body `{ id, force? }`, token and host check) is decided by the server alone: only an idle session gets the command (a busy one only with `force` exactly `true`), a second call while one is running is a 409, the page never chooses instructions for the compaction, and the answer is only `{ compacted: true }` or a fixed message (already compacted, too small, failed, timed out). A timeout does not release the in-progress mark while the session still says it is compacting: its end event does, and a second compact stays refused meanwhile. On success the history is read again (the `Context compacted` marker) and the context is measured again. The panel never changes auto-compaction: it stays as it is and no pi setting is written.

### Claude usage bar

The header shows how much of your Claude limits you have used (RP96): two compact meters, **5h** and **7d** (the 5-hour and the 7-day window; there is no monthly or per-model figure in the data), each with a fill bar, the percent used and a countdown to its reset (`2h 29m`, `4d 14h`). A thin **pace mark** on each bar shows how much of the window has already run: if the fill is past the mark you are using it faster than the clock. The fill is green under 70%, yellow from 70% and red from 90% (RP144), and those two also carry a `⚠`, so the warning never depends on colour alone; grey is kept for old data. A dash (`5h –`) means that window already reset or was not reported. Grey meters with a small yellow dot in front (RP147) mean the data is old: the file was last updated 15 minutes ago or more, and the dot's tooltip says how old (`Usage data is 20 min old`). `Claude usage: no data` means there is no usable file yet. Hover it, click it or focus it with the keyboard to open a popover with each window's wide bar, `N% used`, `Resets in …`, the exact reset time, how much of the window has run, a written warning when it runs ahead of the clock, and how old the data is; Esc closes it. On a narrow header only the percents stay. It only reads `GET /api/usage`: nothing about that route or the extension changed.

The data comes from a small file that an extension of the agent writes (`~/.gentle-shell/agent/claude-usage.json`); set `REPO_PANEL_USAGE_FILE` to read another path. The panel only reads it, on every request, through `GET /api/usage` (answer: `available`, `five`, `seven`, `updatedAt`, `stale`). The page asks every 30 seconds while the tab is visible. Sessions that were already open must be restarted to load that extension, or they never write the file.

## Responsiveness

- **Interactive lane.** What the person does is served first: every POST (except the read-only `POST /api/queue` and `POST /api/conformity`) and any GET sent with `x-priority: user` (the page sends it when a card's chat is opened). Such a request may use up to 2 child processes over the cap and goes before waiting automatic refresh work. The periodic refresh stays in the background lane.
- **`REPO_PANEL_MAX_PARALLEL`.** Caps the child processes (git, gh) the panel runs at once, so a refresh of many repositories does not starve the machine. A positive integer; default 8 (absent, invalid, 0 or negative values fall back to it).
- **`GET /api/perf`** (needs the token, does not record itself). Answers `{ routes, queue }`. Per route, over its last 200 requests: `n`, `p50`, `p95` and `max` in ms, `waitP50` (median wait for a process slot), `procsAvg` (processes per request), `executions` (handler runs; identical concurrent GETs share one) and `priorities` (counts of `user` and `background`). `queue` is `{ active, max, waitingBackground, waitingUser }`.
- **Server-Timing.** Every JSON answer carries `Server-Timing: total;dur=<ms>` and, when the request waited for a slot, `queue;dur=<ms>`.
- **Slow log.** A request of 1500 ms or more prints one console line (route, ms, queue wait, process count) at most once per route every 10 s. Nothing else of the request is logged.
- **Summary store (RP78).** `GET /api/summary` no longer builds the board per request: the server keeps every repo's facts in memory (`server/summarystore.js`) and answers a snapshot at once with no Git or `gh` call. Each fact has its own age: the local state and the repo state are read every 15 s, the pull requests, the roadmap and the last commit every 60 s, a pool of 3 repos at a time, in the background lane; a read that does not answer in 90 s counts as failed. Nothing is read until a page asks for the first time (no client, no work), so a server started only for a request stays passive. The session of a row is the RPC host's live state, read when the snapshot is built (RPC2b-1; `starting` counts as working). A repo whose facts were not all read yet is a `loading` row (a calm "Loading…" card with no action, counted as idle, sorted last); a failed read keeps the last good value and the row carries `stale: { facts }`, the card is marked busy (`aria-busy`) and its tooltip says "Updating: <facts>" (RP94b: there is no "Updating…" text; also set when a fact is older than 3 times its interval). A fact that never succeeded gives the usual error row. `?fresh=1` reads every fact of every repo again before answering. When nobody asked for the Summary for 60 s the loop slows down to 30 s and 300 s, and a request speeds it up again. `server.js` starts the loop; creating a server does not. Hot repos (the current branch has an open pull request) re-read their pull requests every 15 s and their local state every 10 s while a page is active, and after a merge, re-run, fetch, a command to the session or a chat message the server re-reads that repo at once and once more 5 s later.
- **Board from memory (RP80).** `GET /api/board?since=N` answers at once, from the Summary store's memory and with no Git or `gh` call, `{ rev, repos, refreshing }`: the repos whose facts changed after revision `N` (all of them for `0`; `400` for a `since` that is not an integer >= 0, `404` without a store). Each repo carries its `rev`, the last-success time `at` of each fact, `errors`, `stale` and the values `local`, `prs`, `roadmap`, `state` and the new sixth fact `req` (the requirements, read every 60 s like the pull requests and never part of the Summary). `POST /api/board/refresh` answers `{ started: true }` at once and re-reads everything (or only `{ id }`) in the background. F5 paints from that memory immediately and re-reads in the background, with the Updating indicator of the header shown while the server reports repos in `refreshing`; after a command sent from the page ends, or a fetch or merge, the page asks the server to catch up that repo and its own direct reads win over an older board fact. A server restart (a lower `rev`) is followed, not ignored. The old per-repo routes are unchanged: if the board answers 404 or fails three times in a row, the page falls back to them and retries the board slowly. `API_VERSION` stays 15.
- **After an action (RP86b).** When the person's own action ends (a flow button, a fetch, the end of a session) the page used to read five routes of that repo directly (`/api/local`, `/api/prs`, `/api/roadmap`, `/api/requirements`, `/api/state`) and ask the board to catch up. While the board answers, it now reads directly only `local`, `prs` and `state` (what an action changes, and the freshest signal after one: the board is polled every 3 s); the roadmap (about 240 KB on a big repo) and the requirements arrive by the board, as long as the page already holds them for that repo (a repo with no roadmap is held: the server answers `{ available: false }`; a failed read, which leaves `null` or a failed state, is not held and is read again). A fact the page does not hold, a board that is down or never answered, and a refresh that is not an action keep the five direct reads. Measured on this repo: the five in parallel took a median of 1,841 ms and `local` plus `prs` alone 1,039 ms.
- **Request timeouts.** The page gives up on a GET after 25 s and on a POST after 70 s ("Request timed out"); the Summary, which builds the whole board, has its own 90 s limit until RP78. Switching or closing the chat card cancels its pending reads.
- **Identical reads are shared.** Two identical GETs in flight run once, per lane: an interactive request never joins a background one that may have waited in the queue.
- **A malformed URL answers 400** (and a wrong Host 403) and never takes the server down.
- **Known limits.** The background lane has no aging: an endless chain of interactive requests would delay it (human clicks never do). With the default limit of 8 the wait of an interactive request for a process slot is about 0 ms.
- **`scripts/measure-panel.js`.** `node scripts/measure-panel.js [--port 4398] [--json]` starts its own temporary panel on its own port (a copy of your config, no browser polling it) and times the Summary, each per-repo route, a full refresh and the wait of an interactive read during it. It only sends GET requests: it never runs an action or sends anything to a session.

## Merge behaviour

- Clicking **Merge** merges immediately, with no confirmation (like GitHub's own button). It is only enabled when the PR is green and mergeable.
- Merging goes through the GitHub API, so your local branches and working tree are never touched.
- The server re-checks readiness right before merging and pins the merge to the PR head SHA, so a late push cancels it.
- *Delete branch* is offered only when the repo does not already delete merged branches (`deleteBranchOnMerge`). If GitHub already removed the branch, that is treated as success, and local branches whose remote disappeared show as "remote branch deleted" instead of an error.
- A repo whose current branch (other than the base) already landed gets a red **Merged: run /flow-base** mark and goes to the top of its column. The panel flags it when the remote branch is gone or a merged PR came from that branch, and not when a new open PR reuses the branch name.
- `GET /api/roadmap?id=<repo>` returns the parsed `docs/ROADMAP.md` read with `git show origin/<base>:<path>`, never from the working tree, so a unit counts as done only once its PR is merged. Run a fetch to see newer data. A repo without the file answers `available: false` (not an error).
- `GET /api/summary` (token required; read-only; `?fresh=1` skips the cache) returns `{ rows, counts, attention, generatedAt }`, one row per configured repo, built only from what the other routes read (`localState`, `prState`, `roadmapState` with its derived states, `readState`, the session screens, `lib.workQueue`; the session comes from the RPC host). A row always has every field and a value that is not known is `null`, never invented: `{ id, name, group, room, branch, progress: { total, completada, enRevision, bloqueada, pendiente, enCurso }, session: { state }, next: { id, entrega, resultadoVisible } | null, blocking: [{ unit, waitsFor, external }], lastMovement: { at, what }, action: { kind, label, pr } | null, error, needs, rank }`. `needs` is true when the repo is in `attention` (an asking session, a PR with failing checks, or a `Bloqueada` unit only when the repo has no takeable next unit; false for error rows) and `rank` is its urgency, lower is more urgent, from one definition in `server/summary.js` that reuses `lib.QUEUE_RANK`: 0 a session asking you, 1 failing CI, then the "Go work on" kinds in their own order (2 `merge`, 3 `branch` and `manual`, 4 `waiting`, 5 `deliver`, 6 `start`), 7 a working session, 8 a blocked repo, 9 everything else and error rows. `progress` counts each roadmap row once: `enRevision` and `enCurso` come from the derived states (not the hand-written column) and a derived `Lista` row stays in `pendiente`; the values are `null` when the repo has no readable roadmap. `session.state` maps the session: `none` (closed), `free` (idle), `working` (busy), `waiting` (asking a question) and `unknown` (a state the vocabulary does not know; `starting` is `working`). `blocking` has at most 3 entries: the `Bloqueada` rows (`waitsFor` their table dependencies, `external` the dependencies that are not rows) and, when no unit can be taken, the first `Pendiente` row with its unmet dependencies. `lastMovement` is the date and subject of the local `HEAD` commit (both `null` when Git cannot say). `action` is the first entry of the "Go work on" queue for that repo (`merge`, `branch`, `manual`, `waiting`, `deliver` or `start`; `pr` only for `merge`), except that a session in `waiting` gives `{ kind: "answer", label: "Answer the question in the session" }`; it is `null` when there is nothing to do. `counts` classifies each repo once (`waiting`, `working`, `blocked` by `blocking`, otherwise `idle`; error rows are not counted) and `attention` lists the repos with an asking session, a PR with failing checks or a blocked unit with no takeable next unit, with a `why`. A repo with a `Bloqueada` unit AND a next unit it can take does not need attention (`blocking`, `counts.blocked` and `rank` do not change). **A repo whose Git or `gh` read fails gets a row with `error` set and nulls; the others are unaffected.** Repos are read six at a time, and the whole response is cached for 10 seconds. `API_VERSION` does not change.
- Branch protection and required reviews on GitHub still apply.

## Computed unit states

The roadmap file only holds `Pendiente`, `En curso`, `Completada` and `Bloqueada`. The panel adds three states computed from Git and GitHub, never written in the file. A unit is linked to work by its ID as a complete token in a branch name or in an open PR title (`p2` matches `p2-header` and `feat/p2_x`, not `p20-x`, `p2.1-x` or `rp3b-x` for `rp3`).

- Precedence per unit: `En revisión` > `Lista` > `En curso` (derived) > the state written in the file. `Completada` and `Bloqueada` units are never overridden.
- `En revisión`: an open PR has the ID in its title or head branch.
- `Lista`: the current branch has the ID and the tree has changes or commits over the base, or another local branch with the ID has commits over `origin/<base>`.
- `En curso` (derived): a local branch with the ID exists, but it has no commits over the base and the tree is clean. A row written as `En curso` in the file creates no derived entry; it is only replaced when it becomes `Lista` or `En revisión`.
- `siguiente` skips every unit that has a derived state.
- A branch merged by squash still counts as not merged for Git, so it can only affect units that are not `Completada`, and it is ignored when its remote branch was deleted.

Known limits and what is not verified:

- Not seen in a browser: the card warning, the ⋯ menu, closing it by clicking outside or with Escape, and the drawer's passing list keeping its open state. Only the pure helpers (`cardWarning`, `cardMenu`) and the server routes are tested.
- The `put-in-conditions` order was never typed into a real session: not verified that the agent can read a file outside the repo from the order (it now goes by RPC `prompt`).

- Rooms: the room tag, its dot, the **+ Room** dialog, the **Assign to room** menu group, the **Remove room** confirmation and the drawer's Rooms section were never seen in a browser (only the pure helpers and the routes are tested); neither were the dialog's focus and keyboard behavior.
- Only the first 30 local branches are inspected; a matching branch beyond that is not seen.
- The real GitHub path (`En revisión` from `gh pr list`) and its rendering in the browser have no automated test; pure functions cover the logic.
- The requirements and prerequisites blocks of the Conformity drawer have no browser test: their rendering (collapsed passing list, remedy lines, loading and failed messages) and the badge count were not seen on screen. Unit tests cover the checks, the routes and `conformityView`.
- The conformity view was only checked with a headless screenshot of the open drawer. Not verified in a browser: clicking the button and a repo name, closing the drawer, the `All repositories conform.` message, the `no-base` and `no-repo` statuses, and a repo whose only problems are info-level. Unit tests cover the report logic.

## Page code

The page is plain scripts with no build step. `index.html` loads them one after the other and they share the global scope (the state `S`, the helpers and every function), so the order matters: every file except the last only defines things, and touches the page when one of its functions is called, never while it loads. Three files are pure (data in, HTML out) and the page tests share them: `public/view.js`, `public/highlight.js` (the syntax colors of the file and diff viewer: JavaScript and TypeScript, JSON, CSS, HTML, Markdown and shell, files up to 2,000 lines; the text of a file is always escaped, the only markup it adds is a token span) and `public/resumen.js`. The rest is split by layer, in load order:

- `public/data.js`: the requests to the server (with their pool) and the reads of each repo.
- `public/feed.js`: the event stream, the board data and the refresh ticks.
- `public/tabs.js`: the derived state, the "go work on" queue and the Summary and Conformity tabs.
- `public/chat.js`: the chat, its composer, the notes pad and the three-block layout.
- `public/board.js`: the Work board and its cards.
- `public/actions.js`: the click handlers (`data-act`): merge, re-run, rooms and the usage bar.
- `public/app.js`: only the boot (the state, the document listeners, the timers and the first load). It loads last because it is the one that runs at load.

A new page script goes into `index.html`, into the closed list of static files in `server/http.js` and into `test/pagesrc.js`, in that order of loading.

## Security

The server binds to `127.0.0.1` only, rejects unknown `Host` headers (DNS rebinding), requires a random per-run token on every API call, and only operates on repositories listed in `config.json`. The one place where the panel writes inside a repo is the notes file (`POST /api/notes`, RP93): a fixed path, never one sent by the page, refused through links, and out of Git.
